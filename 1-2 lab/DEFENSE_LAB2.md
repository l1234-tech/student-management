# Конспект к защите лабораторной №2 — Backend и REST API

> **Проект:** система управления студентами общежития.  
> **Фактический стек:** Python, Django, Django REST Framework, HTML/CSS/JavaScript, серверный JSON-файл.  
> **Цель:** перенести хранение и бизнес-логику на backend, реализовать REST API, серверную валидацию, CRUD, фильтрацию, корректные HTTP-статусы и stateless-взаимодействие.

## Ответ на вводный вопрос: что изменилось относительно лабораторной №1?

В лабораторной №1 основная логика списка выполнялась в браузере. В лабораторной №2 браузер стал клиентом серверного API: он отправляет HTTP-запросы, получает JSON и отображает результат. Backend построен на Django и Django REST Framework. Маршруты связывают URL с обработчиками, serializers проверяют входные данные, services реализуют предметные правила, repository читает и записывает серверный JSON-файл. ИСУ выступает идентификатором. Реализованы получение списка и отдельного студента, создание, частичное изменение, удаление и фильтрация. Проверки выполняются не только в браузере, но и на сервере, поэтому их нельзя обойти простым выключением JavaScript.

## 1. Python в серверной веб-разработке

Python — язык общего назначения с читаемым синтаксисом и динамической типизацией. В backend его используют для обработки HTTP-запросов, бизнес-правил, валидации, работы с хранилищем и формирования ответов.

Плюсы — высокая скорость разработки и развитая экосистема. Ограничение — часть ошибок типов обнаруживается во время выполнения, если их не поймали тесты или анализаторы.

В проекте код `1-2 lab/students/` разделён на `views.py`, `serializers.py`, `services.py`, `repository.py`, `errors.py` и `exceptions.py`.

```python
def get_student(ISU: int) -> dict:
    student = repo.get_by_id(ISU)
    if student is None:
        raise NotFound(f"Студент с ИСУ {ISU} не найден")
    return student
```

Аннотации показывают ожидаемые типы, но логика функции реально проверяет отсутствие студента и выдаёт осмысленную ошибку.

**Ответ:** «Python применяется для маршрутов, валидации и бизнес-логики. Django обрабатывает web-запросы, DRF помогает сериализовать и проверять данные, сервисный слой реализует правила системы студентов».

## 2. FastAPI, Flask и Django REST Framework

Framework — набор средств, задающий основу приложения и берущий на себя повторяющиеся задачи вроде маршрутизации и формирования ответов.

- **Flask** минималистичен; много компонентов разработчик выбирает самостоятельно.
- **FastAPI** использует аннотации типов и Pydantic, поддерживает async и автоматически строит OpenAPI-документацию.
- **Django REST Framework** добавляет к Django инструменты REST API: serializers, API views и связанные механизмы.

Задание допускает разные технологии, но **наш фактический код лабораторной №2 использует Django + Django REST Framework**, а не FastAPI.

В `students/views.py` используются `@api_view` и `Response`:

```python
@api_view(["GET", "POST", "QUERY"])
def api_requests(request):
    ...
```

**Ответ:** «Мы выбрали Django и DRF. Django предоставляет основу приложения, а DRF облегчает работу с API, сериализаторами и HTTP-ответами. FastAPI и Flask — альтернативы, но не технологии нашего решения».

## 3. Типизация Python и аннотации типов

Python динамически типизирован: тип относится к объекту, на который указывает переменная. Аннотации документируют контракт и помогают IDE и статическим анализаторам, но сами по себе не проверяют значение во время выполнения.

В проекте:
- `ISU: int` — ожидается целый ИСУ;
- `filters: dict` — ожидается словарь фильтров;
- `-> list[dict]` — ожидается список словарей;
- `dict | None` — словарь либо `None`.

Например, `list_students(filters: dict) -> list[dict]` описывает вход/выход функции. Но если запрос содержит строку вместо числа, реальную проверку должен сделать serializer или явная логика сервиса.

**Ответ:** «Аннотации помогают понимать код, но не заменяют валидацию. Данные HTTP-запроса проходят через DRF Serializer, который проверяет типы, диапазоны и формат».

## 4. Модели данных: dataclass, Pydantic, словари и serializers

- **Словарь** — структура ключ–значение; удобно для данных, похожих на JSON.
- **Класс** — описывает состояние и поведение.
- **dataclass** автоматически создаёт типичные методы класса данных.
- **Pydantic-модель** задаёт схему и валидирует входные данные средствами Pydantic.
- **DRF Serializer** в нашем проекте описывает поля, валидирует данные и формирует представление ответа.

Во второй лабораторной запись студента хранится как словарь с полями `ISU`, `name`, `group`, `dormitory`, `room`, `checkin_date`, `is_foreign`, `note`. Схема определяется в `StudentSerializer`.

```python
serializer = StudentSerializer(data=request.data)
serializer.is_valid(raise_exception=True)
student = services.create_student(serializer.validated_data)
```

Сырые данные превращаются в проверенный `validated_data). Далее service проверяет бизнес-правила, например уникальность ИСУ.

**Ответ:** «В нашей реализации модель записи представлена словарём, а DRF Serializer служит контрактом API: описывает поля, проверяет ввод и предоставляет проверенные значения».

## 5. Исключения и обработка ошибок

Исключение сигнализирует о ситуации, в которой обычный путь выполнения невозможен. `raise` выбрасывает исключение, `try/except` перехватывает конкретные ожидаемые ошибки. Нельзя бездумно подавлять все исключения, иначе будет трудно найти причину сбоя.

В проекте типы `NotFound`, `BadRequest` и `ConflictError` описывают отсутствие студента, неправильный запрос и конфликт уникальности. Service сообщает о проблеме, а HTTP-слой преобразует её в ответ API.

```python
student = repo.get_by_id(ISU)
if student is None:
    raise NotFound(f"Студент с ИСУ {ISU} не найден")
```

**Ответ:** «При отсутствии студента сервис не возвращает ложный успешный ответ, а выбрасывает NotFound. Слой API превращает это в корректный HTTP-статус и JSON-ошибку».

## 6. Декораторы

Декоратор — функция/объект, который оборачивает другую функцию или изменяет её поведение. Запись `@name` — синтаксис применения декоратора.

```python
@api_view(["GET", "POST", "QUERY"])
def api_requests(request):
    ...
```

В проекте `@api_view` регистрирует функцию как обработчик API DRF и указывает допустимые методы. Для отдельной записи используется другой набор методов: GET, PATCH и DELETE.

**Ответ:** «Декоратор `api_view` интегрирует функцию с DRF и ограничивает список разрешённых методов. Это часть маршрутизации/обработки API, а не комментарий».

## 7. Контекст HTTP-запроса и область видимости

Request-объект содержит метод, путь, заголовки, параметры, тело и другие данные текущего запроса.

В `students/views.py`:
- `request.method` — HTTP-метод;
- `request.query_params` — query-параметры URL;
- `request.data` — разобранное тело запроса.

При GET фильтры берутся из `request.query_params.dict()`; при QUERY — из `request.data`. Локальные переменные обработчика существуют только в рамках вызова. Общий список не является сессионным состоянием браузера: источник данных — серверный JSON-файл через repository.

## 8. Синхронный и асинхронный код

Синхронная функция выполняет операции последовательно. Асинхронная использует `async`/`await` и событийный цикл, чтобы при поддерживаемых I/O-операциях не блокировать выполнение ожиданием.

Асинхронность особенно полезна при большом количестве ожиданий сети, но не ускоряет автоматически вычисления и не помогает, если внутри async-функции вызвать блокирующую операцию.

В backend лабораторной №2 обработчики объявлены обычным `def`: это синхронный код. На клиенте функции `loadStudents` и `deleteStudent` в JS используют `async/await`, потому что ждут ответ `fetch()`. Асинхронность браузера не означает, что Python backend тоже асинхронный.

## 9. Итераторы, генераторы и коллекции

Коллекция хранит элементы. В нашем коде список студентов — список словарей. В `services.list_students(filters)` фильтрация реализована через list comprehension:

```python
students = [s for s in students if s.get(key) == value]
```

Каждый фильтр сужает результат. Например, `group=M3301` и `dormitory=8` оставляют записи, подходящие по обоим критериям.

Итератор даёт последовательный доступ к элементам. Генератор позволяет производить значения по требованию (обычно через `yield`). В этом сервисе используются обычные списки, не генератор. Фильтрация выполняется в памяти после чтения JSON, поэтому на большом объёме будет менее эффективной, чем запрос к БД с индексами.

## 10. Модули, пакеты и слои backend

Модуль — Python-файл; пакет — организованный набор модулей. Разделение по слоям делает каждую часть ответственной за одну задачу.

| Файл | Ответственность |
| --- | --- |
| `students/urls.py` | связывает URL и обработчики |
| `students/views.py` | HTTP-запрос и HTTP-ответ |
| `students/serializers.py` | проверка и сериализация данных |
| `students/services.py` | бизнес-правила, фильтры, уникальность, наличие студента |
| `students/repository.py` | чтение/запись JSON-файла |
| `students/errors.py` | единый формат API-ошибок |
| `students/exceptions.py` | прикладные исключения |

Путь POST:

```text
HTTP POST -> urls.py -> views.py -> StudentSerializer
          -> services.create_student() -> repository.add()
          -> JSON-файл -> HTTP 201 + JSON
```

Так можно заменить механизм хранения, не переписывая HTML и весь слой HTTP.

**Ответ:** «Views связывают HTTP и приложение, serializer валидирует вход, service реализует правила, repository работает с файлом. Слои можно тестировать и изменять независимо».

## 11. REST и RESTful API

REST — архитектурный стиль взаимодействия вокруг ресурсов. URL обозначает коллекцию или конкретный ресурс, HTTP-метод задаёт намерение, а тело запроса/ответа часто содержит JSON.

- `GET /api/requests` — список;
- `GET /api/requests/123456` — студент;
- `POST /api/requests` — создание;
- `PATCH /api/requests/123456` — частичное изменение;
- `DELETE /api/requests/123456` — удаление;
- `QUERY /api/requests` — специальная фильтрация из требований лабораторной.

QUERY не относится к классическому набору базовых HTTP-методов вроде GET/POST/DELETE; здесь он реализован по явному требованию задания и должен одинаково поддерживаться frontend и backend.

## 12. HTTP-методы и статус-коды

| Метод/статус | Смысл | Пример |
| --- | --- | --- |
| GET | чтение | получить список |
| POST | создание | добавить студента |
| PATCH | частичное изменение | поменять комнату/заметку |
| DELETE | удаление | удалить по ИСУ |
| QUERY | фильтрация по телу | сложный набор фильтров |
| 200 OK | успешно | чтение/изменение |
| 201 Created | создано | POST успешно создал студента |
| 204 No Content | успех без тела | DELETE |
| 400 Bad Request | запрос некорректен | неизвестный фильтр |
| 404 Not Found | ресурс не найден | неверный ИСУ |
| 409 Conflict | конфликт | повторный ИСУ |
| 422 Unprocessable Entity | данные не прошли валидацию | неверный формат/диапазон |
| 500 Internal Server Error | непредвиденная ошибка сервера | неожиданный сбой |

В коде создания используется `HTTP_201_CREATED`, удаление завершает ответом `HTTP_204_NO_CONTENT`. Конкретные ответы DRF могут зависеть от обработчика ошибок, поэтому статус стоит проверять на реальном запросе.

## 13. Маршрутизация, path- и query-параметры

Маршрутизация связывает URL и функцию-обработчик.
- **Path-параметр** — часть пути: `/api/requests/123456`, здесь `123456` — ИСУ.
- **Query-параметр** — после `?`: `/api/requests?group=M3301&dormitory=8`.

В `students/urls.py` есть маршрут списка и маршрут детали. Функция `api_request_detail(request, ISU: int)` получает ИСУ из пути. GET-список передаёт фильтры из `request.query_params.dict()`; QUERY получает их из JSON-тела в `request.data`.

## 14. JSON, сериализация и десериализация

JSON — текстовое представление данных. Сериализация превращает объект в JSON-строку; десериализация разбирает JSON в структуру программы. Валидация отдельно проверяет, допустимы ли значения.

На frontend `JSON.stringify(student)` сериализует объект; `response.json()` читает тело ответа как JavaScript-объект. На backend DRF разбирает тело в `request.data`, `StudentSerializer` проверяет его, а `Response({"data": ...})` отдаёт JSON.

**Модель студента:** ИСУ, ФИО, группа, общежитие, комната, дата заселения, признак иностранного студента и заметка.

## 15. Серверная валидация и обработка ошибок

Клиентскую проверку можно обойти, поэтому backend независимо проверяет входящие данные.

В `students/serializers.py`:
- типы и диапазоны ИСУ, общежития и комнаты;
- формат группы;
- ФИО;
- дата в ISO-формате, не ранее 2016 года и не в будущем;
- Boolean для `is_foreign`;
- наличие обязательных полей при создании.

В `services.py`:
- проверяется уникальность ИСУ при создании;
- проверяется существование студента;
- запрещено менять ИСУ через PATCH на другое значение;
- фильтры ограничены белым списком `FILTER_FIELDS`.

Пример уникальности:

```python
if repo.get_by_id(int(data["ISU"])) is not None:
    raise ConflictError(f"Студент с ИСУ {data['ISU']} уже существует")
```

В текущем JSON-хранилище уникальность контролирует приложение. Для реляционной БД надёжную защиту от конкурентных записей обычно дополнительно задают ограничением UNIQUE в самой БД.

## 16. Stateless-архитектура

Stateless означает, что сервер не зависит от сохранённой сессии конкретного браузера для обработки очередного запроса. Запрос должен содержать достаточно данных для операции. Это **не** означает отсутствие постоянного хранилища: список студентов сохраняется на сервере в JSON-файле.

При удалении frontend отправляет `DELETE /api/requests/123456). Сервер сам читает данные через repository, ищет запись с этим ИСУ и удаляет её; клиент не передаёт весь список.

**Ответ:** «Stateless — характеристика взаимодействия, а не требование хранить всё в памяти без состояния. Данные остаются на сервере, но каждый запрос обрабатывается независимо от сессии браузера».

## 17. Хранение и фильтрация в памяти/JSON-файле

JSON-файл используется как простое серверное хранилище. Repository инкапсулирует чтение/запись, сервис применяет правила.

Плюсы: не нужна отдельная СУБД, данные можно осмотреть вручную, удобно для учебного проекта. Минусы: нет полноценной транзакционности и индексов, параллельную запись нужно координировать, фильтрация проходит в памяти.

В `services.py` разрешены `ISU`, `name`, `group`, `dormitory`, `room`, `is_foreign`. Числовые значения преобразуются к int, после чего список последовательно фильтруется.

Пример тела QUERY:
```json
{"group":"M3301","dormitory":8}
```
Результат должен соответствовать обоим условиям.

## 18. CRUD и уникальная идентификация

CRUD — Create, Read, Update, Delete. API распределяет операции между методами:
- **List:** GET коллекции;
- **Read:** GET ресурса по ИСУ;
- **Create:** POST, валидация, проверка уникальности, сохранение;
- **Update:** PATCH, проверка частичного набора полей;
- **Delete:** DELETE, ответ 204;
- **Filter:** QUERY со структурой JSON.

ИСУ выбран как идентификатор, потому что ФИО может повторяться, группа и комната тоже не гарантируют уникальность. Повторный ИСУ даёт конфликт, несуществующий ИСУ — Not Found.

## Типовые дополнительные вопросы

**Почему фильтрация на сервере?** Правила едины для любых клиентов; JavaScript нельзя считать доверенным; API можно использовать отдельно от сайта.

**PATCH или POST для редактирования?** PATCH частично меняет существующий ресурс; POST обычно используется для создания или другой операции над коллекцией.

**Serializer или repository — в чём разница?** Serializer работает с контрактом API и валидацией; repository — с хранением и чтением данных.

**Почему не писать всю логику во view?** Смешались бы HTTP, бизнес-правила, валидация и запись файла; такой код сложнее менять и тестировать.

**Может ли GET изменять данные?** По смыслу HTTP GET должен быть безопасным методом чтения. Изменение делается POST/PATCH/DELETE.

**Почему DELETE возвращает 204 без JSON?** Код означает успешную операцию без тела ответа; frontend проверяет `response.ok` и не обязан парсить JSON для пустого ответа.

**Почему QUERY?** Таково требование задания для большого набора фильтров. Это нестандартный метод по сравнению с основными CRUD-методами, поэтому клиент и сервер должны согласовать его использование.

**Что будет, если отключить JS-валидацию?** Некорректный запрос всё равно должен быть остановлен backend Serializer/сервисом.
