## Лабораторная 1. Frontend

В первой лабораторной был реализован клиентский интерфейс системы управления студентами без frontend-фреймворков.

### Цель первой лабораторной

Нужно было сделать интерфейс, который работает прямо в браузере: пользователь добавляет студентов через форму, видит их в таблице, может открыть подробную информацию, удалить запись или перейти к редактированию. На этом этапе серверной части ещё не было, поэтому данные хранились на стороне клиента.

### Что было сделано

- Главная страница со списком студентов в виде таблицы.
- Форма добавления и редактирования студента.
- Страница досье конкретного студента.
- Кнопки действий: добавить, редактировать, удалить, открыть подробную информацию.
- Минимальный адаптивный интерфейс на HTML и CSS.
- Клиентская логика на JavaScript в отдельных файлах.
- Валидация формы через HTML-атрибуты и JS.
- Favicon с котиком.

### Реализация frontend-части

В первой версии логика была разделена по файлам:

```text
index.html          список студентов
student_form.html   форма добавления и редактирования
student.html        досье студента
css/style.css       стили и адаптивность
js/index.js         таблица, удаление, переходы
js/student_form.js  добавление и редактирование
js/student.js       подробная информация
js/validation.js    клиентская валидация
images/favicon.jpg  иконка вкладки
```

Главная страница читала данные из cookies, очищала таблицу и динамически создавала строки через JavaScript. У кнопок действий использовался `data-id`, чтобы JS понимал, с каким студентом работает пользователь.

Форма студента использовалась и для добавления, и для редактирования. При редактировании страница получала `id` из адресной строки через `URLSearchParams`, находила студента и подставляла данные в поля формы.

Страница досье также получала `id` из адреса, находила студента и выводила все поля в таблицу подробной информации.

### Модель студента в первой лабораторной

```js
const student = {
  id: Date.now(),
  fullName: fullName,
  group: group,
  ISU: Number(ISU),
  numberHouse: Number(numberHouse),
  numberRoom: Number(numberRoom),
  date: date,
  inostran: inostran,
  note: note
};
```

`id` создавался через `Date.now()`, чтобы отличать записи друг от друга при удалении, редактировании и открытии досье.

### Cookies и JSON

По варианту использовались cookies. Так как cookies хранят только строки, массив студентов сериализовался в JSON:

```js
const data = encodeURIComponent(JSON.stringify(students));
document.cookie = `students=${data}`;
```

При чтении выполнялось обратное действие:

```js
const decodedData = decodeURIComponent(cookiesData);
const students = JSON.parse(decodedData);
```

### CRUD на клиенте

- Добавление: форма собирала объект студента, добавляла его в массив и сохраняла массив в cookies.
- Просмотр: главная страница читала cookies и отрисовывала таблицу.
- Удаление: студент удалялся из массива через `filter()`.
- Редактирование: старый объект заменялся через `map()`.
- Досье: нужный студент находился по `id` и выводился на отдельной странице.

### Валидация в первой лабораторной

Часть проверок была сделана HTML-атрибутами:

```html
<input type="number" required min="100000" max="999999">
<input type="date" required>
```

Часть проверок была реализована через JavaScript:

- ФИО должно состоять из букв.
- Группа должна соответствовать формату.
- ИСУ должен быть числом.
- ИСУ не должен начинаться с нуля.
- Дата заселения не должна быть в будущем.
- ИСУ должен быть уникальным среди студентов.

## Лабораторная 2. Backend

Во второй лабораторной проект был перенесён на backend и стал работать через REST API.

### Цель второй лабораторной

Нужно было убрать хранение и основную бизнес-логику из браузера и перенести её на сервер. После этого frontend стал stateless: он только отображает данные и отправляет запросы, а состояние студентов хранится и обрабатывается на backend.

### Использованный стек

- Python.
- Django.
- Django REST Framework.
- HTML, CSS, JavaScript.
- JSON-файл как простое серверное хранилище.

### Архитектура backend

Backend реализован как Django-проект с приложением `students`.

Основное разделение по слоям:

- `views.py` принимает HTTP-запросы и возвращает HTTP-ответы.
- `urls.py` связывает URL-адреса с обработчиками.
- `serializers.py` проверяет входные данные.
- `services.py` содержит бизнес-логику.
- `repository.py` отвечает только за чтение и запись данных.
- `errors.py` описывает единый формат ошибок.

### REST API

| Метод | URL | Назначение |
| --- | --- | --- |
| `GET` | `/api/requests` | Получить список студентов |
| `GET` | `/api/requests/:ISU` | Получить одного студента по ИСУ |
| `POST` | `/api/requests` | Создать студента |
| `PATCH` | `/api/requests/:ISU` | Обновить студента |
| `DELETE` | `/api/requests/:ISU` | Удалить студента |
| `QUERY` | `/api/requests` | Получить список с фильтрацией |

### Модель данных backend

```json
{
  "ISU": 123456,
  "name": "Иванов Иван Иванович",
  "group": "M3301",
  "dormitory": 8,
  "room": 1201,
  "checkin_date": "2024-09-01",
  "is_foreign": false,
  "note": "Без замечаний"
}
```

`ISU` является уникальным идентификатором студента и используется в URL для получения, редактирования и удаления записи.

### JSON-хранилище

Вместо cookies используется файл:

```text
data/students_data.json
```

Repository читает данные из этого файла, изменяет список студентов и сохраняет его обратно. Для лабораторной это удобно, потому что не нужна отдельная база данных, а содержимое файла легко проверить вручную.

### Stateless frontend

После второй лабораторной браузер больше не хранит состояние студентов.

Теперь frontend работает так:

```text
страница открылась
JS делает fetch-запрос к API
сервер возвращает JSON
JS отрисовывает данные в DOM
```

### Фильтрация

Фильтрация реализована на сервере в `services.list_students()`.

Поддерживаются поля:

```text
ISU, name, group, dormitory, room, is_foreign
```

Пример:

```text
/api/requests?group=M3301&dormitory=8
```

Для большого количества фильтров используется метод `QUERY` с JSON-телом.

### Валидация и ошибки

Серверная валидация реализована в `students/serializers.py`.

Проверяется:

- ФИО.
- Формат группы.
- Диапазон ИСУ.
- Уникальность ИСУ.
- Номер общежития.
- Номер комнаты.
- Дата заселения.
- Типы данных.

Ошибки возвращаются в едином формате и с корректными HTTP-кодами: `400`, `404`, `409`, `422`, `500`.
