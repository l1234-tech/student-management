### 31. Derived State и reducer. Чем вычисляемые данные отличаются от хранимых?

Хранимый state содержит первичные данные, которые приложение должно помнить: список студентов, фильтр и выбранную запись. Derived State вычисляется из исходного state, например отфильтрованный список; его обычно не дублируют в хранилище, чтобы не получить две расходящиеся копии.

Reducer — чистая функция перехода состояния: `nextState = reducer(previousState, action)`. Она централизует правила изменения состояния и возвращает новый результат. Reducer не должен отправлять запросы или менять внешние объекты; эффекты выполняются отдельно.

```jsx
function reducer(state, action) {
  switch (action.type) {
    case 'added': return [...state, action.student];
    case 'removed': return state.filter(s => s.id !== action.id);
    default: return state;
  }
}
```

`useReducer` полезен, когда несколько событий меняют связанные поля и переходы проще описать действиями. **Опора на лекцию:** лекция 9, реактивность и вычисляемые значения. **Дополнение:** reducer и `useReducer` раскрыты по [официальной документации React](https://react.dev/reference/react/useReducer).

### 32. Синхронная и асинхронная валидация формы в SPA

Синхронная проверка не ждёт внешнего ответа: обязательность, длина, формат, диапазон, совпадение полей. Асинхронная проверка обращается к серверу или внешнему источнику: например, доступен ли email или существует ли код группы. Синхронную проверку можно показать при вводе или blur; асинхронную следует ограничивать debounce и отменять/игнорировать устаревшие ответы.

Ошибку необходимо привязать к полю, сообщить её доступным образом и не полагаться только на цвет. Кнопку отправки можно блокировать при явно некорректных данных, но сервер должен повторно валидировать всё критичное: клиент легко обойти. Состояние асинхронной проверки должно различать `idle`, `checking`, `valid` и `error`.

**Опора на лекцию:** формы и проверка данных в клиентском приложении. **Дополнение:** конкретные правила предметной области определяет API.

### 33. RxJS: Observable и Observer. Отличие потока событий от Promise

Observable описывает поток уведомлений, а Observer задаёт обработчики `next`, `error` и `complete`. Поток может выдать ноль, одно или много значений во времени. Подписка запускает или подключает обработку; `unsubscribe()` позволяет прекратить участие и освободить ресурс.

Promise представляет один будущий результат: он завершается одним значением или ошибкой. У Promise нет встроенного метода отмены, тогда как Observable по контракту подписки можно отписать; реально ли это остановит сетевую операцию — зависит от источника и адаптера. Observable поддерживает операторы преобразования и комбинирования последовательностей, поэтому подходит для событий ввода и длительных потоков.

```ts
const observer = {
  next: value => console.log(value),
  error: error => console.error(error),
  complete: () => console.log('готово')
};
const subscription = stream$.subscribe(observer);
subscription.unsubscribe();
```

**Опора на лекцию:** RxJS. **Дополнение:** [RxJS Subscription](https://rxjs.dev/guide/subscription) и API Observables.

### 34. Hash Routing и History API. Отличия и требования к серверу

Hash routing хранит маршрут после `#`, например `/#/students/42`. Фрагмент не отправляется серверу как часть HTTP-пути, поэтому простая статическая раздача часто работает без настройки серверных маршрутов. URL выглядит менее чисто, а часть браузерных функций фрагмента уже занята.

History API позволяет использовать обычный путь `/students/42`; router меняет историю через `pushState`/`replaceState` и обрабатывает `popstate`. Но при прямом запросе такого URL сервер должен вернуть SPA shell (или обработать маршрут на сервере). Без fallback перезагрузка страницы может дать 404. Оба варианта требуют, чтобы router корректно восстанавливал состояние при Back/Forward.

**Опора на лекцию:** навигация SPA и маршрутизация. **Дополнение:** [MDN History API](https://developer.mozilla.org/en-US/docs/Web/API/History_API) и [hash routing](https://developer.mozilla.org/en-US/docs/Glossary/Hash_routing).

### 35. JWT на frontend: access/refresh, обновление и обработка 401

Access token предъявляется при запросе к API и обычно имеет ограниченный срок действия. Refresh token используется для получения новой пары/нового access token и должен храниться и передаваться с более строгими мерами. После 401 клиент может один раз запросить обновление, затем повторить исходный запрос; если обновление не удалось — завершить сессию и направить пользователя на вход. Нельзя бесконечно повторять запросы или запускать параллельное обновление для каждого запроса отдельно.

JWT — формат токена, а не гарантия полномочий: сервер проверяет подпись, срок, issuer/audience и права. Клиент может скрыть недоступный экран, но не может сам разрешить защищённое действие. Способ хранения влияет на риски: `localStorage` доступен JavaScript и уязвим при XSS; `HttpOnly`, `Secure`, `SameSite` cookie снижает доступность токена для скрипта, но требует учитывать CSRF и настройки cookie.

**Опора на лекцию:** SPA и аутентификация в клиентском приложении. **Дополнение:** точные правила задают backend и политика безопасности проекта.

### 36. Protected Routes. Чем клиентская защита маршрута отличается от проверки прав backend?

Protected route — клиентская проверка перед показом страницы: есть ли сессия и подходит ли роль пользователя. Она улучшает навигацию и UX: неавторизованного пользователя можно отправить на `/login`, а пользователя без роли — показать экран 403.

Это не граница безопасности. Клиентский код можно изменить, а API вызвать напрямую. Поэтому backend обязан проверять аутентификацию и полномочия при каждом защищённом запросе, включая конкретный объект и действие. UI guard только помогает не показывать заведомо недоступный интерфейс и не заменяет серверную авторизацию.

**Опора на лекцию:** маршруты SPA и роли. **Дополнение:** правило авторизации должно быть реализовано на сервере независимо от состояния интерфейса.

### 37. State management: единый источник истины, иммутабельность и предсказуемость

Единый источник истины означает, что каждое значение имеет одного владельца. Это не значит, что всё состояние лежит в одном глобальном объекте: состояние формы может быть локальным, а сессия — в store. Не следует хранить дубликаты, которые можно вычислить.

Иммутабельное обновление создаёт новое значение вместо незаметной мутации старой структуры. Это помогает обнаруживать изменения, сохранять снимки и прогнозировать переходы. Предсказуемость обеспечивают явные actions и чистые reducer/операции, а побочные эффекты (запросы, таймеры) выполняются отдельно. Неизменяемость — соглашение модели и инструмента; глубокое копирование каждого объекта вручную не всегда необходимо.

**Опора на лекцию:** state management, Derived State и reducer. **Дополнение:** модель действий см. в [React managing state](https://react.dev/learn/managing-state).

### 38. SPA и MPA. Как устроено одностраничное приложение и чем отличается?

SPA загружает приложение и затем меняет содержимое, маршруты и данные внутри текущего документа; переходы обычно выполняются клиентским router. MPA состоит из отдельных страниц-документов, которые сервер отдаёт при переходах. SPA может давать быстрые переходы после первоначальной загрузки и сохранять клиентское состояние, но требует JavaScript, настройки маршрутизации, обработки загрузки данных и внимания к первому экрану.

MPA часто проще для страниц, где навигация и серверная генерация являются естественной моделью; браузер получает новый документ при переходе. Это не взаимоисключающие категории: SSR/метафреймворки могут формировать HTML на сервере и затем гидратировать интерактивное приложение. Выбор зависит от требований к SEO, первому отображению, взаимодействиям, архитектуре и инфраструктуре.

**Опора на лекцию:** лекция 8, AJAX и SPA; лекция 10, CSR/SSR. **Дополнение:** метрики первого отображения раскрыты в лекции 10.

### 39. Слои архитектуры SPA: Router, Pages, Features, Domain Model, API Client и Shared

Это один из способов группировки кода по роли. **Router** связывает URL с экраном. **Pages** собирают страницу из возможностей. **Features** реализуют пользовательские сценарии, например поиск или редактирование студента. **Domain Model** описывает предметные данные и правила. **API Client** инкапсулирует HTTP и преобразование ответов. **Shared** хранит действительно общие элементы: базовые UI-компоненты, утилиты и типы.

Например, страница студентов получает данные из `students` feature; feature вызывает доменную операцию или API-клиент; отображает `StudentList` из общих UI-блоков. Такой разрез помогает направить зависимости к стабильным контрактам и не дублировать HTTP-код по компонентам. Названия и число слоёв не являются обязательным стандартом: не нужно создавать пустые папки, если проект мал.

**Опора на лекцию:** архитектура SPA и компонентное разбиение. **Дополнение:** схема слоёв — практический вариант организации, а не единственно возможная структура.

### 40. Hot и Cold Observable. Почему подписчики могут получать разные значения?

Cold Observable обычно начинает отдельное выполнение для каждой подписки. Например, два подписчика на `from([1, 2, 3])` каждый получают полный набор; два подписчика на Observable HTTP-запроса часто запускают два запроса, если источник не разделён.

Hot Observable связан с уже работающим источником событий, например DOM-событием или Subject. Подписчик получает значения с момента своей подписки и может пропустить более ранние события. Для позднего подписчика можно использовать replay-поведение, если нужно выдать последнее или часть прошлых значений. Термины описывают модель совместного выполнения/вещания, но детали зависят от способа создания и операторов multicast.

**Опора на лекцию:** RxJS и жизненный цикл подписки. **Дополнение:** термины сверены с [RxJS Glossary and Semantics](https://rxjs.dev/guide/glossary-and-semantics) и [Subject](https://rxjs.dev/guide/subject).
