## 1. Node.js как среда выполнения JavaScript. Назначение V8 и libuv, отличия от выполнения JavaScript в браузере.

Node.js — среда выполнения JavaScript вне браузера. V8 компилирует и исполняет JavaScript, управляет JavaScript-кучей и сборкой мусора. libuv предоставляет цикл событий, неблокирующий ввод-вывод и рабочий пул для ряда операций. Поверх них Node.js добавляет API и модули вроде node:http, node:fs и node:stream.

В браузере среда предоставляет DOM, window, document и Web APIs. В Node.js DOM нет; зато есть API файлов, сетевых соединений, процессов и окружения. Язык общий, но доступные объекты и среда различаются.

Связь компонентов: JavaScript выполняется в V8; асинхронные операции передаются системному API и/или libuv; когда операция готова, callback ставится в очередь и вызывается Event Loop.

**Ответ на защите:** «V8 исполняет JavaScript, а libuv помогает Node.js выполнять асинхронный ввод-вывод и организует Event Loop. Node.js не является браузером: DOM в нём нет, зато доступны серверные API».

**Опора на лекцию:** лекция №11, разделы о V8, Node Core, libuv и обработке событий.

## 2. Event Loop в Node.js. Очереди задач и микрозадач, влияние длительных обработчиков на работу сервиса.

Event Loop позволяет основному JavaScript-потоку обслуживать множество готовых событий ввода-вывода. Упрощённо цикл проходит фазы таймеров, системных событий, ожидания I/O, setImmediate и закрытия handles. Promise callbacks относятся к очереди микрозадач; process.nextTick имеет собственную очередь Node.js. Микрозадачи не являются отдельной фазой libuv.

После текущего синхронного стека Node обрабатывает микрозадачи, затем продолжает цикл. Таймер setTimeout(fn, 100) задаёт минимальную задержку, а не точное время запуска. В некоторых контекстах порядок setTimeout(0) и setImmediate не гарантирован.

~~~js
console.log("sync");
Promise.resolve().then(() => console.log("promise"));
setTimeout(() => console.log("timer"), 0);
setImmediate(() => console.log("immediate"));
~~~

console.log исполняется синхронно, Promise callback — микрозадача, timer и immediate обрабатываются Event Loop. Долгий callback задерживает остальные callbacks и ответы другим соединениям на этом процессе.

**Опора на лекцию:** лекция №11, фазы Event Loop, микрозадачи, poll callback и starvation.

## 3. Блокирующий и неблокирующий ввод-вывод. Почему async/await не делает вычислительный цикл неблокирующим?

Блокирующий вызов не возвращает управление, пока операция не завершится. Например, синхронное чтение файла задерживает дальнейшее выполнение потока. Неблокирующий API запускает операцию и позволяет Node продолжать работу; результат поступает через callback, Promise или событие.

async/await упрощает асинхронный код, но не превращает синхронные вычисления в неблокирующие. На await функция приостанавливается только в ожидании Promise. CPU-цикл до или после await занимает Event Loop.

~~~js
async function handleRequest() {
  const data = await readFile("students.json", "utf8"); // ожидание I/O
  let total = 0;
  for (let i = 0; i < 1000000000; i++) total += i; // синхронный CPU-цикл
  return data.length + total;
}
~~~

data — прочитанная строка, total — сумма, накапливаемая в цикле. Большой цикл блокирует главный JS-поток. Для CPU-тяжёлой работы задачу делят на короткие порции или переносят в worker/отдельный процесс.

**Опора на лекцию:** лекция №11, примеры с асинхронным fs, синхронным API и тезис «async/await не разблокирует CPU-код».

## 4. Потоки Node.js. Readable, Writable, Transform, pipeline и обработка ошибок при передаче данных.

Поток обрабатывает данные частями, поэтому весь файл не требуется держать в памяти. Readable производит данные, например чтение файла; Writable принимает их, например файл назначения; Transform читает и преобразует данные; pipeline соединяет потоки, координирует передачу данных, завершение и ошибки.

~~~js
import { createReadStream, createWriteStream } from "node:fs";
import { pipeline } from "node:stream/promises";

await pipeline(
  createReadStream("students.csv"),
  createWriteStream("students-copy.csv")
);
~~~

createReadStream создаёт источник, createWriteStream — назначение, pipeline возвращает Promise, который завершается после успеха или отклоняется при ошибке. Ошибку нужно перехватить и перевести в контролируемое состояние задания/ответа; нельзя оставлять необработанный отказ Promise.

**Дополнение к лекции:** типы потоков и pipeline описаны в [официальной документации Node.js](https://nodejs.org/api/stream.html).

## 5. Backpressure. Причины появления, контроль скорости обработки и ограничение потребления памяти.

Backpressure появляется, когда источник выдаёт данные быстрее, чем следующий этап способен принять их. Без ограничения буфер растёт и может исчерпать память. Потоки передают сигнал замедления обратно производителю. Если writable.write(chunk) возвращает false, производитель должен дождаться drain.

~~~js
import { once } from "node:events";

for await (const chunk of source) {
  if (!destination.write(chunk)) await once(destination, "drain");
}
destination.end();
~~~

chunk — очередная порция; write сообщает, можно ли продолжать; drain означает, что буфер назначения освободил место. В прикладном коде также обрабатывают ошибки, отмену и закрытие соединения. Обычно pipeline безопаснее ручной организации цепочки.

**Дополнение:** [Backpressuring in Streams, Node.js Learn](https://nodejs.org/learn/modules/backpressuring-in-streams).

## 6. worker_threads. Назначение, обмен сообщениями и выбор между потоковой обработкой и отдельным рабочим потоком.

worker_threads запускает JavaScript в дополнительном потоке того же процесса и полезен для CPU-интенсивной работы. Потоки данных нужны для последовательной обработки больших объёмов с контролем памяти; Worker нужен для параллельного вычисления. Запуск Worker и передача данных тоже имеют стоимость, поэтому короткие мелкие операции часто невыгодно выносить отдельно. Для множества задач можно держать пул Workers.

Данные передаются через postMessage. Обычно они копируются по structured clone; некоторые буферы можно передавать без копирования как transferable.

~~~js
// main.js
import { Worker } from "node:worker_threads";
const worker = new Worker(new URL("./sum-worker.js", import.meta.url));
worker.postMessage([1, 2, 3]);
worker.on("message", result => console.log(result));
worker.on("error", error => console.error(error));
worker.on("exit", code => console.log("worker exit", code));
~~~

worker — экземпляр рабочего потока; postMessage отправляет массив; message получает ответ; error сообщает об ошибке; exit сообщает, что поток завершился. Рабочий файл принимает сообщение и отправляет результат обратно. Основной поток должен обработать все эти исходы.

**Опора на лекцию:** №11, Thread Pool и Worker Threads, обмен сообщениями, Structured Clone и transferable. **Дополнение:** [документация Node.js](https://nodejs.org/api/worker_threads.html).

## 7. WebSocket. Установка соединения через HTTP Upgrade, двунаправленный обмен и отличие от HTTP polling и Server-Sent Events.

WebSocket устанавливает длительное двунаправленное соединение. После handshake обе стороны могут отправлять сообщения независимо друг от друга. HTTP polling требует периодически посылать запросы; Server-Sent Events (SSE) передаёт поток от сервера клиенту, а для команды клиент обычно использует HTTP-запрос.

При handshake клиент отправляет HTTP-запрос с Upgrade: websocket и Connection: Upgrade. Сервер подтверждает переход статусом 101 Switching Protocols; затем стороны обмениваются WebSocket-кадрами.

~~~~text
Клиент: GET /ws + Upgrade: websocket
Сервер: 101 Switching Protocols
Далее: сообщения в обе стороны по одному соединению
~~~~

WebSocket подходит для уведомлений и событий реального времени. Для обычного CRUD проще HTTP; постоянные соединения требуют контроля авторизации, отключений, тайм-аутов и нагрузки.

**Дополнение:** рукопожатие и протокол описаны в [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html).

## 8. WebRTC. Установка соединения и роль сигналинга, SDP и ICE. Назначение STUN и TURN. Передача данных через RTCDataChannel, режимы надёжности и порядка доставки, отличия от WebSocket.

WebRTC позволяет установить интерактивное соединение между браузерами/узлами для аудио, видео и данных. Приложению нужен отдельный сигналинговый канал, например HTTP или WebSocket, чтобы участники обменялись описаниями и сетевыми кандидатами.

SDP описывает параметры медиа и каналов. ICE собирает и проверяет возможные сетевые пути. STUN помогает определить внешний адрес/порт за NAT. TURN ретранслирует трафик, когда прямое соединение установить нельзя. RTCDataChannel передаёт прикладные данные между peers. Его параметры позволяют выбирать надёжность и порядок доставки: чат обычно требует упорядоченной надёжной доставки, а некоторые временные телеметрические данные могут допускать потери.

WebSocket — клиент-серверный канал через сервер приложения; WebRTC стремится организовать обмен между peers, хотя сигналинг и TURN могут потребовать серверной инфраструктуры.

**Дополнение:** [W3C WebRTC](https://www.w3.org/TR/webrtc/), [STUN, RFC 8489](https://www.rfc-editor.org/rfc/rfc8489.html), [TURN, RFC 8656](https://www.rfc-editor.org/rfc/rfc8656.html).

## 9. Жизненный цикл WebSocket-соединения. Ping/Pong, тайм-ауты, закрытие и повторное подключение.

Клиент начинает handshake; сервер проверяет запрос и учётные данные; после открытия идёт обмен сообщениями; затем соединение закрывают штатно либо оно теряется из-за сети/процесса.

Ping/Pong — управляющие кадры для проверки доступности. Серверная библиотека может отправлять ping и закрывать соединение, если pong не пришёл вовремя. Браузерный JavaScript API напрямую не предоставляет отправку протокольного ping; для приложения можно определить собственное heartbeat-сообщение.

Reconnect должен иметь ограниченную частоту, например экспоненциальную задержку с небольшим случайным разбросом. Повторы прекращают после выхода пользователя, истечения авторизации или достижения лимита. При reconnect нужно восстановить подписки и не выполнить команду дважды. Параметры тайм-аутов зависят от инфраструктуры и требований приложения.

## 10. Прикладной протокол поверх WebSocket. Типы сообщений, корреляция запросов и ответов, идентификаторы событий и обработка ошибок.

WebSocket задаёт транспорт, но не формат предметных сообщений. Приложение определяет общую структуру: тип, ID, данные и версию. requestId связывает ответ с запросом; eventId идентифицирует независимое событие.

~~~json
{ "type": "command", "requestId": "r-17", "name": "student.update", "payload": { "isuId": 42 } }
{ "type": "result", "requestId": "r-17", "ok": true, "payload": { "updated": true } }
{ "type": "event", "eventId": "e-501", "name": "student.updated", "payload": { "isuId": 42 } }
{ "type": "error", "requestId": "r-17", "code": "FORBIDDEN", "message": "Недостаточно прав" }
~~~

Сервер валидирует размер и структуру каждого сообщения, а не доверяет входящему JSON. Ошибка должна иметь стабильный машинный code и безопасное сообщение; stack trace клиенту не отправляют. Версия контракта помогает менять формат совместимо.

## 11. Безопасность WebSocket. Аутентификация, проверка Origin, авторизация команд и разграничение клиентских и служебных подключений.

Установленное соединение не означает, что пользователь авторизован. Сервер проверяет аутентификацию при handshake, а право на чувствительную операцию — при каждой команде. Проверка Origin снижает риск использования браузерной сессии чужим сайтом, но не заменяет аутентификацию.

Нельзя доверять роли или actor ID, присланным в сообщении. Сервер получает пользователя из проверенной сессии/токена и сам проверяет его права. Ограничивают размер и частоту сообщений, используют WSS при передаче по сети, закрывают неактивные соединения и не раскрывают внутренние ошибки.

Служебные соединения между сервисами должны иметь отдельные полномочия и быть недоступными обычным пользователям. Получатель события проверяет доверенный источник.

## 12. Журнал аудита. Отличие от технического лога, состав записи, доверенный источник событий и связь события с успешным изменением данных.

Технический лог нужен для диагностики: запуск, исключения, задержки. Аудит фиксирует значимые действия над бизнес-данными: кто изменил объект, что сделал, когда и с каким результатом. Запись может содержать eventId, время UTC, проверенного пользователя/сервис, действие, тип и ID объекта, результат, request/correlation ID. Пароли, токены и лишние персональные данные не записывают.

actorId берётся сервером из проверенной авторизации, а не из сообщения клиента. Событие student.updated публикуют только после подтверждённого успешного изменения. Иначе подписчик может получить событие об операции, которая завершилась ошибкой или откатилась. Расхождение между сохранением данных и отправкой события решают повторной доставкой или transactional outbox, когда это требуется архитектурой.

## 13. Доставка событий между сервисами. Потеря связи, повторная отправка, подтверждения и идемпотентная обработка.

Сеть может задержать сообщение, оборвать соединение или привести к повторной обработке. Поэтому «ровно одна доставка» не гарантируется автоматически. Практичный подход — повторная доставка с eventId и идемпотентный обработчик.

Отправитель повторяет сообщение, если не получил подтверждение. Получатель хранит уже обработанные eventId и не применяет повтор второй раз. Для порядка используют sequence/version объекта. После восстановления соединения клиент может получить пропущенные события или заново загрузить актуальное состояние через GET API.

В простой лабораторной достаточно определить контракт, обработать reconnect и показать дедупликацию на учебном уровне. Очередь и outbox — варианты для систем, где потеря события недопустима.

## 14. CSV как формат обмена. Кодировка, заголовки, экранирование кавычек и разделителей, многострочные поля и проверка данных.

CSV — текстовый формат табличных данных. Его нельзя надёжно разбирать простым split по запятой или переводу строки: значение может содержать разделитель, кавычки и перенос строки. В заключённом в кавычки поле кавычка обычно удваивается. Разделитель и кодировку (часто UTF-8) нужно согласовать.

Импортёр проверяет ожидаемые заголовки, число столбцов, типы, обязательность и бизнес-ограничения. Ошибку связывают с номером строки и полем. Экспортёр экранирует значения и не включает секреты. Большие файлы обрабатывают потоковым парсером, что ограничивает память и позволяет считать прогресс. Полезен предварительный отчёт о некорректных строках до подтверждения импорта.

## 15. Фоновые задания импорта и экспорта. Состояния, прогресс, частичные ошибки, дубликаты и передача больших файлов порциями.

Долгую обработку не обязательно выполнять в открытом HTTP-запросе. Сервер валидирует запрос, создаёт jobId и возвращает его; worker выполняет импорт/экспорт, клиент проверяет статус либо получает WebSocket-уведомления.

Типовые состояния: queued, running, completed, failed, cancelled. Прогресс хранит обработанное/успешное/ошибочное число строк, время начала и краткую безопасную ошибку. Для дубликатов заранее задают правило: отклонить файл, пропустить, обновить по ключу либо вернуть построчную ошибку.

Частичный результат сопровождают отчётом, чтобы оператор видел применённые изменения. Большие файлы передают и обрабатывают ограниченными порциями с backpressure и лимитами. Повтор задания должен быть идемпотентным или явно подтверждённым, иначе возможны дубликаты.

## 16. nginx как reverse proxy. Маршрутизация HTTP и WebSocket, заголовки Upgrade и Connection, тайм-ауты и адресация сервисов в Docker Compose.

Reverse proxy принимает внешний запрос и перенаправляет его внутреннему сервису. nginx может направлять обычный HTTP в Java API, а путь /ws/ — в Node.js. В Docker Compose сервисы обращаются друг к другу по имени сервиса и внутреннему порту. localhost внутри контейнера указывает на тот же контейнер.

Для WebSocket nginx передаёт Upgrade и Connection и использует подходящие тайм-ауты для долгих соединений.

~~~nginx
location /ws/ {
    proxy_pass http://realtime:3000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;
}
~~~

location выбирает путь; proxy_pass задаёт внутренний сервис realtime и порт 3000; proxy_http_version задаёт HTTP/1.1 для upstream; proxy_set_header передаёт заголовки Upgrade; proxy_read_timeout задаёт время ожидания данных от upstream. Значения тайм-аутов подбирают под требования сервиса.

**Дополнение:** [nginx: WebSocket proxying](https://nginx.org/en/docs/http/websocket.html), [proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html).
