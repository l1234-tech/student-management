## 1. Метафреймворки: Next.js, Nuxt, SvelteKit, AnalogJS. Назначение и отличия от обычных frontend-фреймворков

### Что такое метафреймворк?

Метафреймворк — это надстройка над frontend-фреймворком или библиотекой, которая предоставляет готовую инфраструктуру для создания полноценного веб-приложения.

Обычный UI-фреймворк отвечает преимущественно за построение интерфейса: компоненты, состояние, реактивность, обновление DOM и обработку пользовательских событий.

Однако для полноценного приложения этого недостаточно. Дополнительно нужны:
- маршрутизация;
- организация структуры проекта;
- серверный и клиентский рендеринг;
- загрузка данных;
- обработка ошибок;
- кеширование;
- предварительная загрузка ресурсов;
- работа с серверной частью;
- сборка и развёртывание приложения.
Эти возможности обычно приходится подключать и настраивать отдельно. Метафреймворк объединяет их в единую систему и задаёт общие соглашения о том, как организовать приложение.

В лекции №10 на странице 26 показана важная схема: метафреймворк расширяет UI-фреймворк, а не заменяет его. На странице 27 приведены пять основных механизмов метафреймворка:
1. Routing — маршрутизация.
2. Rendering — рендеринг.
3. Data Loading — загрузка данных.
4. Cache — кеширование.
5. Hydration — гидратация.
### Сравнение четырёх метафреймворков

Next.js

Метафреймворк на основе React. Предоставляет файловую маршрутизацию, SSR, SSG, ISR, серверные возможности, загрузку данных и API-маршруты. В App Router используются Server Components и Client Components.

Основа: React. Официальная документация: Next.js Docs.

Nuxt

Метафреймворк на основе Vue. Предоставляет файловую маршрутизацию, SSR, предварительную генерацию страниц, route rules, middleware, useFetch, useAsyncData, серверные API-маршруты через Nitro.

Основа: Vue. Официальная документация: Nuxt Docs.

SvelteKit

Метафреймворк на основе Svelte. Предоставляет файловую маршрутизацию, серверные и клиентские функции загрузки данных, SSR, prerendering, серверные обработчики и формы.

Основа: Svelte. Официальная документация: SvelteKit Docs.

AnalogJS

Метафреймворк на основе Angular. Предоставляет файловую маршрутизацию, SSR, SSG, серверные API-маршруты и загрузку данных. Использует инструменты экосистемы Angular и сборку на Vite.

Основа: Angular. Официальная документация: AnalogJS Docs.

В лекции №10 на странице 28 они объединены в одну категорию задач: React → Next.js, Vue → Nuxt, Svelte → SvelteKit, Angular → AnalogJS. Общие концепции похожи, но детали реализации и соглашения различаются. Лекция№10(2).pdf

### Чем метафреймворк отличается от обычного frontend-фреймворка?

| Возможность | Обычный frontend-фреймворк | Метафреймворк |
| --- | --- | --- |
| Компоненты | Да | Использует компоненты базового фреймворка |
| Управление состоянием | Да или через библиотеки | Использует механизмы базового фреймворка |
| Маршрутизация | Часто подключается отдельно | Обычно встроена |
| SSR | Может требовать отдельной настройки | Обычно предусмотрен |
| SSG / ISR | Обычно не являются базовой возможностью | Поддерживаются в разных формах |
| Загрузка данных | Через API и дополнительные средства | Есть специальные серверные и клиентские механизмы |
| Middleware | Нужно организовывать отдельно или через Router | Обычно предусмотрено |
| Кеширование | Организуется самостоятельно | Есть интеграция с кешем и revalidation |

### Как это выглядит в нашей лабораторной?

В лабораторной №5 мы выбрали Nuxt, поскольку предыдущий frontend был построен на Vue.

### В результате структура приложения выглядит примерно так

```text
5 lab/
├── app/
│   ├── pages/
│   │   ├── login.vue
│   │   ├── profile.vue
│   │   └── students/
│   │       ├── index.vue
│   │       └── [id]/
│   │           ├── index.vue
│   │           └── edit.vue
│   │
│   ├── components/
│   ├── composables/
│   ├── middleware/
│   └── layouts/
│
├── server/
│   ├── api/
│   │   └── backend/
│   └── utils/
│
└── nuxt.config.ts
```

Nuxt автоматически определяет страницы по структуре app/pages, предоставляет SSR, middleware и серверные обработчики.

### Например, страница

```text
app/pages/students/[id]/index.vue
```

### соответствует адресу

/students/42

### а серверный файл

```text
server/api/backend/[...path].ts
```

обеспечивает проксирование запросов frontend к Java API.

При этом метафреймворк не заменяет Java backend. Он отвечает за серверную инфраструктуру frontend-приложения.
### Что важно не перепутать?

Метафреймворк не обязательно означает, что всё приложение становится backend-приложением. Он может иметь серверную среду выполнения, но это не требует переносить бизнес-логику и базу данных из отдельного backend.

Именно так устроена наша лабораторная: Nuxt выполняет SSR и транспортную работу, Java остаётся источником бизнес-правил, проверки JWT, ролей и операций с PostgreSQL.

Кратко для защиты: метафреймворк расширяет возможности обычного frontend-фреймворка, предоставляя маршрутизацию, серверный рендеринг, загрузку данных, кеширование, middleware и сборку. Next.js основан на React, Nuxt — на Vue, SvelteKit — на Svelte, AnalogJS — на Angular. В нашей лабораторной Nuxt используется для серверных возможностей frontend, а бизнес-логика остаётся в Java.

## 2. Ограничения SPA. Клиентский и серверный рендеринг: CSR и SSR

### Что такое SPA?

SPA (Single Page Application) — архитектура веб-приложения, при которой происходит загрузка и обновление одного HTML-документа, а дальнейшие изменения интерфейса выполняются динамически средствами JavaScript.

В лекции №8 SPA описывается как приложение, в котором отправка форм, переходы и подгрузка данных происходят динамически через AJAX. Лекция№8(2).pdf

В отличие от традиционного подхода MPA, где при переходе обычно загружается новый HTML-документ, SPA сохраняет общую оболочку приложения.

### Например, в системе управления студентами пользователь может переходить

```text
/students
```

/students/123456
```text
/profile
/admin
```

При клиентской навигации браузер не обязан загружать новый HTML-документ. Меняется отображаемый компонент и при необходимости загружаются данные.
### Как работает SPA при CSR?

CSR (Client-Side Rendering) — стратегия, при которой HTML пользовательского интерфейса формируется в браузере.

### Последовательность

1. Пользователь открывает URL.
2. Сервер отправляет HTML-оболочку приложения.
3. Браузер загружает CSS и JavaScript.
4. JavaScript запускается.
5. Приложение обращается к API за данными.
6. Получает JSON.
7. Строит интерфейс и отображает его в DOM.
8. Подключает обработчики событий, после чего интерфейс становится интерактивным.
Браузер

Запрос страницы

Сервер

Отдаёт HTML-оболочку и JS

JavaScript в браузере

Запрос данных к API

API

Возвращает JSON

DOM и пользовательский интерфейс

Браузер строит и показывает страницу

В лекции №10 на страницах 5, 9–11 подробно показан этот путь: HTML-оболочка → загрузка JS → запрос API → JSON → построение UI. Лекция№10(2).pdf

#### Преимущества CSR

- серверу не нужно формировать полный HTML для каждого запроса;
- после первоначальной загрузки переходы обычно происходят быстро;
- удобно строить интерактивные интерфейсы;
- frontend и backend можно развивать относительно независимо;
- большую часть вычислений по отображению выполняет браузер.
#### Недостатки CSR

- первый экран может появляться позже, поскольку сначала нужно загрузить JavaScript;
- поисковые роботы и простые клиенты могут получить HTML-оболочку без основного содержимого;
- слабое устройство пользователя может медленно выполнять тяжёлый JavaScript;
- начальная загрузка большого приложения может быть дорогой;
- данные для первого экрана часто загружаются только после запуска JS, добавляя ожидание API.
Важно: современные поисковые системы могут выполнять JavaScript, поэтому утверждение «CSR вообще не индексируется» неверно. Но SSR/SSG позволяют сразу отдать содержимое в HTML и упрощают индексацию.
### Как работает SSR?

SSR (Server-Side Rendering) — стратегия, при которой HTML пользовательского интерфейса формируется на сервере по запросу.

### Последовательность

1. Браузер отправляет запрос на сервер.
2. Серверный Router определяет нужную страницу.
3. Сервер загружает необходимые данные.
4. Компоненты выполняются на сервере и формируют HTML.
5. Сервер отправляет готовый HTML браузеру.
6. Браузер показывает содержимое.
7. Загружается JavaScript.
8. Выполняется Hydration, подключаются обработчики событий и состояние.
Браузер → SSR-сервер

```text
GET /students/42
```

Router и загрузка данных

Запрос к backend API

SSR-рендерер

Формирует HTML с данными

Браузер

Показывает HTML, затем Hydration делает его интерактивным

В лекции №10 на странице 12 показано: браузер → SSR-сервер → источник данных → генерация HTML → HTML-ответ → показ содержимого → Hydration. Лекция№10(2).pdf

#### Преимущества SSR

- содержимое страницы доступно в первоначальном HTML;
- часто улучшается FCP и LCP;
- поисковому роботу проще получить текст и структуру страницы;
- можно получить данные до отображения первого экрана;
- сервер может безопасно работать с секретами и приватными API.
#### Недостатки SSR

- сервер выполняет рендеринг при запросах, что увеличивает его нагрузку;
- первый байт может прийти поздно, если сервер долго получает данные;
- нужно контролировать кеширование;
- необходима корректная работа с окружениями server/browser;
- после получения HTML всё равно требуется JS и Hydration для интерактивности.
В лекции №10 на странице 15 подчёркивается, что SSR не ускоряет базу данных: медленный источник данных задерживает генерацию HTML. Лекция№10(2).pdf

### Главное отличие CSR от SSR

| Критерий | CSR | SSR |
| --- | --- | --- |
| Где формируется основной HTML интерфейса | В браузере | На сервере |
| Что приходит первым | HTML-оболочка и JS | Готовый HTML с содержимым |
| Получение данных | Обычно из браузера после JS | Может происходить на сервере до отправки HTML |
| Первый видимый контент | Может задерживаться до JS и API | Может появиться раньше |
| Интерактивность | После выполнения JS | После Hydration |
| Серверная нагрузка | Обычно ниже на рендеринг | Выше из-за генерации HTML |
| SEO | Требует внимания к выполнению JS | Часто проще обеспечить |

### Важный нюанс: SSR не отменяет CSR

SSR и CSR могут использоваться вместе. Например, при первом открытии Nuxt формирует HTML на сервере, а после Hydration Vue управляет интерактивностью и клиентскими переходами.

То есть сервер отвечает за первоначальную генерацию HTML, а браузер — за дальнейшую интерактивность приложения.
### Пример в нашей лабораторной

В nuxt.config.ts указано:
```text
export default defineNuxtConfig({
    ssr: true
});
```

Это включает SSR.

Страница списка студентов использует useStudentList, который внутри построен на useAsyncData. Поэтому данные загружаются во время серверного рендеринга и включаются в payload Nuxt для передачи браузеру.

### Упрощённо

```vue
<script setup lang="ts">
const filters = computed(() => ({
    page: 0,
    size: 10
}));

const { data, pending, error } =
    await useStudentList(filters);
```

</script>

```vue
<template>
    <p v-if="pending">Загрузка...</p>
    <p v-else-if="error">Ошибка загрузки</p>

    <ul v-else>
        <li
            v-for="student in data?.data ?? []"
            :key="student.ISU"
        >
            {{ student.name }}
        </li>
    </ul>
</template>
```

Изначально сервер получает данные студентов, формирует HTML со списком и отдаёт его браузеру. После Hydration Vue подключает интерактивность.

Кратко для защиты: CSR формирует интерфейс в браузере после загрузки JavaScript и получения данных. SSR формирует HTML на сервере и отправляет браузеру уже готовое содержимое. SSR улучшает доступность первого содержимого и может помочь SEO, но увеличивает нагрузку на сервер и не отменяет клиентский JavaScript.

## 3. Стратегии рендеринга: CSR, SSR, SSG, ISR. Преимущества, недостатки и сценарии применения

Рендеринг — процесс формирования HTML-представления пользовательского интерфейса.

В метафреймворках есть несколько основных стратегий, различающихся тем, когда и где именно создаётся HTML.

В лекции №10 на страницах 8–21 последовательно рассмотрены CSR, SSR, SSG и ISR, а на странице 20 дана сравнительная таблица. Лекция№10(2).pdf

1. CSR — Client-Side Rendering
HTML интерфейса формируется непосредственно в браузере.

### Когда создаётся страница

- сервер отправляет HTML-оболочку;
- браузер загружает JavaScript;
- приложение получает необходимые данные;
- JavaScript формирует интерфейс.
### Пример

```ts
async function loadStudents() {
    const response = await fetch("/api/students");

    if (!response.ok) {
        throw new Error("Ошибка загрузки");
    }

    const students = await response.json();

    renderStudents(students);
}
```

#### Преимущества

- серверу не нужно рендерить HTML на каждый запрос;
- удобно реализовывать сложные интерактивные приложения;
- можно использовать клиентское кеширование;
- проще разделять frontend и backend.
#### Недостатки

- первоначальный интерфейс может появиться поздно;
- много JavaScript влияет на скорость загрузки и работу слабых устройств;
- данные появляются после выполнения клиентского кода;
- SEO требует дополнительного внимания.
#### Когда использовать

- административные панели;
- личные кабинеты;
- внутренние системы;
- приложения, где пользовательская интерактивность важнее индексируемого содержимого.
2. SSR — Server-Side Rendering
HTML создаётся на сервере при поступлении запроса.

### Например, запрос

```text
GET /students/123456
```

### поступает в Nuxt, который

1. Определяет маршрут.
2. Получает данные студента от Java API.
3. Формирует HTML.
4. Возвращает HTML браузеру.
### Пример упрощённого серверного компонента Nuxt:

```vue
<script setup lang="ts">
const route = useRoute();

const { data: student, error } = await useFetch(
    `/api/students/${route.params.id}`
);
```

</script>

```vue
<template>
    <p v-if="error">
        Не удалось загрузить студента
    </p>

    <div v-else-if="student">
        <h1>{{ student.name }}</h1>
        <p>{{ student.group }}</p>
    </div>
</template>
```

### Важный нюанс: реальный проект использует собственный useStudentCard, а серверный transport проходит через Nuxt proxy к Java.

#### Преимущества

- HTML сразу содержит данные;
- подходит для динамических страниц;
- помогает поисковой индексации;
- можно получить персонализированную страницу с учётом серверной сессии.
#### Недостатки

- HTML нужно формировать при запросах;
- увеличивается нагрузка на сервер;
- долгий запрос к БД/API задерживает HTML;
- требуется контролировать кеширование персональных данных.
#### Когда использовать

- карточки товаров;
- страницы пользователей;
- динамические каталоги;
- страницы с содержимым, зависящим от пользователя или актуальных данных.

метафреймворк может сформировать готовые HTML-файлы во время build.

Далее эти файлы размещаются на CDN или статическом хостинге.


Пользователь

В лекции №10 на страницах 16–17 показано, что SSG формирует HTML во время сборки, а затем CDN раздаёт готовые HTML-артефакты. Лекция№10(2).pdf

#### Преимущества

- очень быстрая отдача готового HTML;
- низкая нагрузка на сервер рендеринга;
- удобное кеширование через CDN;
- хорошая индексация;
- высокая предсказуемость.
#### Недостатки

- содержимое отражает данные на момент сборки;
- при изменении данных может потребоваться новая сборка;
- не подходит для персональных страниц, если они отличаются для каждого пользователя;
- для динамических маршрутов нужно заранее определить, какие страницы генерировать.
#### Когда использовать

- документация;
- лендинги;
- блог;
- публичная информация;
- страницы, которые редко меняются.
4. ISR — Incremental Static Regeneration
ISR — стратегия, которая позволяет обновлять ранее сгенерированные статические страницы без полной пересборки всего сайта.

Идея: изначально страница создаётся как статическая, но после определённого времени становится устаревшей и может быть сгенерирована заново.

### Последовательность

1. Страница создаётся и сохраняется в кеше.
2. Пользователи получают готовую страницу.
3. По истечении заданного времени страница считается устаревшей.
4. Запускается повторная генерация.
5. После обновления новые запросы получают свежую версию.
В лекции №10 на странице 18 ISR определяется именно как обновление готовых статических страниц без полной пересборки сайта. Revalidation задаёт правило, когда страница считается устаревшей. Лекция№10(2).pdf

#### Преимущества

- быстрая отдача статического HTML;
- не нужно пересобирать всё приложение;
- можно поддерживать актуальность публичных страниц;
- снижение нагрузки на backend при повторных запросах.
#### Недостатки

- некоторые пользователи могут получить устаревшую версию;
- нужно корректно выбирать время обновления;
- сложнее инвалидировать связанные кеши;
- не подходит для приватных страниц без учёта пользователя.
#### Когда использовать

- каталоги товаров;
- публичные профили;
- новости;
- рейтинги;
- страницы, которые обновляются периодически.

| Параметр | CSR | SSR | SSG | ISR |
| --- | --- | --- | --- | --- |
| Кто создаёт HTML | Браузер | Сервер | Сборка | Сборка / серверное обновление |
| Когда | После JS | При запросе | При build | При обновлении устаревшей страницы |

| Нагрузка на сервер | Низкая на рендеринг | Выше | Низкая при отдаче | Умеренная при регенерации |
| Типичный пример | Личный кабинет | Карточка студента | Документация | Каталог |

- частоту изменения данных;
- персонализацию;
- стоимость вычислений;
- объём JavaScript.

## 4. Гибридный рендеринг. Совмещение серверного и клиентского рендеринга

Гибридный рендеринг (Hybrid Rendering) — подход, при котором внутри одного приложения используются разные стратегии рендеринга для разных страниц или участков интерфейса.

Основная причина — у разных страниц разные требования.

### Например

- главная страница может быть статической;
- каталог — кешируемым с периодическим обновлением;
- карточка студента — серверной, поскольку зависит от актуальных данных;
- панель управления — интерактивной и в основном клиентской.
В лекции №10 на страницах 23–25 показано, что одного режима недостаточно: Router выбирает стратегию для каждого маршрута. Лекция№10(2).pdf

### Как работает Hybrid Rendering?

### Представим веб-приложение

Router
```text
  |
  ├── /about       → SSG
  |
  ├── /catalog     → ISR
  |
  ├── /students/42 → SSR
  |
  └── /settings    → CSR
```

Router определяет маршрут и применяет нужную стратегию.
### Пример распределения стратегий

/about

Публичная информация, редко меняется

SSG

/catalog

Каталог, можно допустить небольшое устаревание

ISR

/students/42

Карточка зависит от актуальных данных и доступа

SSR

/settings

Интерактивные настройки личного кабинета

CSR

### Почему это выгодно?

Если использовать SSR для абсолютно всех страниц, сервер будет выполнять лишнюю работу для статического контента.

Если использовать CSR для всего, публичные страницы могут дольше отображать содержимое и потребовать дополнительных запросов.

Если использовать SSG для всего, персональные данные и часто меняющаяся информация будут устаревать или станут небезопасными.

Гибридный подход позволяет выбирать компромисс для каждой страницы.
Как реализовать это в Nuxt?
Nuxt позволяет задавать правила рендеринга и кеширования по маршрутам через routeRules.

### Упрощённый пример

```text
export default defineNuxtConfig({
    routeRules: {
        "/about": {
            prerender: true
        },

        "/catalog/**": {
            swr: 300
        },

        "/students/**": {
            ssr: true
        },

        "/settings": {
            ssr: false
        }
    }
});
```

### Пояснения

- prerender: true — заранее сгенерировать статическую страницу.
- swr: 300 — использовать кеш с политикой stale-while-revalidate на указанном маршруте.
- ssr: true — включить серверный рендеринг.
- ssr: false — отключить SSR для маршрута и рендерить его на клиенте.
Это иллюстрация возможностей Nuxt, а не конфигурация нашей лабораторной.

Важный момент безопасности: нельзя применять публичное кеширование или prerendering к страницам, содержащим персональные данные, если кеш не изолирован по пользователю. Нельзя допускать, чтобы HTML одного пользователя выдавался другому.

В нашей лабораторной все маршруты имеют Cache-Control: private, no-store, поскольку они могут содержать данные текущей сессии.
Гибридность на уровне одной страницы
### Гибридность может проявляться не только между маршрутами, но и внутри одной страницы

- сервер формирует основной контент;
- браузер после Hydration включает интерактивные элементы;
- отдельный блок может догружать данные на клиенте;
- независимые блоки могут рендериться потоково.
### Например, карточка студента

1. Nuxt на сервере получает данные студента.
2. Формирует HTML карточки.
3. Браузер показывает карточку.
4. Vue подключает кнопку редактирования, формы и другие обработчики.
5. При действиях пользователя данные отправляются через API.
Кратко для защиты: гибридный рендеринг позволяет использовать CSR, SSR, SSG и ISR в одном приложении. Router или конфигурация маршрутов выбирает стратегию для конкретной страницы. Это помогает учитывать свежесть данных, SEO, персонализацию и производительность. В нашей лабораторной основной режим — SSR, а общий HTTP-кеш для персональных страниц отключён.

## 5. Hydration. Назначение, принцип работы и проблема Hydration Mismatch

### Что такое Hydration?

Hydration (гидратация) — процесс, при котором браузер подключает клиентский JavaScript к HTML, который уже был сформирован сервером, и делает его интерактивным.

При SSR сервер создаёт HTML и отправляет его браузеру. Пользователь уже может видеть содержимое страницы, но обработчики событий ещё не обязательно подключены.

### Например, сервер отправил

```vue
<div>
    <h1>Студент №42</h1>
    <button>Редактировать</button>
```

</div>

Браузер отобразил этот HTML. Однако сама кнопка пока не обязательно реагирует на нажатие, потому что JavaScript ещё не выполнился или Hydration не завершилась.

### После загрузки JavaScript фреймворк

1. Восстанавливает клиентское дерево компонентов.
2. Сопоставляет его с уже существующей HTML-разметкой.
3. Подключает обработчики событий.
4. Связывает DOM с реактивным состоянием.
5. Делает интерфейс интерактивным.
В лекции №10 на странице 40 Hydration определена как процесс «оживления» статичного HTML: браузер подключает JavaScript и связывает его с уже отрендеренной разметкой. Отдельно подчёркивается, что Hydration не означает повторную загрузку всей страницы. Лекция№10(2).pdf

Зачем нужна Hydration?
Без Hydration SSR-страница могла бы оставаться просто статичной HTML-разметкой.

Пользователь видел бы содержимое, но интерактивные элементы не работали бы как полноценное приложение.

### Hydration объединяет преимущества двух подходов

- SSR быстро отдаёт готовый HTML;
- JavaScript в браузере обеспечивает интерактивность.
### Например, карточка студента отображается сразу, а после Hydration начинают работать

- кнопка редактирования;
- удаление;
- открытие модального окна;
- изменение состояния интерфейса.
Три момента готовности страницы
### В лекции №10 на странице 39 выделены три разных состояния

1. HTML получен — браузер получил разметку.
2. Контент виден — HTML и CSS уже отображены.
3. JavaScript готов — Hydration завершилась, обработчики и интерактивность работают.
Это важное различие: страница может быть визуально готова до завершения JavaScript. Лекция№10(2).pdf

### Что такое Hydration Mismatch?

Hydration Mismatch — расхождение между HTML, который был сгенерирован на сервере, и результатом первоначального рендеринга на клиенте.

То есть сервер и браузер получили разные результаты для одного и того же компонента.

В лекции №10 на страницах 42–43 это описано как несовпадение первоначального результата рендеринга сервера и клиента. Отдельно подчёркивается, что нужно искать причину расхождения, а не просто убирать предупреждение. Лекция№10(2).pdf

### Почему возникает Hydration Mismatch?

1. Использование случайных значений

### Неправильно

```vue
<script setup>
const id = Math.random();
```

</script>

```vue
<template>
    <p>{{ id }}</p>
</template>
```

На сервере будет сгенерировано одно значение, а в браузере — другое. Разметка не совпадёт.

2. Использование текущего времени
```vue
<script setup>
const now = new Date().toLocaleString();
```

</script>

```vue
<template>
    <p>{{ now }}</p>
</template>
```

Сервер и браузер могут иметь разные временные зоны, локали или значения времени.

3. Использование browser-only API во время первоначального рендеринга

### Например

```ts
const theme = localStorage.getItem("theme");
```

На сервере localStorage отсутствует, а в браузере существует.

Если на сервере отображается light, а на клиенте dark, возникает несовпадение.

4. Разная логика по окружению
```vue
<template>
    <p v-if="typeof window !== 'undefined'">
        Браузер
    </p>

    <p v-else>
        Сервер
    </p>
</template>
```

На сервере будет одна разметка, на клиенте — другая.

5. Некорректная HTML-вложенность

### Например

<p>
```vue
    Текст
    <div>Блок</div>
```

</p>

Браузер может автоматически исправить некорректную структуру DOM, из-за чего клиентское дерево не совпадёт с ожидаемым.
Как исправлять Hydration Mismatch?
Главный принцип: первоначальный результат рендеринга на сервере и клиенте должен быть одинаковым.

### В Nuxt browser-only действия нужно выполнять на клиенте, например в onMounted()

```vue
<script setup>
import { ref, onMounted } from "vue";

const theme = ref("light");

onMounted(() => {
    theme.value =
        localStorage.getItem("theme") ?? "light";
});
```

</script>

```vue
<template>
    <p>Тема: {{ theme }}</p>
</template>
```

На сервере и при начальной гидратации значение будет light. После монтирования в браузере оно может измениться на сохранённое.

### Другие способы

- генерировать случайное значение один раз на сервере и передавать его клиенту;
- передавать время и локаль явно;
- использовать SSR-safe composables;
- оборачивать browser-only содержимое в <ClientOnly>, если его нельзя отрендерить на сервере;
- проверять корректность HTML-вложенности.
Что не стоит делать: просто отключать предупреждения Hydration. Это может скрыть симптом, но не устранить проблему. Несовпадение может привести к неправильному отображению или лишним операциям обновления DOM.
Как это работает в нашей лабораторной?
### В нашей лабораторной используется Nuxt с

ssr: true

На странице списка студентов данные загружаются через useStudentList, а на карточке — через useStudentCard.

useAsyncData сохраняет результат SSR в Nuxt payload, чтобы браузер мог использовать эти данные при Hydration и не выполнять тот же запрос повторно без необходимости.

Таким образом, сервер и клиент получают согласованный набор данных для первоначального интерфейса.

Кратко для защиты: Hydration делает серверный HTML интерактивным, подключая клиентский JavaScript и обработчики событий. Hydration Mismatch возникает, когда серверная и клиентская версии первоначальной разметки отличаются. Причины — случайные значения, время, browser API, различия окружений и некорректная HTML-вложенность. Решение — обеспечить одинаковый первоначальный рендер и переносить browser-only логику в клиентские lifecycle hooks.

## 6. Streaming SSR. Потоковая передача HTML и постепенная загрузка содержимого

### Что такое Streaming SSR?

Streaming SSR — способ серверного рендеринга, при котором HTML отправляется браузеру частями, по мере готовности отдельных участков страницы, а не одним большим ответом после завершения всей генерации.

### Обычный SSR часто работает по следующей схеме

1. Сервер получает запрос.
2. Загружает все необходимые данные.
3. Формирует весь HTML.
4. Отправляет его браузеру.
Если одна часть страницы долго загружает данные, может задерживаться отправка всего HTML.

Streaming SSR решает эту проблему: сервер может отправить уже готовую оболочку страницы и fallback для медленных блоков, а затем передать окончательный контент, когда он будет готов.

В лекции №10 на страницах 45–50 это разобрано через shell, fallback, Suspense и несколько независимых границ ожидания. На странице 45 подчёркивается: Streaming уменьшает время ожидания отображения готовых частей, но не ускоряет сами запросы к данным. Лекция№10(2).pdf

### Как работает Streaming SSR?

### Представим страницу

StudentPage
```text
├── Header
├── StudentInfo
├── StudentHistory
└── Recommendations
```

### Допустим

- Header готов сразу;
- StudentInfo загружается за 100 мс;
- StudentHistory — за 300 мс;
- Recommendations — за 2 секунды.
Обычный SSR может ждать все три блока, прежде чем отправить HTML.

### Streaming SSR может

1. Отправить Header.
2. Отправить fallback для истории и рекомендаций.
3. Передать StudentInfo, когда он готов.
4. Передать StudentHistory.
5. Передать рекомендации последними.
Упрощённая временная шкала

Не в масштабе, иллюстрация порядка готовности блоков
Header

Сразу

StudentInfo

~100 мс

StudentHistory

~300 мс

Recommendations

~2 с

Важное следствие: пользователь может начать читать и использовать уже готовые части страницы раньше, не ожидая самого медленного блока.
### Что такое fallback?

Fallback — временное содержимое, которое отображается вместо ещё не готового блока.

### Например

<Suspense fallback={<p>Загружаем историю студента...</p>}>
```text
    <StudentHistory />
```

</Suspense>

Пока StudentHistory не готов, показывается fallback. Когда данные и компонент готовы, он заменяется окончательным содержимым.
### Что такое Suspense?

Suspense — механизм React для определения границ ожидания асинхронного содержимого.

Он позволяет указать, какой участок интерфейса должен показывать fallback, пока вложенный компонент не готов.

### Пример

```vue
import { Suspense } from "react";

function StudentPage() {
    return (
        <main>
            <h1>Карточка студента</h1>

            <Suspense fallback={<p>Загружаем данные...</p>}>
                <StudentInfo />
            </Suspense>

            <Suspense fallback={<p>Загружаем историю...</p>}>
                <StudentHistory />
            </Suspense>
        </main>
    );
}
```

Обе области могут ожидать независимо. Страница не обязана блокироваться из-за самой медленной части.

В лекции №10 на странице 50 указано, что независимые Suspense-границы завершают ожидание независимо друг от друга. Лекция№10(2).pdf

### Что такое Shell?

Shell — основная оболочка страницы, которая готова к отправке раньше остальных данных.

### Она может включать

- общую шапку;
- навигацию;
- структуру страницы;
- fallback-блоки.
Пользователь сначала видит оболочку, а затем постепенно получает готовые участки.
Progressive и Selective Hydration
В лекции №10 на странице 51 дополнительно упоминаются Progressive и Selective Hydration.
- Progressive Hydration — гидратация частей интерфейса по мере готовности.
- Selective Hydration — React может приоритизировать гидратацию отдельных областей, в том числе связанных с пользовательским взаимодействием.
Важно: это понятия экосистемы React. Не нужно утверждать, что все метафреймворки реализуют их идентично.
Преимущества Streaming SSR
- раннее отображение готовой оболочки;
- пользователь не ждёт все данные целиком;
- независимые блоки могут появляться по готовности;
- уменьшается эффект блокировки всей страницы;
- улучшается восприятие скорости.
Недостатки и ограничения
- сложнее организовать ошибки и состояния частично готовой страницы;
- инфраструктура должна поддерживать передачу потоков;
- не все прокси и браузеры одинаково хорошо показывают маленькие порции данных;
- после начала отправки HTTP-заголовков уже нельзя изменить статус ответа;
- сам сетевой запрос от Streaming не становится быстрее.
Например, если backend отвечает за 2 секунды, Streaming не сделает его ответ секундным. Он лишь позволяет показать остальные готовые части раньше.

Официальная документация Next.js отдельно отмечает этот нюанс: после начала streaming HTTP-ответа статус уже нельзя изменить, поэтому критические проверки и 404 лучше выполнять до начала потоковой передачи.
Next.js+1

Используется ли Streaming SSR в нашей лабораторной?
В лабораторной №5 реализован SSR через Nuxt, но явная организация страницы посредством Streaming SSR и Suspense-границ в проекте не заявлена. Поэтому корректно говорить, что мы используем SSR, а Streaming SSR изучаем как дополнительную возможность метафреймворков.

Кратко для защиты: Streaming SSR отправляет HTML частями по мере готовности блоков. Сначала браузер получает shell и fallback, а затем готовый контент. Suspense определяет границы ожидания. Это позволяет показывать части страницы раньше, но не ускоряет сами запросы к данным.

## 7. Серверные и клиентские компоненты. Особенности выполнения кода в разных окружениях

Серверное и клиентское окружение
### В метафреймворках код может исполняться в разных средах

1. Build time — этап сборки.
2. Server runtime — среда выполнения на сервере.
3. Browser runtime — выполнение в браузере.
В лекции №10 на странице 29 эти три окружения показаны отдельно. Ошибки SSR часто связаны с тем, что разработчик использует возможности одного окружения в другом. Лекция№10(2).pdf

### Например

| Возможность | Сервер | Браузер |
| --- | --- | --- |
| window | Нет | Да |
| document | Нет | Да |
| localStorage | Нет | Да |
| Доступ к серверным переменным окружения | Да | Только публичные значения, специально переданные клиенту |
| Прямой доступ к серверным секретам | Да | Нет |
| DOM | Нет | Да |

### Что такое Server Components и Client Components?

Важное уточнение: понятие Server Components / Client Components в строгом смысле относится прежде всего к React Server Components и Next.js App Router. Нельзя автоматически переносить эту модель на все метафреймворки.

Server Component — React-компонент, который выполняется на сервере. Он может:
- получать данные;
- обращаться к серверным ресурсам;
- использовать секреты, которые не должны попасть в браузер;
- формировать часть интерфейса;
- не отправлять клиенту свой обычный JavaScript-код компонента как интерактивную клиентскую часть.
Но Server Component не может использовать обычные клиентские обработчики вроде onClick или браузерные Hooks, такие как useState.

### Пример

```vue
// app/students/page.tsx
export default async function StudentsPage() {
    const response = await fetch(
        "https://api.example.com/students"
    );

    const students = await response.json();

    return (
        <ul>
            {students.map(student => (
                <li key={student.id}>
                    {student.name}
                </li>
            ))}
        </ul>
    );
}
```

Компонент получает данные на сервере и формирует список.

### Client Component — React-компонент, в котором нужна интерактивность

- локальное состояние;
- обработчики событий;
- браузерные API;
- клиентские Hooks;
- интерактивные формы.
В Next.js для обозначения клиентской границы используется директива:
"use client";

### Пример

"use client";

```vue
import { useState } from "react";

export default function StudentNote() {
    const [visible, setVisible] = useState(false);

    return (
        <div>
            <button onClick={() => setVisible(!visible)}>
                Показать заметку
            </button>

            {visible && <p>Заметка студента</p>}
        </div>
    );
}
```

Здесь состояние и обработчик должны работать в браузере.
Как они взаимодействуют?
Обычно серверный компонент получает данные, а клиентский обеспечивает интерактивность.

### Например

```vue
// Server Component
import StudentActions from "./StudentActions";

export default async function StudentPage() {
    const student = await getStudent(42);

    return (
        <main>
            <h1>{student.name}</h1>

            <StudentActions
                studentId={student.id}
                studentName={student.name}
            />
        </main>
    );
}
```

### Клиентская часть

"use client";

```vue
import { useState } from "react";

export default function StudentActions({
    studentId,
    studentName
}) {
    const [showNote, setShowNote] = useState(false);

    return (
        <div>
            <button onClick={() => setShowNote(!showNote)}>
                Показать заметку
            </button>

            {showNote && <p>Студент: {studentName}</p>}
        </div>
    );
}
```

Через границу серверного и клиентского компонентов передаются сериализуемые данные. Функции-обработчики и обычные callback нельзя просто передать как сериализуемый prop из Server Component в Client Component.

В лекции №10 на страницах 52–56 подчёркивается: Server Components — специфика React, сервер получает данные, клиент добавляет состояние и обработчики событий. Лекция№10(2).pdf

Как это относится к Nuxt?
В Nuxt нет точно такой же универсальной модели React Server Components. Обычный Vue-компонент при SSR может выполниться на сервере для формирования HTML, а затем быть гидратирован в браузере.

### То есть в Nuxt правильнее говорить о

- серверном выполнении при SSR;
- клиентском выполнении после Hydration;
- клиентских и серверных composables/API;
- разделении кода с помощью .client / .server или import.meta.client / import.meta.server.
### Например

```vue
<script setup>
import { ref, onMounted } from "vue";

const theme = ref("light");

onMounted(() => {
    theme.value = localStorage.getItem("theme") ?? "light";
});
```

</script>

onMounted вызывается в браузере после монтирования компонента, поэтому доступ к localStorage здесь безопасен.

### Если же написать

```ts
const theme = localStorage.getItem("theme");
```

на верхнем уровне setup, SSR может завершиться ошибкой, потому что localStorage не существует на сервере.
### Как это реализовано в нашей лабораторной?

Nuxt выполняет SSR, но авторизация, проверка JWT и бизнес-логика остаются в Java.

Например, server/api/backend/[...path].ts — серверный Nuxt endpoint, который:
- принимает запрос браузера;
- читает HttpOnly-cookie;
- при необходимости обновляет токены;
- отправляет запрос к Java;
- возвращает ответ клиенту.
JWT не попадает в HTML и клиентское состояние. Это важное архитектурное решение.

Кратко для защиты: серверные и клиентские компоненты различаются средой выполнения и доступными возможностями. В React Server Components работают на сервере, а Client Components нужны для состояния, событий и browser API. В Nuxt обычные Vue-компоненты могут рендериться на сервере, а затем гидратироваться в браузере; это не та же самая модель React Server Components. В нашей лабораторной сервер Nuxt служит транспортом к Java, а бизнес-логика остаётся на backend.

## 9. Клиентская навигация и Prefetching. Предварительная загрузка страниц и ресурсов

Клиентская навигация
Клиентская навигация — переход между страницами SPA без полной перезагрузки HTML-документа.

### При обычной навигации браузер

1. отправляет запрос на новый URL;
2. получает новый HTML;
3. загружает документ;
4. повторно строит страницу.
### При клиентской навигации

1. пользователь нажимает ссылку;
2. Router перехватывает переход;
3. URL изменяется средствами клиентской маршрутизации;
4. приложение загружает необходимые данные или код страницы;
5. меняется отображаемый компонент;
6. общий Layout обычно остаётся на месте.
В лекции №10 на странице 35 отдельно показано различие между первым открытием URL и переходом внутри приложения: при клиентской навигации полный HTML-документ обычно не запрашивается. Лекция№10(2).pdf

### В Nuxt используется компонент

```vue
<template>
    <nav>
        <NuxtLink to="/students">
            Студенты
        </NuxtLink>

        <NuxtLink to="/profile">
            Профиль
        </NuxtLink>
    </nav>
</template>
```

NuxtLink выполняет навигацию с использованием Router, а не обычную полную перезагрузку страницы.
### Что такое Prefetch?

Prefetching — предварительная загрузка ресурсов маршрута до того, как пользователь перейдёт по ссылке.

Например, пользователь находится на странице /students, где есть ссылка на /students/123456.

### Пока пользователь ещё не нажал на неё, приложение может заранее загрузить

- JavaScript-код страницы;
- данные маршрута;
- необходимые ресурсы;
- иногда payload или другие зависимости маршрута.
Когда пользователь нажмёт ссылку, часть работы уже будет выполнена.

В лекции №10 на странице 36 Prefetch определён как предварительная загрузка ресурсов маршрута до клика. Ожидаемый результат — более быстрый переход, хотя сама подготовительная загрузка тоже использует сетевой трафик. Лекция№10(2).pdf

### Как работает Prefetching?

Ссылка появилась в интерфейсе

Пользователь видит маршрут

Prefetch

Предварительно загружаются ресурсы

Клик по ссылке

Переход пользователя

Более быстрый переход

Часть ресурсов уже готова

Преимущества Prefetching
- сокращает ожидание после клика;
- улучшает воспринимаемую скорость приложения;
- позволяет загружать код заранее;
- полезен для часто посещаемых маршрутов.
Недостатки
- расходует сетевой трафик до того, как пользователь решил перейти;
- может загружать ненужные данные;
- требует контроля при большом количестве ссылок;
- предварительная загрузка персональных данных должна учитывать авторизацию и кеширование.
### Нужно различать Prefetch, Preload и обычную загрузку

- Prefetch — ресурс может понадобиться в будущем.
- Preload — ресурс нужен для текущей страницы и должен быть загружен с высоким приоритетом.
- Lazy Loading — ресурс загружается только при необходимости.
Как это связано с маршрутизацией метафреймворка?
Метафреймворк знает структуру маршрутов и может заранее определить зависимости конкретной страницы. Поэтому он способен выполнять Prefetch автоматически или по настройкам.

В Nuxt <NuxtLink> поддерживает автоматическую предварительную загрузку ресурсов маршрута при соответствующих условиях. В Next.js аналогичную задачу выполняет компонент Link с механизмом prefetch.

Важно: Prefetch не означает, что приложение обязательно заранее выполнит все запросы к Java backend. Конкретный объём предварительной загрузки зависит от фреймворка, маршрута, режима сборки и конфигурации.

### Пример Nuxt:

```vue
<template>
    <NuxtLink to="/students/123456">
        Открыть карточку студента
    </NuxtLink>
</template>
```

Nuxt Router может заранее подготовить ресурсы маршрута. Для точного управления предварительной загрузкой применяются настройки NuxtLink и Router.

Как применяется в нашей лабораторной?

### При переходе из таблицы студентов в карточку

<NuxtLink :to="`/students/${student.ISU}`">
```text
    {{ student.name }}
```

</NuxtLink>

Переход выполняется клиентским Router. Общий Layout сохраняется, а содержимое страницы меняется. Сам факт такого перехода не означает, что вся карточка обязательно была загружена заранее.

Кратко для защиты: клиентская навигация меняет страницу без полной перезагрузки HTML, используя Router. Prefetching заранее загружает ресурсы будущего маршрута до клика, поэтому переход может произойти быстрее. Но предварительная загрузка использует трафик и должна применяться разумно.

## 10. Серверная загрузка данных. Взаимодействие метафреймворка с внешним REST API

### Что такое серверная загрузка данных?

Серверная загрузка данных — получение необходимой информации на сервере метафреймворка до формирования HTML-ответа.

Вместо того чтобы отправлять браузеру пустую оболочку и заставлять его самостоятельно запрашивать все данные, сервер может:
1. Получить HTTP-запрос пользователя.
2. Определить маршрут.
3. Выполнить запрос к внешнему API.
4. Получить JSON.
5. Передать данные компоненту.
6. Сформировать HTML с данными.
7. Отправить готовый HTML браузеру.
В лекции №10 на страницах 57–59 сравниваются загрузка данных на сервере и в браузере. Серверная загрузка позволяет включить данные в HTML первого экрана, а браузерная — обновлять данные без полной перезагрузки документа. Лекция№10(2).pdf

### Что такое REST API?

REST API — интерфейс взаимодействия между клиентом и сервером через HTTP, построенный вокруг ресурсов и стандартных HTTP-методов.

### Например, backend системы управления студентами может предоставлять

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| GET | /api/user/students | Получить список |
| GET | /api/user/students/123456 | Получить конкретного студента |
| POST | /api/admin/students | Создать студента |
| PUT | /api/admin/students/123456 | Полностью обновить запись |
| PATCH | /api/admin/students/123456 | Частично обновить запись |
| DELETE | /api/admin/students/123456 | Удалить студента |

Где выполняется запрос к REST API?
Есть два основных варианта.

1. Запрос в браузере
```ts
const response = await fetch("/api/students");

const students = await response.json();
```

#### Преимущества

- проще реализовать действия пользователя;
- данные можно загружать по мере необходимости;
- удобно обновлять интерфейс без перезагрузки.
#### Недостатки

- для первого экрана нужно дождаться выполнения JavaScript;
- запросы могут раскрывать адреса API и часть сетевой логики;
- нельзя безопасно хранить секреты в клиентском коде.
2. Запрос на сервере метафреймворка

### Nuxt может выполнить запрос к backend во время SSR

```vue
<script setup lang="ts">
const { data, error, pending } = await useAsyncData(
    "students",
    () => $fetch("/api/backend/user/students")
);
```

</script>

```vue
<template>
    <p v-if="pending">Загрузка...</p>
    <p v-else-if="error">Ошибка</p>

    <ul v-else>
        <li
            v-for="student in data"
            :key="student.ISU"
        >
            {{ student.name }}
        </li>
    </ul>

```

В реальной лабораторной вместо обычного $fetch используется собственная инфраструктура useStudents и useApi, поскольку нужно учитывать серверный SSR, cookie и Java backend.
### Почему нужны useFetch и useAsyncData?

В Nuxt есть несколько способов выполнять запросы.

$fetch — удобная обёртка над Fetch API. Подходит для запросов в обработчиках событий и обычных серверных/клиентских функциях.

useFetch — composable для загрузки данных в компонентах с поддержкой SSR и состояния data, pending, error.

useAsyncData — более гибкий механизм, который позволяет управлять ключами, преобразованием ответа, кешированием и поведением запроса.

Официальная документация Nuxt объясняет, что useFetch — удобная обёртка над useAsyncData и $fetch, а $fetch часто подходит для пользовательских действий.
Nuxt Tutorial

## 11. Последовательная и параллельная загрузка данных. Проблема Request Waterfall

### Что такое Request Waterfall?

Request Waterfall (водопад запросов) — ситуация, когда несколько независимых сетевых запросов выполняются последовательно, хотя могли бы выполняться одновременно.

Это приводит к лишнему ожиданию.

### Представим, что для страницы профиля нужны три независимых ресурса

- информация о пользователе;
- настройки;
- список уведомлений.
Каждый запрос занимает примерно 300 мс.
Последовательная загрузка
```ts
const user = await fetchUser();
const settings = await fetchSettings();
const notifications = await fetchNotifications();
```

Сначала выполняется fetchUser(). Только после его завершения начинается fetchSettings(). После завершения второго запроса начинается третий.

### Общее время

\[
T = T_1 + T_2 + T_3
\]

### Если каждый запрос занимает 300 мс

\[
T = 300 + 300 + 300 = 900 \text{ мс}
\]

Параллельная загрузка
### Если запросы независимы, их можно запустить одновременно

const [user, settings, notifications] =
```ts
    await Promise.all([
        fetchUser(),
        fetchSettings(),
        fetchNotifications()
    ]);
```

### Общее время будет примерно равно времени самого медленного запроса

\[
T \approx \max(T_1, T_2, T_3)
\]

### При одинаковых запросах по 300 мс

\[
T \approx 300 \text{ мс}
\]

В лекции №10 на страницах 60–62 приводится именно этот пример: три запроса по 300 мс дают около 900 мс при последовательной загрузке и около 300 мс при параллельной. Лекция№10(2).pdf

### Что такое Promise.all?

Promise.all() принимает массив Promise и возвращает один Promise, который завершится, когда завершатся все переданные операции.

### Пример

```ts
const requests = [
    fetch("/api/user"),
    fetch("/api/settings"),
    fetch("/api/notifications")
```

];

```ts
const responses = await Promise.all(requests);
```

Обратите внимание: запросы начинают выполняться уже при вызове fetch, а Promise.all ожидает завершения всех.

### После получения ответов их нужно обработать

const [user, settings, notifications] =
```ts
    await Promise.all([
        fetch("/api/user").then(r => r.json()),
        fetch("/api/settings").then(r => r.json()),
        fetch("/api/notifications").then(r => r.json())
    ]);
```

Когда нельзя использовать параллельную загрузку?
Если второй запрос зависит от результата первого, их нельзя выполнить одновременно.

### Например

```ts
const user = await fetchUser();

const orders = await fetchOrders(user.id);
```

Чтобы получить заказы, нужен user.id. Поэтому сначала необходимо загрузить пользователя.

### Но после получения ID можно параллельно загрузить несколько независимых ресурсов

```ts
const user = await fetchUser();
```

const [orders, settings, notifications] =
```ts
    await Promise.all([
        fetchOrders(user.id),
        fetchSettings(user.id),
        fetchNotifications(user.id)
    ]);
```

Promise.all и ошибки
У Promise.all есть особенность: если один из Promise отклоняется, общий Promise тоже отклоняется.

Если необходимо получить результаты всех запросов, даже когда часть из них завершилась ошибкой, можно использовать Promise.allSettled():
```ts
const results = await Promise.allSettled([
    fetchUser(),
    fetchSettings(),
    fetchNotifications()
```

]);

for (const result of results) {
```text
    if (result.status === "fulfilled") {
        console.log("Данные:", result.value);
    } else {
        console.error("Ошибка:", result.reason);
    }
}
```

Как это связано с нашей лабораторной?
На странице списка студентов фильтры и параметры запроса могут быть известны заранее. Загрузка списка может выполняться одной операцией через useStudentList.

Если бы одновременно требовались независимые дополнительные сведения, например настройки отображения и справочник групп, их можно было бы запрашивать параллельно.

Однако загрузка сессии пользователя и защищённых данных иногда действительно образует последовательность: сначала необходимо восстановить сессию, а затем обращаться к защищённому API. В нашей лабораторной это сделано через restoreSession() и последующий запрос данных.

Не всякая последовательность запросов является ошибкой. Нужно отличать необходимую зависимость от искусственного ожидания.

Кратко для защиты: Request Waterfall возникает, когда независимые запросы выполняются друг за другом. Последовательная загрузка занимает сумму времени всех запросов, а параллельная — примерно время самого медленного. Для независимых запросов используют Promise.all, но если один запрос зависит от результата другого, последовательность необходима.

## 12. Кеширование данных. Cache Hit, Cache Miss и основные стратегии кеширования

### Что такое кеширование?

Кеширование (Caching) — сохранение ранее полученных данных или результатов вычислений, чтобы при повторном обращении не выполнять операцию заново.

### В веб-приложении кешировать можно

- HTML-страницы;
- JSON-ответы API;
- результаты запросов к базе данных;
- JavaScript, CSS и изображения;
- данные отдельных компонентов;
- результаты SSR;
- вычисленные значения.
Цель кеширования — уменьшить время ответа, сетевую нагрузку и количество повторных операций.

В лекции №10 на странице 63 отдельно подчёркивается, что для каждого кеша важны три вещи: ключ, свежесть и правила обновления. Лекция№10(2).pdf

### Что такое Cache Hit?

Cache Hit — ситуация, когда запрошенные данные уже присутствуют в кеше и могут быть использованы.

### Пример

1. Пользователь открыл список студентов.
2. Приложение выполнило запрос к Java.
3. Ответ сохранён в кеше.
4. Пользователь повторно открывает тот же список.
5. Приложение получает данные из кеша без повторного запроса к backend.
Это Cache Hit.
### Что такое Cache Miss?

Cache Miss — ситуация, когда нужных данных нет в кеше или кеш не может быть использован.

### Тогда

1. Приложение выполняет запрос к источнику данных.
2. Получает результат.
3. При разрешённой политике сохраняет его в кеше.
4. Возвращает данные пользователю.
В лекции №10 на странице 64 показаны два пути: cache hit — используем готовые данные, cache miss — обращаемся к источнику и можем сохранить результат в кеше. Лекция№10(2).pdf

Основные виды кеширования
1. Browser Cache

Кеширование браузером статических файлов и HTTP-ответов.

### Настраивается с помощью HTTP-заголовков

Cache-Control: public, max-age=3600

Это разрешает публично кешировать ресурс и использовать его в течение часа без проверки актуальности.

### Другой пример

Cache-Control: private, no-store

Это запрещает сохранение ответа в общем или частном HTTP-кеше.

2. CDN Cache

CDN (Content Delivery Network) хранит статические ресурсы или разрешённые публичные ответы на географически распределённых серверах.

Пользователь получает данные от ближайшего edge-сервера.

В лекции №10 на странице 17 CDN приводится как сеть серверов для быстрой доставки готовых страниц. Лекция№10(2).pdf

3. Server Cache

Кеш на стороне сервера приложения. Может содержать результаты запросов, вычислений или готовые данные.

### Например

```ts
const cache = new Map();

async function getStudents() {
    const cached = cache.get("students");

    if (cached) {
        return cached;
    }

    const response = await fetch("/api/students");
    const students = await response.json();

    cache.set("students", students);

    return students;
}
```

Это упрощённая реализация без TTL и инвалидации.

4. Application Data Cache

Кеш предметных данных внутри frontend-приложения.

Например, можно сохранять полученный список студентов на 30 секунд и повторно использовать его при возвращении на страницу.

Такой подход используется в нашей лабораторной через useStudents.ts.
### Что такое Cache Key?

Cache Key — ключ, по которому определяется, какие именно данные находятся в кеше.

### Для списка студентов ключ может включать

### students

### username=andrey

### group=P3222

### page=0

### size=10

sort=name,asc

### Почему это важно?

Если кешировать только по слову students, пользователь может получить данные с неправильными фильтрами или данные другого пользователя.

Поэтому ключ должен учитывать все параметры, от которых зависит ответ.
TTL
TTL (Time To Live) — время жизни кешированной записи.

### Например

TTL = 30 секунд

После 30 секунд запись становится устаревшей и должна быть обновлена согласно политике кеша.
Основные стратегии кеширования
| Стратегия | Принцип |
| --- | --- |
| Cache First | Сначала используем кеш, при отсутствии идём к источнику |
| Network First | Сначала пробуем сеть, при ошибке используем кеш |
| Stale-While-Revalidate | Сразу отдаём старые данные и обновляем их в фоне |
| Time-based | Данные становятся устаревшими по TTL |
| On-demand | Кеш инвалидируется по событию или команде |

Когда кеширование опасно?
### Нельзя бездумно кешировать

- персональные данные;
- ответы, зависящие от роли;
- сессионную информацию;
- данные, которые могут измениться сразу после запроса;
- приватные API-ответы в общем кеше.
### В нашей лабораторной на всех маршрутах установлен

Cache-Control: private, no-store

Это запрещает HTTP-кеширование персональных страниц.

### При этом внутренний кеш студентов реализован отдельно

- ключ зависит от пользователя и фильтров;
- срок жизни — 30 секунд;
- после CRUD выполняется инвалидация;
- при logout данные очищаются.
Важно различать HTTP-кеширование ответа и внутренний кеш данных приложения. Это разные уровни.

Официальная документация MDN описывает HTTP-кеширование, Cache-Control, валидаторы и revalidation.
MDN+1

Кратко для защиты: кеширование сохраняет данные для повторного использования. Cache Hit означает, что данные найдены в кеше, Cache Miss — что нужно обратиться к источнику. Кеш должен иметь ключ, время свежести и правила обновления. В нашей лабораторной персональные HTTP-ответы не кешируются общим кешем, а данные студентов имеют отдельный пользовательский кеш с TTL 30 секунд.

## 13. Revalidation и инвалидация кеша. Обновление данных по времени и по событию

### Что такое Revalidation?

Revalidation — процесс проверки актуальности кешированных данных и их обновления при необходимости.

Если данные уже сохранены в кеше, приложение может не загружать их заново каждый раз. Но со временем данные меняются, и кеш может устареть.

Например, студент сменил группу. В кеше может ещё находиться старая информация.

Revalidation позволяет определить, актуальны ли сохранённые данные, и при необходимости получить новую версию.

В лекции №10 на странице 66 Revalidation определяется как процесс проверки актуальности кешированных данных. На странице 67 показано, что TTL и событие определяют условие обновления, а SWR — поведение ответа. Лекция№10(2).pdf

Revalidation по времени
Это механизм, когда данные считаются устаревшими после заданного времени.

### Например

TTL = 60 секунд

Первые 60 секунд данные считаются свежими.

### После этого кеш может

- перестать отдавать данные;
- сначала отдать старые данные и обновить их в фоне;
- инициировать проверку на сервере.
### Пример простого кеша с TTL:

```ts
const cache = new Map();

async function getStudents() {
    const cached = cache.get("students");

    if (
        cached &&
        Date.now() - cached.timestamp < 60_000
    ) {
        return cached.data;
    }

    const response = await fetch("/api/students");
    const data = await response.json();

    cache.set("students", {
        data,
        timestamp: Date.now()
    });

    return data;
}
```

Если запись младше 60 секунд, возвращаем её из кеша. Иначе запрашиваем данные заново и обновляем кеш.
Revalidation по событию
Иногда ждать истечения TTL нерационально.

Например, после успешного редактирования студента данные нужно обновить сразу.

Для этого применяется инвалидация кеша.

Инвалидация (Cache Invalidation) — удаление или пометка кешированных данных как устаревших, чтобы при следующем обращении они были получены заново или обновлены.

### События

- создание студента;
- редактирование;
- удаление;
- смена пользователя;
- выход из системы;
- изменение настроек.
### Пример

```ts
function invalidateStudentsCache() {
    cache.delete("students");
}
```

### После сохранения

```ts
async function updateStudent(id, input) {
    const response = await fetch(`/api/students/${id}`, {
        method: "PUT",
        headers: {
            "Content-Type": "application/json"
        },
        body: JSON.stringify(input)
    });

    if (!response.ok) {
        throw new Error("Не удалось сохранить");
    }

    invalidateStudentsCache();

    return response.json();
}
```

После успешного изменения кеш удаляется. Следующее обращение загрузит актуальные данные.
### Чем Revalidation отличается от Invalidation?

- Revalidation — проверка актуальности и обновление кеша.
- Invalidation — пометка кеша как недействительного или его удаление.
Invalidation — один из способов инициировать последующую revalidation, но это не одно и то же.
### Что такое Stale-While-Revalidate?

SWR (Stale-While-Revalidate) — стратегия, при которой сначала пользователю отдаётся устаревшая версия данных, а параллельно запускается обновление кеша.

### Последовательность

1. Кеш содержит свежую версию v1.
2. Время свежести истекло.
3. Запрос получает старую версию v1.
4. В фоне выполняется повторное получение данных.
5. Кеш обновляется до v2.
6. Следующий запрос получает v2.
В лекции №10 на странице 19 приведён именно такой сценарий: пользователь после истечения времени продолжает получать v1, пока в фоне создаётся v2. Лекция№10(2).pdf

### Как выглядит SWR в простом примере?

```ts
const cache = new Map();

async function getStudents() {
    const key = "students";
    const cached = cache.get(key);

    if (!cached) {
        const data = await fetchStudents();

        cache.set(key, {
            data,
            timestamp: Date.now()
        });

        return data;
    }

    const isStale =
        Date.now() - cached.timestamp > 60_000;

    if (isStale) {
        // Обновляем в фоне
        fetchStudents().then(data => {
            cache.set(key, {
                data,
                timestamp: Date.now()
            });
        });
    }

    // Сразу отдаём старые данные
    return cached.data;
}
```

Это упрощённая иллюстрация SWR. В production-реализации потребуется обработка ошибок обновления, параллельных запросов и согласованности.
### Revalidation в Next.js

В актуальной документации Next.js предусмотрены time-based и on-demand варианты revalidation:
- cacheLife — задаёт жизненный цикл кешированных данных;
- revalidateTag — обновляет данные по тегу;
- updateTag — немедленно истекает связанный кеш;
- revalidatePath — инвалидирует кеш конкретного маршрута.
Поведение конкретных API зависит от версии и выбранной модели кеширования Next.js.
Next.js+1

Как это работает в нашей лабораторной?
В useStudents.ts реализован внутренний кеш:
- срок жизни — 30 секунд;
- ключ списка зависит от username и фильтров;
- ключ карточки зависит от ИСУ;
- после CRUD кеш очищается;
- при logout пользовательские данные очищаются.
### Упрощённо

```ts
function invalidate() {
    clearNuxtData(key =>
        key.startsWith("students:")
    );

    times.value = {};
}
```

После успешного редактирования или удаления вызывается invalidate(). Следующий запрос получает свежие данные.

Это инвалидация прикладного кеша, а не ISR.

Кратко для защиты: Revalidation проверяет актуальность кешированных данных. По времени она запускается после TTL, по событию — после изменения данных или другого действия. Invalidation помечает кеш устаревшим или удаляет его. SWR сразу отдаёт старую версию и обновляет её в фоне. В нашей лабораторной используется пользовательский кеш TTL 30 секунд с инвалидацией после CRUD и logout.

## 14. Middleware и защищённые маршруты. Перенаправление пользователей и проверка доступа

### Что такое Middleware?

Middleware — промежуточная функция, которая выполняется между поступлением запроса и дальнейшей обработкой маршрута или страницы.

Она позволяет выполнить дополнительные проверки и действия до основного рендеринга.

### Например

- проверить наличие сессии;
- проверить роль пользователя;
- перенаправить пользователя на другую страницу;
- изменить URL;
- проверить заголовки запроса;
- выполнить дополнительную обработку запроса.
В лекции №10 на странице 37 показана последовательность: запрос → правила redirect/rewrite → Router → получение данных → рендеринг. Подчёркивается, что до рендеринга запрос может быть перенаправлен на другой URL. Лекция№10(2).pdf

### Виды Middleware в Nuxt

Здесь важно различать два понятия.

1. Route Middleware

Выполняется при навигации к странице — как при прямом открытии URL, так и при клиентском переходе.

### Используется для

- проверки авторизации;
- проверки ролей;
- перенаправления пользователя;
- ограничения доступа к страницам.
### Nuxt поддерживает

- именованные middleware;
- глобальные middleware;
- middleware, заданные непосредственно в метаданных страницы.
2. Server Middleware

Выполняется в серверном окружении при обработке HTTP-запросов. Может использоваться для логирования, проверки заголовков и других серверных задач.

Это не то же самое, что Route Middleware: они работают на разных этапах.
### Как работает защищённый маршрут?

### Представим два маршрута

/profile — доступен авторизованному пользователю
/admin   — доступен только ADMIN

### Логика

1. Пользователь открывает маршрут.
2. Middleware получает информацию о сессии.
3. Если сессии нет, перенаправляет на /login.
4. Если сессия есть, проверяет роль.
5. Если роль подходит, пропускает к странице.
6. Если роль не подходит, перенаправляет на /forbidden.
### Пример Route Middleware в Nuxt

```ts
// app/middleware/access.global.ts

export default defineNuxtRouteMiddleware(async (to) => {
    const auth = useAuth();

    // Проверяем, требуется ли авторизация
    if (!to.meta.requiresAuth) {
        return;
    }

    // Восстанавливаем сессию
    await auth.restoreSession();

    // Если пользователь не вошёл
    if (!auth.user.value) {
        return navigateTo("/login");
    }

    // Проверяем необходимую роль
    const roles = to.meta.roles as string[] | undefined;

    if (
        roles?.length &&
        !roles.includes(auth.user.value.role)
    ) {
        return navigateTo("/forbidden");
    }
});
```

### На странице задаём метаданные

```vue
<script setup>
```

definePageMeta({
```text
    requiresAuth: true,
    roles: ["ADMIN"]
});
```

</script>

Теперь перед переходом Nuxt выполнит middleware и проверит пользователя.
### Что означает redirect и rewrite?

Эти механизмы позволяют изменить маршрут обработки.
- Redirect — пользователь перенаправляется на другой URL, и адрес в браузере меняется.
- Rewrite — сервер внутренне меняет маршрут обработки, но браузер может продолжать показывать исходный URL.
### Например

/profile → /login

Это redirect.

А внутреннее направление запроса /api/public на другой серверный обработчик — пример rewrite-подобной логики.
### Почему Middleware не заменяет backend-проверку прав?

Это один из самых важных вопросов по защите.

### Route Middleware в Nuxt может запретить переход на страницу, но пользователь всё равно может

- вручную вызвать API;
- изменить клиентское состояние;
- отправить запрос через Postman;
- обойти frontend-код.
### Поэтому backend обязан независимо проверять

- валидность токена;
- пользователя;
- его роль;
- права на конкретную операцию.
Например, даже если frontend разрешает /admin, Java должен проверить, что запрос действительно пришёл от администратора.

В нашей лабораторной Java остаётся источником истины по авторизации и разграничению доступа.
Как это сделано в проекте?
В app/middleware/access.global.ts реализована глобальная проверка маршрутов:
- восстанавливается сессия через useAuth().restoreSession();
- неавторизованный пользователь перенаправляется на /login;
- пользователь без необходимой роли перенаправляется на /forbidden;
- ошибки сети не должны автоматически трактоваться как выход из системы.
Важное замечание: сама проверка маршрута не выполняет проверку прав в Java. В Java backend остаются реальные проверки токенов и ролей.

Также серверный proxy server/api/backend/[...path].ts проверяет допустимые сочетания методов и путей, а затем передаёт запрос к Java.

Официальное руководство Nuxt описывает Route Middleware как механизм, выполняемый и при клиентской навигации, и при SSR.
Nuxt Tutorial+1

Кратко для защиты: Middleware — промежуточный механизм, который выполняется до обработки страницы или HTTP-запроса. В Nuxt Route Middleware используется для проверки авторизации, ролей и перенаправлений. Однако frontend middleware не является реальной защитой API: backend обязан самостоятельно проверять токен и права пользователя.

## 15. Обработка состояний приложения. Loading, Error, Not Found и HTTP-статусы

### Почему необходимо обрабатывать состояния?

При взаимодействии с сервером пользовательский интерфейс не всегда находится в состоянии успешной загрузки.

### Возможны ситуации

- данные ещё загружаются;
- запрос завершился ошибкой;
- запрошенный объект отсутствует;
- пользователь не авторизован;
- у пользователя недостаточно прав;
- сервер временно недоступен;
- список пуст.
Если не учитывать эти ситуации, интерфейс может показывать пустой экран или некорректное содержимое.

Поэтому нужно явно моделировать состояния страницы.
### Основные состояния

1. Loading

Состояние загрузки. Показывается, пока ожидается результат асинхронной операции.

### Пример

```vue
<p v-if="pending">
    Загрузка студентов...
```

</p>

В Nuxt для этого используются pending у useAsyncData, useFetch и связанных composables.

### Для улучшения UX можно показывать

- spinner;
- skeleton;
- временную заглушку;
- текст загрузки.
2. Success

Данные успешно получены.
```vue
<ul v-else-if="students?.length">
    <li
        v-for="student in students"
        :key="student.ISU"
    >
        {{ student.name }}
    </li>
```

</ul>

3. Empty State

Запрос завершился успешно, но данных нет.

Это не ошибка. Например, поиск студентов по фильтру не дал результатов.
```vue
<p v-else-if="students?.length === 0">
    Студенты не найдены.
```

</p>

4. Error

Запрос завершился ошибкой.
```vue
<p v-if="error">
    Не удалось загрузить студентов.
```

</p>

```vue
<button v-if="error" @click="refresh()">
    Повторить
```

</button>

### Важно разделять типы ошибок

- сеть недоступна;
- backend вернул 500;
- пользователь не авторизован;
- доступ запрещён;
- ресурс не найден;
- сервер вернул ошибку валидации.
5. Not Found

Состояние отсутствующего ресурса или маршрута.

### Например

- пользователь открыл /students/999999;
- студент с таким ИСУ отсутствует;
- маршрут вообще не существует.
Для этих случаев обычно используется HTTP 404.
### Основные HTTP-статусы

| Код | Значение | Когда использовать |
| --- | --- | --- |
| 200 | OK | Успешный запрос |
| 201 | Created | Ресурс создан |
| 204 | No Content | Операция успешна, тело ответа отсутствует |
| 301 / 302 | Redirect | Перенаправление |
| 304 | Not Modified | Используется сохранённый кеш |
| 400 | Bad Request | Некорректный запрос |
| 401 | Unauthorized | Нет действительной аутентификации |
| 403 | Forbidden | Нет прав на операцию |
| 404 | Not Found | Ресурс или маршрут не найден |
| 409 | Conflict | Конфликт состояния |
| 422 | Unprocessable Content | Данные не проходят проверку |
| 429 | Too Many Requests | Слишком много запросов |
| 500 | Internal Server Error | Внутренняя ошибка сервера |
| 502 | Bad Gateway | Ошибка ответа вышестоящего сервера |
| 503 | Service Unavailable | Сервис временно недоступен |
| 504 | Gateway Timeout | Таймаут при обращении к вышестоящему серверу |

Важно: 401 и 403 не взаимозаменяемы. 401 означает проблему аутентификации, 403 — что сервер понял, кто обращается, но запрещает действие.

```vue
<script setup lang="ts">
const { data, pending, error, refresh } =
    await useAsyncData(
        "students",

    );
```

</script>

```vue
<template>
    <section>
        <h1>Студенты</h1>

            Загрузка студентов...
```

### Как обрабатывать 404 в Nuxt?

### Например, если студент не найден

```text
if (error.value?.statusCode === 404) {
    throw createError({
        statusCode: 404,
        statusMessage: "Студент не найден"
    });
}
```

Nuxt переключит приложение на соответствующий экран ошибки.

Для неизвестных маршрутов также должна отображаться страница 404.
### Почему важно не превращать любую ошибку в 404?

Допустим, Java backend временно недоступен и Nuxt не может получить карточку студента.

Это не означает, что студент не существует.

### Возможны

- 503 — сервис недоступен;
- 504 — таймаут;
- 500 — внутренняя ошибка;
- 404 — студент действительно не найден.
Если все ошибки преобразовывать в 404, пользователь будет получать ложную информацию.
### Как это реализовано в лабораторной?

### В проекте используются

- pending и error у useAsyncData;
- LoadingIndicator.vue;
- ErrorMessage.vue;
- app/error.vue;
- 404 для отсутствующего маршрута и студента;
- повторный запрос через refresh();
- нормализация ошибок Java API.
На странице студента отдельно проверяется статус 404. При этом недоступность backend не должна маскироваться под отсутствие студента.

Также важен ответ 204 No Content: при удалении студента Java может вернуть успешный статус без тела. В таком случае нельзя безусловно вызывать response.json(), потому что тела нет.

Кратко для защиты: приложение должно явно обрабатывать Loading, Success, Empty, Error и Not Found. HTTP-статусы позволяют различать причины: 401 — не авторизован, 403 — нет прав, 404 — ресурс отсутствует, 5xx — проблема сервера. В нашей лабораторной эти состояния отображаются компонентами загрузки и ошибок, а для отсутствующего студента используется 404.
