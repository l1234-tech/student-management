## Теория 1. Проблема N+1

N+1 возникает, когда сначала выполняется один запрос для списка родительских сущностей, а затем для каждой сущности отдельный запрос за связанной коллекцией. Например, один SELECT загружает N групп, а обращение к `group.students` в цикле запускает ещё N запросов. Итого примерно 1 + N запросов.

Это не всегда буквально N запросов — зависит от fetch strategy, кэша и размера коллекции, — но риск растёт с числом родителей. Решение выбирают по фактическому запросу и объёму данных: join fetch, EntityGraph, batch fetching или DTO-проекция. Один огромный join тоже может размножить строки, особенно при нескольких коллекциях.

## Теория 2. Проверка JWT

API не должно доверять claims только потому, что токен выглядит как Base64URL JSON. Нужно проверять криптографическую подпись доверенным ключом, допустимый алгоритм, срок действия (exp), при необходимости not-before (nbf), issuer, audience и другие ожидаемые claims. Нужно также понимать, как система отзывает/ограничивает токены, если это предусмотрено архитектурой.

Подписанный JWT обычно не зашифрован: содержимое можно прочитать, поэтому секреты туда не помещают. Проверка подписи гарантирует целостность, но авторизация по ролям всё равно нужна отдельно. Принимающий сервис должен ограничить набор допустимых алгоритмов и не позволять токену самому диктовать недоверенный алгоритм проверки.

## Практика. JPA-связь Student → StudyGroup (many-to-one)

```java
@Entity
public class Student {
    @Id
    @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "study_group_id", nullable = false)
    private StudyGroup studyGroup;
}

@Entity
public class StudyGroup {
    @Id
    @GeneratedValue
    private Long id;

    @Column(nullable = false, unique = true)
    private String name;
}
```

У каждого студента есть одна группа, но у группы может быть много студентов — это Many-to-One со стороны Student. `@JoinColumn` задаёт внешний ключ в таблице студента. Если нужна навигация от группы к студентам, можно добавить `@OneToMany(mappedBy = "studyGroup")`, но для условия «студент принадлежит одной группе» достаточно связи со стороны Student. Имена/типы ID нужно согласовать с фактической схемой проекта.
