# Рубежка №1 — билет 29: точные условия и подробные решения

## Теоретический вопрос 57 — условие из файла

> Почему запрос списка групп с обращением к group.students в цикле может вызвать проблему N+1? Объясните, как число SQL-запросов растёт при увеличении числа групп.

### Подробный ответ

Проблема N+1 возникает, когда сначала выполняется один запрос для получения N объектов, а затем для каждого объекта ORM выполняет отдельный запрос для связанной коллекции. Например, один запрос загружает все учебные группы; обращение к `group.students` в цикле может спровоцировать отдельную загрузку студентов для каждой группы.

Если загружается одна группа — это может выглядеть незаметно. Для 20 групп потенциально получится один SQL-запрос на список групп плюс ещё 20 запросов коллекций, то есть около 21 запроса вместо одного или нескольких продуманно сгруппированных запросов. Точное количество зависит от настройки загрузки, кеша и ORM, но принцип роста количества обращений остаётся.

Проблема ухудшает задержку из-за множества round trips, даже если каждый отдельный запрос быстрый. Её диагностируют по SQL-логам и метрикам; решение выбирают под реальный запрос, размер коллекций и способ выдачи данных.

## Теоретический вопрос 58 — условие из файла

> Какие проверки обязан выполнить API перед принятием JWT? Зачем проверять подпись, ожидаемый алгоритм, срок действия, issuer и audience, а не доверять содержимому токена?

### Подробный ответ

JWT нельзя принимать только потому, что его можно декодировать. Декодирование заголовка и payload не доказывает, что токен выпущен доверенной стороной или не изменён.

Проверки включают:
1. **Подпись** — подтвердить целостность и происхождение токена подходящим ключом.
2. **Алгоритм** — разрешать только ожидаемый и поддерживаемый алгоритм; нельзя слепо доверять алгоритму из недоверенного токена.
3. **Срок действия (`exp`)** — отклонить истёкший токен; при применимости проверить `nbf`.
4. **Issuer (`iss`)** — удостовериться, что токен выпустил ожидаемый издатель.
5. **Audience (`aud`)** — удостовериться, что токен предназначен этому API.
6. При необходимости проверить subject, scopes/roles и прочие claims согласно контракту приложения.

Если не проверить подпись, пользователь может подделать payload; если не проверять срок — истёкший токен будет принят; если игнорировать issuer или audience — токен от другого сервиса может быть принят не по назначению. Конкретная библиотека и политика API определяют детали, но содержимому неподтверждённого токена доверять нельзя.

## Практическое задание 29 — условие из файла

> На Java/JPA объявите фрагменты двух сущностей Student и StudyGroup так, чтобы студент принадлежал одной группе.

### Решение

```java
import jakarta.persistence.*;

@Entity
public class StudyGroup {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    // При необходимости обратная связь:
    // @OneToMany(mappedBy = "studyGroup")
    // private List<Student> students;
}

@Entity
public class Student {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private Long isuId;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "study_group_id", nullable = false)
    private StudyGroup studyGroup;
}
```

### Подробный разбор

- `@Entity` помечает классы как JPA-сущности.
- `@Id` определяет первичный ключ; `@GeneratedValue` поручает генерацию идентификатора провайдеру/БД в соответствии со стратегией.
- `@ManyToOne` на Student означает, что многие студенты могут принадлежать одной учебной группе.
- `@JoinColumn` задаёт внешний ключ `study_group_id` в таблице студента.
- `optional = false` и `nullable = false` показывают, что по модели принадлежность обязательна.

По условию достаточно связи со стороны Student. Если нужна навигация от группы к студентам, можно добавить `@OneToMany(mappedBy = "studyGroup")`, но надо учитывать загрузку коллекции, JSON-сериализацию и риск N+1.
