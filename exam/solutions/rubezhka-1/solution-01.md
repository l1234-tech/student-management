# Рубежка №1 — билет 1: условия и подробные решения

В этом файле сначала приведены **точные формулировки заданий из PDF «Рубежка №1.pdf»**, затем — подробные ответы и разбор практики.

## Теоретический вопрос 1 — условие из файла

> Почему интернет, веб, сайт, веб-приложение и API не являются синонимами? Объясните различия через участников и цель взаимодействия.

### Подробное решение

Эти понятия относятся к разным уровням системы.

1. **Интернет** — глобальная инфраструктура взаимосвязанных сетей, которая позволяет устройствам обмениваться данными по согласованным протоколам. По интернету работают не только сайты, но и электронная почта, голосовая связь, мессенджеры и другие сервисы.
2. **Веб (World Wide Web, WWW)** — один из сервисов, работающих поверх интернета. Веб-ресурсы обычно адресуются URL, а браузер и сервер обмениваются сообщениями по HTTP или HTTPS.
3. **Сайт** — набор связанных страниц и ресурсов, доступных по определённому домену или группе адресов. Сайт может быть преимущественно информационным.
4. **Веб-приложение** — программная система, в которой пользователь выполняет действия: входит в аккаунт, ищет записи, заполняет формы, создаёт или редактирует данные. Оно включает интерфейс и прикладную логику, а часто — backend и базу данных.
5. **API (Application Programming Interface)** — формализованный контракт, по которому одна программа взаимодействует с другой. В веб-приложении frontend может отправить запрос к API и получить JSON. API не обязательно предназначено непосредственно для человека и не обязано иметь визуальный интерфейс.

**Участники взаимодействия:** пользователь взаимодействует с интерфейсом сайта или веб-приложения; браузер обменивается HTTP-сообщениями с сервером; frontend и backend взаимодействуют через API; сервер может обращаться к базе данных.

**Пример:** в системе управления студентами браузер показывает страницу с таблицей. JavaScript запрашивает `GET /api/students`, backend получает данные и возвращает JSON. Интернет обеспечивает передачу данных, веб — способ доступа к ресурсу, приложение реализует пользовательский сценарий, а API задаёт контракт между компонентами.

Частая ошибка — говорить, что API и сайт одно и то же. Сайт — то, что обычно видит пользователь; API — интерфейс программного взаимодействия, который может обслуживать этот сайт и другие клиенты.

## Теоретический вопрос 2 — условие из файла

> Почему GET, POST, PUT, PATCH и DELETE не следует считать взаимозаменяемыми? Сопоставьте их с CRUD и поясните, чем семантика HTTP-метода отличается от конкретной бизнес-операции.

### Подробное решение

**CRUD** — четыре базовые операции над данными: Create (создание), Read (чтение), Update (изменение), Delete (удаление). HTTP-метод сообщает серверу семантику запроса, но не диктует всю внутреннюю бизнес-логику.

| HTTP-метод | Типичное назначение | Связь с CRUD | Важное свойство |
|---|---|---|---|
| `GET` | Получить ресурс или список | Read | Safe: не должен запрашивать изменение состояния |
| `POST` | Создать ресурс или запустить операцию | Обычно Create, но не только | Не гарантирует идемпотентность |
| `PUT` | Создать/полностью заменить представление ресурса по известному URI | Обычно Update | Идемпотентен по семантике |
| `PATCH` | Изменить часть ресурса | Update | Идемпотентность зависит от конкретной операции |
| `DELETE` | Удалить ресурс | Delete | Идемпотентен по эффекту на целевое состояние |

**Safe (безопасный)** означает, что клиент не просит изменить состояние ресурса. Сервер может вести журналы и статистику, но смысл GET не должен состоять в изменении данных. Поэтому нельзя проектировать удаление как `GET /students/42/delete`.

**Идемпотентность** означает: многократное выполнение одинакового запроса приводит к тому же целевому состоянию, что и однократное. Например, повторный `PUT /students/42` с одним и тем же представлением оставляет студента в том же состоянии. Повторный POST создания может создать две записи, если сервер не реализовал защиту от дублей или ключ идемпотентности.

CRUD и HTTP — не одно и то же. Например, POST может инициировать отправку письма или запуск отчёта, а PATCH может обновить только группу студента. Метод задаёт протокольный смысл, а конкретное действие определяется контрактом API.

## Практическое задание 1 — условие из файла

> Запишите сырой HTTP/1.1-запрос, который получает студента с ИСУ ID 42 по адресу https://university.example/api/students/42. Укажите метод, путь, Host и Accept для JSON. Записывать TCP/TLS не требуется.

### Решение

```http
GET /api/students/42 HTTP/1.1
Host: university.example
Accept: application/json
```

### Разбор запроса

- `GET` — метод чтения: клиент запрашивает существующий ресурс, не меняя его.
- `/api/students/42` — путь в URL. В нём `/api/students` обозначает коллекцию студентов, а `42` — идентификатор конкретной записи.
- `HTTP/1.1` — версия протокола в стартовой строке.
- `Host: university.example` — обязательный для HTTP/1.1 заголовок, указывающий имя хоста назначения.
- `Accept: application/json` — сообщает серверу, что клиент ожидает представление в формате JSON.

В задании указан HTTPS, но требуется записать только HTTP-запрос. Поэтому TCP-соединение и TLS-handshake описывать не нужно: они являются нижележащими этапами передачи, а не строками этого фрагмента HTTP.

**Что проверить на защите:** путь не должен включать схему `https://` и домен; они отражены отдельно в `Host`. Не нужно добавлять тело запроса для обычного GET в этом задании.
