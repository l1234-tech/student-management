# Рубежка №1 — билет 1: точные условия и подробные решения

## Теоретический вопрос 1 — условие из файла

> Почему интернет, веб, сайт, веб-приложение и API не являются синонимами? Объясните различия через участников и цель взаимодействия.

### Подробный ответ

Эти понятия относятся к разным уровням, поэтому заменять одно другим некорректно.

- **Интернет** — инфраструктура взаимосвязанных сетей и протоколов, позволяющая устройствам обмениваться данными. На ней работают веб, электронная почта, мессенджеры и другие сервисы.
- **Веб (WWW)** — сервис поверх интернета: ресурсы связываются URL, а браузер и сервер обычно обмениваются сообщениями по HTTP/HTTPS.
- **Сайт** — совокупность связанных страниц и ресурсов, доступных по адресу. Сайт может быть информационным и почти не иметь интерактивной логики.
- **Веб-приложение** — программа с интерфейсом и логикой, в которой пользователь выполняет действия: ищет, создаёт, редактирует или удаляет записи.
- **API** — контракт программного взаимодействия. Например, frontend делает запрос к backend и получает JSON. API может обслуживать браузер, мобильное приложение и другие сервисы и не обязано иметь визуальный интерфейс.

**Ответ через участников и цель:** пользователь взаимодействует с интерфейсом; браузер взаимодействует с веб-сервером через HTTP; frontend взаимодействует с backend через API; backend может читать и изменять базу данных. Интернет доставляет данные, веб даёт механизм доступа к ресурсам, приложение реализует сценарий пользователя, а API определяет формат и правила обмена между программами.

Пример: браузер отображает список студентов. JavaScript вызывает `GET /api/students`, backend читает данные и возвращает JSON. Это не означает, что API и сайт — одно и то же: сайт/приложение отображает информацию человеку, API предоставляет интерфейс для программ.

## Теоретический вопрос 2 — условие из файла

> Почему GET, POST, PUT, PATCH и DELETE не следует считать взаимозаменяемыми? Сопоставьте их с CRUD и поясните, чем семантика HTTP-метода отличается от конкретной бизнес-операции.

### Подробный ответ

CRUD — Create, Read, Update, Delete: создание, чтение, изменение и удаление данных. HTTP-метод задаёт семантику запроса, а бизнес-логика приложения определяет конкретное действие.

| Метод | Типичное назначение | Связь с CRUD | Особенности |
|---|---|---|---|
| GET | Прочитать ресурс или список | Read | Safe: не должен запрашивать изменение состояния |
| POST | Создать ресурс или запустить операцию | Часто Create | Не гарантирует идемпотентность |
| PUT | Создать или полностью заменить представление ресурса по известному URI | Часто Update | Идемпотентен по семантике |
| PATCH | Изменить часть ресурса | Update | Идемпотентность зависит от операции |
| DELETE | Удалить ресурс | Delete | Идемпотентен по эффекту на целевое состояние |

**Safe** означает, что клиент не просит метод изменить состояние ресурса. Сервер всё ещё может вести логи и метрики; главное — смысл GET не должен быть «удалить» или «изменить» запись.

**Идемпотентность** означает, что повторение одного и того же запроса имеет тот же целевой эффект, что и однократное выполнение. Повторный PUT с теми же данными оставляет ресурс в том же состоянии. Повторный POST создания может добавить дубликат, если сервер специально не предотвращает это. У DELETE ответы при первом и повторном вызовах могут различаться, но желаемое состояние «ресурс удалён» остаётся тем же.

CRUD — классификация действий с данными; HTTP-метод — контракт протокола. POST, например, может не только создать запись, но и инициировать бизнес-операцию вроде запуска отчёта.

## Практическое задание 1 — условие из файла

> Запишите сырой HTTP/1.1-запрос, который получает студента с ИСУ ID 42 по адресу https://university.example/api/students/42. Укажите метод, путь, Host и Accept для JSON. Записывать TCP/TLS не требуется.

### Решение

```http
GET /api/students/42 HTTP/1.1
Host: university.example
Accept: application/json
```

### Подробный разбор

- `GET` — чтение существующего ресурса.
- `/api/students/42` — путь; `42` — идентификатор студента. Схему и домен сюда не включают.
- `HTTP/1.1` — версия протокола.
- `Host` — имя сервера назначения, обязательное в HTTP/1.1.
- `Accept: application/json` — клиент предпочитает JSON в ответе.

В условии сказано не записывать TCP/TLS, поэтому не нужно описывать установление соединения или TLS-handshake. Сам HTTP-запрос состоит из стартовой строки и заголовков; пустая строка отделила бы заголовки от тела, но у данного GET тела нет.

**Типичная ошибка:** писать `GET https://university.example/api/students/42 HTTP/1.1`. В форме origin request-target для такого запроса указывается путь, а хост передаётся отдельно в `Host`.
