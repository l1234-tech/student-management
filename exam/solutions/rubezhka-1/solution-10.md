# Рубежка №1 — билет 10: точные условия и подробные решения

## Теоретический вопрос 19 — условие из файла

> Почему приложение из одного большого script.js труднее развивать, чем набор ES-модулей с явными зависимостями? Раскройте роль import, export и отдельной области видимости.

### Подробный ответ

В одном большом `script.js` часто смешиваются обработчики интерфейса, валидация, HTTP-запросы, бизнес-правила и отрисовка. Это повышает связанность: изменение в одном месте может неожиданно повлиять на другое, код труднее тестировать, переиспользовать и искать в нём ошибки.

ES-модули позволяют делить программу на части с понятной ответственностью. `export` открывает переменные или функции как публичный интерфейс модуля; `import` явно объявляет, что другому модулю нужно. Каждая модульная область имеет собственную область видимости, поэтому внутренние объявления не становятся глобальными автоматически.

Например, можно выделить `student-api.js` для `fetch`, `validation.js` для проверок формы и `render-students.js` для изменения DOM. Это делает зависимости явными, упрощает изолированное тестирование и повторное использование.

**Прямой ответ:** модули уменьшают случайное смешивание обязанностей и делают зависимости видимыми. Но дробление на множество маленьких файлов без логической причины тоже ухудшает поддержку.

## Теоретический вопрос 20 — условие из файла

> Какие данные стоит передавать в заголовках HTTP-запроса, а какие — в теле? Как взаимодействуют Content-Type, JSON-сериализация и чтение ответа?

### Подробный ответ

Заголовки описывают метаданные запроса и условия обработки:
- `Content-Type` — формат тела запроса;
- `Accept` — ожидаемый формат ответа;
- `Authorization` — credentials/токен авторизации;
- `Cookie` — подходящие cookies;
- `Cache-Control` — правила кеширования.

Тело содержит передаваемые данные, например JSON-объект нового студента. В JavaScript `JSON.stringify(student)` сериализует объект в текст JSON. Заголовок `Content-Type: application/json` сообщает серверу, что этот текст нужно разобрать как JSON. Для JSON-ответа клиент обычно вызывает `await response.json()`.

Пример:

```js
const response = await fetch("/api/students", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Accept": "application/json"
  },
  body: JSON.stringify({ isu_id: 42, group: "M3301" })
});

if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}

const student = await response.json();
```

Важно: `fetch` не отклоняет Promise только потому, что сервер вернул HTTP 400 или 500. Код проверяет `response.ok` отдельно. `Content-Type` не сериализует объект автоматически: сериализацию выполняет `JSON.stringify`.

## Практическое задание 10 — условие из файла

> Даны асинхронные функции loadStudents() и loadDormitories(), каждая возвращает Promise. Напишите async function loadPageData(), которая запускает их параллельно, ждёт оба результата и возвращает {students, dormitories}. Ошибки не подавляйте.

### Решение

```js
async function loadPageData() {
  const [students, dormitories] = await Promise.all([
    loadStudents(),
    loadDormitories()
  ]);

  return { students, dormitories };
}
```

### Подробный разбор

Обе функции вызываются при создании массива аргументов `Promise.all`; затем программа ожидает выполнения обоих Promise. Это позволяет ожиданиям идти параллельно, а не сначала ждать студентов и только после этого начинать запрос общежитий.

`Promise.all` возвращает массив результатов в том же порядке, в каком Promise были переданы, поэтому первый элемент — `students`, второй — `dormitories`. Если любой Promise отклонится, `Promise.all` тоже отклонится, а ошибка передастся вызывающему коду. Это соответствует условию «ошибки не подавляйте»: здесь нет пустого `catch` и не подставляется фиктивный результат.
