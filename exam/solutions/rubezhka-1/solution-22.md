# Рубежка №1 — билет 22: точные условия и подробные решения

## Теоретический вопрос 43 — условие из файла

> Как контейнер может внедрять значение даже в private-поле? Объясните, что происходит между обнаружением аннотации и получением готового экземпляра бина.

### Подробный ответ

Модификатор `private` ограничивает обычный доступ из кода других классов, но Java предоставляет механизмы reflection. Контейнер может обнаружить поле с аннотацией внедрения, сделать его доступным для рефлексивной операции в рамках разрешённых политикой Java доступа и записать значение зависимости.

Упрощённый жизненный цикл:
1. Spring обнаруживает класс и регистрирует описание bean (BeanDefinition).
2. Контейнер создаёт экземпляр класса.
3. BeanPostProcessor или связанная инфраструктура обработки внедрений анализирует поля/методы и внедряет зависимости.
4. Выполняются callback инициализации, например `@PostConstruct`.
5. После дальнейшей post-processing объект может быть возвращён как готовый бин, иногда через AOP-прокси.

Field injection удобен внешне, но зависимость не видна в публичном конструкторе, и объект нельзя полноценно использовать до внедрения. Поэтому для обязательных зависимостей часто выбирают constructor injection.

## Теоретический вопрос 44 — условие из файла

> Чем BeanDefinition отличается от готового бина? Какую работу выполняют BeanFactoryPostProcessor и BeanPostProcessor и почему порядок их применения важен?

### Подробный ответ

**BeanDefinition** — метаданные/описание того, как создать и настроить бин: класс или фабричный метод, scope, зависимости, свойства, lazy-init и другие параметры. **Bean** — фактический экземпляр объекта, созданный по этим метаданным и прошедший этапы жизненного цикла.

**BeanFactoryPostProcessor** работает с метаданными фабрики до создания обычных экземпляров бинов. Он может изменять BeanDefinition. **BeanPostProcessor** работает с уже созданными экземплярами до и после initialization callback; он может выполнить дополнительную обработку или вернуть обёртку-прокси. Они решают разные задачи и работают на разных этапах.

Порядок важен потому, что изменение BeanDefinition должно происходить до создания объекта, а post-processing самого объекта имеет смысл после его инстанцирования. Если конфигурация изменяется слишком поздно, некоторые бины уже могут быть созданы с прежними метаданными. Аналогично, прокси и другие пост-обработки должны корректно встроиться в жизненный цикл.

## Практическое задание 22 — условие из файла

> На Java/Spring MVC напишите @RestControllerAdvice с обработчиком StudentNotFoundException, возвращающим статус 404 и JSON с полем error. Считайте, что исключение существует, а Map.of доступен.

### Решение

```java
import java.util.Map;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(StudentNotFoundException.class)
    public ResponseEntity<Map<String, String>> handleStudentNotFound(
            StudentNotFoundException exception) {
        return ResponseEntity
            .status(HttpStatus.NOT_FOUND)
            .body(Map.of("error", "student_not_found"));
    }
}
```

### Подробный разбор

- `@RestControllerAdvice` делает класс общим обработчиком исключений REST-контроллеров и сериализует возвращаемое тело в JSON.
- `@ExceptionHandler(StudentNotFoundException.class)` связывает метод с конкретным типом исключения.
- `HttpStatus.NOT_FOUND` задаёт код 404.
- `Map.of("error", "student_not_found")` создаёт тело с требуемым полем.
- `ResponseEntity` позволяет явно управлять одновременно HTTP-статусом и телом ответа.

Таким образом, контроллеры и сервисы могут сигнализировать об отсутствии студента исключением, а единый обработчик формирует одинаковый API-ответ вместо копирования обработки 404 в каждом endpoint.
