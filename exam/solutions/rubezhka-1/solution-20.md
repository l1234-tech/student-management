# Рубежка №1 — билет 20: точные условия и подробные решения

## Теоретический вопрос 39 — условие из файла

> Как различаются WSGI и ASGI по контракту приложения и ожиданию сетевых операций? Почему ASGI подходит для асинхронного I/O и длительных соединений?

### Подробный ответ

WSGI — интерфейс между Python web-приложением и сервером, построенный вокруг синхронной модели запроса/ответа. ASGI — интерфейс, который поддерживает асинхронный обмен событиями и длительные соединения, включая WebSocket. Он позволяет приложению ожидать сетевые операции без обязательного удержания потока на всём протяжении ожидания.

ASGI лучше подходит для приложений, где много I/O-bound задач или нужны длительные соединения. Но ASGI не делает синхронную функцию асинхронной: блокирующий вызов внутри async-обработчика может задержать event loop. Контракт сервера, framework и конкретный код приложения должны соответствовать друг другу.

## Теоретический вопрос 40 — условие из файла

> Чем отличаются I/O-bound и CPU-bound задачи? Почему асинхронность способна улучшить обслуживание ожидающих запросов, но не ускоряет автоматически тяжёлые вычисления?

### Подробный ответ

I/O-bound задача проводит большую часть времени в ожидании внешней операции — сети, диска или базы данных. Асинхронный код может приостановить корутину во время ожидания и позволить event loop заниматься другими запросами. Так повышается эффективность при множестве одновременно ожидающих I/O-операций.

CPU-bound задача в основном выполняет вычисления: обработку массива, сжатие или тяжёлый алгоритм. `await` не сокращает количество вычислений; если CPU-код работает синхронно, он удерживает поток. Для ускорения CPU-bound задач могут потребоваться несколько процессов/ядер, оптимизированные нативные библиотеки или распределённые вычисления.

**Прямой ответ:** асинхронность повышает конкурентность ожидания I/O, а не магически ускоряет CPU-вычисления.

## Практическое задание 20 — условие из файла

> На Java/Spring напишите сервис StudentService, который получает StudentRepository через единственный конструктор. Пометьте сервис подходящей аннотацией. Добавьте метод get(id), вызывающий repository.findById(id). Предположите, что метод репозитория возвращает Optional<Student>.

### Решение

```java
@Service
public class StudentService {
    private final StudentRepository repository;

    public StudentService(StudentRepository repository) {
        this.repository = repository;
    }

    public Student get(long id) {
        return repository.findById(id)
            .orElseThrow(() -> new StudentNotFoundException(id));
    }
}
```

### Подробный разбор

- `@Service` сообщает Spring, что класс является компонентом бизнес-слоя и должен управляться контейнером.
- Единственный конструктор получает `StudentRepository`; Spring автоматически использует его для внедрения зависимости, поэтому `@Autowired` обычно не нужен.
- `findById(id)` возвращает `Optional<Student>`: это явно представляет два варианта — запись найдена или отсутствует.
- `orElseThrow` превращает пустой Optional в понятное исключение. В приложении exception handler должен преобразовать его в HTTP 404.

Условие допускает предположить готовый интерфейс репозитория; `StudentNotFoundException` также должен быть объявлен отдельно или уже существовать в проекте. Важно не возвращать `null` молча, если контракт сервиса ожидает студента.
