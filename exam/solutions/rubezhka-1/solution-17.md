## Теория 1. async def не гарантирует неблокирующий код

`async def` объявляет корутину, но если внутри вызвать блокирующую функцию, event loop не сможет переключиться на другие задачи до окончания этой функции. Например, `time.sleep(5)` блокирует поток. `await asyncio.sleep(5)` отдаёт управление event loop, позволяя выполнять другие корутины.

Аналогично, синхронный сетевой клиент или тяжёлое CPU-вычисление внутри async-обработчика могут блокировать выполнение. Асинхронность особенно полезна для I/O-bound задач, когда ожидание можно перекрыть работой над другими запросами.

## Теория 2. Воркеры и соединения к БД

У каждого процесса-воркера есть собственная память, объекты и обычно свой пул соединений. Если на каждом воркере пул может содержать до 15 соединений, то 4 воркера потенциально могут запросить до 4 × 15 = 60 соединений. Рост воркеров также увеличивает память и конкуренцию за CPU/БД. Реальный максимум зависит от настроек пула, ленивого создания соединений и нагрузки.

Количество воркеров нужно выбирать с учётом ресурсов и лимитов СУБД, а не просто максимизировать.

## Практика. asyncio.gather

```python
import asyncio

async def fetch_mock(delay):
    await asyncio.sleep(delay)
    return delay

async def main():
    results = await asyncio.gather(
        fetch_mock(1),
        fetch_mock(2)
    )
    print(results)

if __name__ == "__main__":
    asyncio.run(main())
```

Ожидаемый вывод: `[1, 2]`. Обе корутины запускаются через gather; общий результат возвращается в порядке аргументов, а не в порядке завершения. Общее время ожидания близко к 2 секундам, а не к 3, потому что ожидания перекрываются.

## Прямые теоретические ответы

**Прямой ответ на вопросы 33–34.** `async def` само по себе не делает код неблокирующим. Если корутина вызывает синхронный `time.sleep` или блокирующий драйвер, поток event loop остановится и другие корутины не получат возможность продолжаться. `await` полезен, когда ожидаемая операция действительно асинхронная и отдаёт управление циклу событий на время ожидания. Для CPU-bound вычислений может понадобиться отдельный процесс/worker или другой способ распараллеливания.

Каждый worker — отдельный процесс с собственной памятью и, часто, своим пулом соединений. Если есть 4 процесса и каждый может держать до 15 соединений, суммарный верхний предел может достигнуть 4 × 15 = 60 соединений к БД. Поэтому увеличение числа workers повышает способность обслуживать параллельные запросы, но одновременно увеличивает потребление памяти и возможную нагрузку на БД. Размер пулов следует согласовать с общим лимитом соединений БД и числом процессов.
