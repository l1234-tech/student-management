# Рубежка №1 — билет 17: точные условия и подробные решения

## Теоретический вопрос 33 — условие из файла

> Почему наличие async def в FastAPI не гарантирует неблокирующего поведения? Сравните результат вызова обычной блокирующей функции внутри async-обработчика с корректным await неблокирующей операции.

### Подробный ответ

`async def` объявляет coroutine-функцию, которая может приостанавливать выполнение на `await`. Но сама запись `async` не превращает вызовы внутри функции в асинхронные.

Если вызвать обычную блокирующую функцию, например `time.sleep(5)`, из async-обработчика, она занимает поток event loop на пять секунд. На этом потоке другие корутины в это время не смогут нормально продолжаться, поэтому задерживаются запросы, которые могли бы обслуживаться параллельно.

Корректный вариант для асинхронного ожидания — использовать неблокирующую операцию, например `await asyncio.sleep(5)` или async I/O-клиент. В момент ожидания корутина отдаёт управление циклу событий, а тот может выполнять другие корутины. Если библиотека только синхронная, её нельзя сделать неблокирующей простым добавлением `await`; может потребоваться потоковый пул или другая библиотека.

**Прямой ответ:** `async def` задаёт форму функции, но неблокирующее поведение зависит от вызываемых операций. Блокирующий код блокирует event loop; корректное `await` асинхронной операции позволяет обслуживать другие запросы во время ожидания.

## Теоретический вопрос 34 — условие из файла

> Почему увеличение числа воркеров увеличивает не только параллельность обработки, но и расход памяти и число соединений с базой? Объясните на примере пула из 15 соединений на процесс.

### Подробный ответ

Worker — отдельный процесс или поток, который обрабатывает нагрузку; для процесса обычно есть отдельное адресное пространство и собственные объекты приложения. При добавлении процессов растут потребление памяти, число копий конфигураций/кэшей, расход ресурсов ОС и потенциальное количество соединений к базе.

Если каждый процесс может создать пул из 15 соединений, то при (W) процессах верхний предел при полном использовании пулов приблизительно равен (15W). Например, 4 процесса могут претендовать на 60 соединений. Это может превысить лимит базы и ухудшить работу других сервисов.

Увеличение workers полезно для параллельной обработки, но это не бесплатное ускорение. Нужно согласовывать число процессов и размер пула с лимитами СУБД, памятью и характером нагрузки. Если соединения создаются лениво или пул не всегда заполнен, фактическое число будет ниже верхнего предела.

## Практическое задание 17 — условие из файла

> На Python/asyncio напишите корутину fetch_mock(delay), ожидающую asyncio.sleep(delay) и возвращающую delay. Напишите main(), которая параллельно вызывает её для 1 и 2 секунд через gather и печатает оба результата. Покажите запуск.

### Решение

```python
import asyncio

async def fetch_mock(delay):
    await asyncio.sleep(delay)
    return delay

async def main():
    results = await asyncio.gather(
        fetch_mock(1),
        fetch_mock(2)
    )
    print(results)

if __name__ == "__main__":
    asyncio.run(main())
```

Ожидаемый вывод:

```text
[1, 2]
```

### Подробный разбор

- `async def fetch_mock` объявляет корутину.
- `await asyncio.sleep(delay)` имитирует неблокирующее ожидание.
- `asyncio.gather` ожидает завершения обеих корутин конкурентно.
- Результаты возвращаются в порядке переданных awaitable-объектов, а не по времени завершения, поэтому первым элементом будет `1`, вторым — `2`.
- `asyncio.run(main())` создаёт и запускает event loop для выполнения главной корутины.

Ожидания перекрываются, поэтому общее время будет близко к двум секундам, а не к трём, если нет дополнительных задержек. Это пример улучшения обслуживания I/O-bound задач, а не ускорения CPU-вычислений.
