# Рубежка №1 — билет 27: точные условия и подробные решения

## Теоретический вопрос 53 — условие из файла

> Почему аутентификация и авторизация должны быть отдельными проверками? Объясните, как роли USER и ADMIN влияют на чтение и изменение записей студентов.

### Подробный ответ

**Аутентификация** устанавливает, кто обращается к системе: например, пользователь предъявляет пароль или JWT, и сервер проверяет credentials. **Авторизация** проверяет, разрешено ли уже установленному субъекту выполнить конкретное действие над ресурсом.

В системе студентов можно разрешить USER читать `GET /students/**`, но запретить ему создавать, удалять или менять записи; роль ADMIN может иметь разрешение на изменение. Сам факт, что токен действительный и пользователь вошёл в систему, не означает, что у него есть любые полномочия.

Разделение важно для безопасности: правильно аутентифицированный пользователь всё ещё может быть неавторизован на операцию. Также нужно учитывать объектный уровень доступа — даже разрешённая роль не должна произвольно изменять чужие данные, если бизнес-правила ограничивают область доступа.

## Теоретический вопрос 54 — условие из файла

> Как связаны JPA, Hibernate и Spring Data JPA и почему ORM не означает отсутствия SQL? Объясните путь от обращения к репозиторию до исполнения запроса к базе.

### Подробный ответ

**JPA** — спецификация Java для ORM и управления сущностями; она описывает API и правила, но сама по себе не является конкретным ORM-провайдером. **Hibernate** — одна из реализаций JPA, которая отображает сущности на таблицы и генерирует/исполняет SQL. **Spring Data JPA** — уровень Spring, который упрощает создание репозиториев, предоставляет типовые операции и генерацию запросов по соглашениям.

Типичный путь: сервис вызывает метод репозитория → Spring Data реализует вызов и использует EntityManager → persistence context и ORM определяют сущности и запрос → Hibernate генерирует SQL и передаёт его JDBC-драйверу → драйвер обращается к БД → результат преобразуется обратно в managed entities/значения → сервис или DTO-mapping формирует ответ.

ORM не отменяет SQL: он берёт на себя отображение объектов на таблицы и генерацию запросов. Чтобы понимать производительность, всё равно важно проверять, какие SQL-запросы реально выполняются.

## Практическое задание 27 — условие из файла

> На JavaScript напишите async function updateProfile(profile, csrfToken), отправляющую POST /profile с JSON-телом и защитой от CSRF (сервер ждёт токен в заголовке X-CSRF-Token, аутентификация — по cookie). Если HTTP-ответ неуспешен, выбрасывайте Error.

### Решение

```js
async function updateProfile(profile, csrfToken) {
  const response = await fetch("/profile", {
    method: "POST",
    credentials: "same-origin",
    headers: {
      "Content-Type": "application/json",
      "Accept": "application/json",
      "X-CSRF-Token": csrfToken
    },
    body: JSON.stringify(profile)
  });

  if (!response.ok) {
    throw new Error(`HTTP error: ${response.status}`);
  }

  return response;
}
```

### Подробный разбор

- POST отправляет изменение профиля на `/profile`.
- `JSON.stringify(profile)` сериализует объект, а `Content-Type` описывает тело.
- `X-CSRF-Token` передаёт CSRF-токен именно в заголовке, как требует условие.
- `credentials: "same-origin"` явно сохраняет отправку same-origin cookies; аутентификация в задании основана на cookie.
- `response.ok` необходимо проверять явно, потому что `fetch` не бросает исключение из-за обычного HTTP 4xx/5xx.
- При ошибке выбрасываем `Error` с кодом статуса. На успехе возвращаем Response, поскольку формат успешного тела в условии не указан.

CSRF-токен должен быть проверен сервером и привязан к корректному контексту сессии/запроса; просто отправить заголовок недостаточно, если backend не выполняет проверку.
