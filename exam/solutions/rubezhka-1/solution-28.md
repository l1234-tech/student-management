# Рубежка №1 — билет 28: точные условия и подробные решения

## Теоретический вопрос 55 — условие из файла

> Почему HTTPS, JWT, проверки ролей и серверная валидация решают разные проблемы? Объясните, какая уязвимость остаётся, если внедрить только один из перечисленных механизмов.

### Подробный ответ

Эти механизмы взаимодополняют друг друга:
- **HTTPS/TLS** защищает канал передачи от перехвата и незаметной модификации данных и помогает клиенту убедиться в подлинности сервера.
- **JWT** — формат токена с claims. При корректной проверке он позволяет передавать информацию об аутентификации между запросами, но сам по себе не гарантирует, что токен действителен или что субъекту разрешена операция.
- **Проверки ролей/авторизация** ограничивают доступ к операциям и ресурсам, например USER может читать студентов, а ADMIN — изменять.
- **Серверная валидация** проверяет форму и допустимость данных, например тип ИСУ, обязательную группу, диапазон и бизнес-ограничения.

Если сделать только HTTPS, любой аутентифицированный или неаутентифицированный клиент всё равно может попытаться вызвать запрещённый endpoint или отправить некорректные данные. Если проверять JWT, но не проверять роли, обычный пользователь может получить доступ к административной операции. Если проверять роль, но не валидировать тело, можно записать некорректные данные. Если валидировать запрос, но не проверять полномочия, пользователь может изменить чужую запись.

## Теоретический вопрос 56 — условие из файла

> В чём роли UserDetailsService, PasswordEncoder и AuthenticationProvider при входе по логину и паролю? Почему недостаточно просто сравнить две строки из формы и базы?

### Подробный ответ

- **UserDetailsService** загружает сведения о пользователе по username: идентификатор, хеш пароля и authorities/roles.
- **PasswordEncoder** проверяет пароль и отвечает за корректную схему хранения: например, `matches(raw, storedHash)`, а при регистрации — `encode(raw)`.
- **AuthenticationProvider** реализует конкретный механизм проверки credentials. В стандартном сценарии username/password он координирует загрузку пользователя, проверку пароля и формирование Authentication.

Нельзя хранить и сравнивать пароль в открытом виде: утечка базы сразу раскроет пароли. Нельзя просто сравнить введённую строку с сохранённым хешем, поскольку алгоритмы парольного хеширования используют соль и параметры стоимости. Проверка выполняется специализированным PasswordEncoder.

После успешной аутентификации система создаёт Authentication с идентичностью пользователя и полномочиями; затем авторизация решает, что пользователь может делать.

## Практическое задание 28 — условие из файла

> На Java/Spring Data JPA напишите сервисный метод changeGroup(long id, String group), меняющий группу студента в базе. Объясните, нужен ли в нём вызов save.

### Решение

```java
@Service
public class StudentService {
    private final StudentRepository repository;

    public StudentService(StudentRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public void changeGroup(long id, String group) {
        Student student = repository.findById(id)
            .orElseThrow(() -> new StudentNotFoundException(id));

        student.setGroup(group);
    }
}
```

### Нужно ли вызывать save?

Если сущность загружена из репозитория внутри активной транзакции, она обычно становится managed — отслеживаемой persistence context. Изменение поля `student.setGroup(group)` обнаруживается механизмом dirty checking, и ORM синхронизирует изменение с БД при flush/commit. Поэтому **в этом случае явный вызов `save(student)` обычно не требуется**.

Транзакция важна: она удерживает сущность в управляемом состоянии до фиксации изменений. Если сущность detached, транзакция отсутствует или код работает по другой модели хранения, поведение будет отличаться и сохранение может потребоваться. Также нужно валидировать новое значение группы и проверить, что такая группа допустима.
