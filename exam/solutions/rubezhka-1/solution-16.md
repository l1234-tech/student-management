# Рубежка №1 — билет 16: точные условия и подробные решения

## Теоретический вопрос 31 — условие из файла

> Как возникает race condition при одновременной записи нескольких потоков в один JSON-файл? Почему последовательность «прочитать — изменить — записать» опасна без координации?

### Подробный ответ

Race condition (состояние гонки) возникает, когда итог зависит от непредсказуемого чередования операций нескольких потоков. Запись в JSON-файл часто состоит из нескольких шагов: прочитать файл → разобрать JSON → изменить структуру → сериализовать → записать. Без синхронизации эта последовательность не является одной атомарной операцией.

Например, в файле хранится счётчик 10. Поток A читает 10, поток B тоже читает 10. Оба увеличивают локальную копию до 11, затем оба записывают 11. Ожидаемое значение после двух инкрементов — 12, а фактическое — 11: одна операция потеряна. При записи полного файла возможно и повреждение/перезапись изменений другого потока.

Для общего файла нужен механизм координации: блокировка вокруг всей операции read-modify-write, отдельный процесс-владелец хранилища, транзакционная база данных или атомарный протокол записи. Простая блокировка только на этапе `write` недостаточна, потому что устаревшее состояние могло быть прочитано ещё до захвата блокировки.

## Теоретический вопрос 32 — условие из файла

> Почему данные запроса нельзя хранить в обычной глобальной переменной серверного приложения? Объясните понятие request context и как фреймворки изолируют информацию разных клиентов.

### Подробный ответ

Обычная глобальная переменная принадлежит процессу и может быть доступна всем обработчикам, работающим в нём. При параллельной обработке два запроса могут одновременно обращаться к одной переменной, поэтому данные одного пользователя могут быть перезаписаны данными другого. Это опасно для пользователя, токена, текущего языка, параметров запроса и других контекстных данных.

Request context — набор данных, относящихся к конкретному запросу: сам запрос, заголовки, параметры, текущий пользователь, trace ID и подобная информация. Веб-фреймворки связывают этот контекст с текущим выполнением запроса — например, через контекстные объекты, thread-local/context-local механизмы или аргументы функции — и очищают/освобождают его после обработки. Важно использовать поддерживаемый механизм framework, а не самодельную глобальную переменную.

Глобальная конфигурация, которая действительно одинакова для всех запросов и не меняется при их обработке, допустима. Проблема — не глобальность сама по себе, а хранение там изменяемого состояния отдельного запроса или пользователя.

## Практическое задание 16 — условие из файла

> На Python напишите пример с multiprocessing.Process: глобальный счётчик counter = 0 увеличивается в двух дочерних процессах, родитель после join() печатает своё значение. Что напечатает родитель и почему?

### Решение

```python
from multiprocessing import Process

counter = 0

def increment():
    global counter
    counter += 1
    print("Дочерний процесс:", counter)

if __name__ == "__main__":
    processes = [Process(target=increment) for _ in range(2)]

    for process in processes:
        process.start()

    for process in processes:
        process.join()

    print("Родительский процесс:", counter)
```

### Подробный разбор результата

В обычной модели `multiprocessing` дочерние процессы имеют отдельные адресные пространства. Каждый получает свою копию исходного глобального значения `counter = 0`; инкремент в ребёнке меняет только его собственную память.

Поэтому каждый дочерний процесс обычно напечатает значение 1, а родитель после `join()` напечатает **0**. `join()` лишь ждёт завершения дочернего процесса; он не объединяет его память с памятью родителя.

Чтобы разделять счётчик, нужно явно использовать IPC/shared state, например `multiprocessing.Value` с блокировкой, `Manager` или очередь сообщений. Одна лишь глобальная переменная общего состояния между процессами не создаёт.
