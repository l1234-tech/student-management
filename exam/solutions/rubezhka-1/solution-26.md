# Рубежка №1 — билет 26: точные условия и подробные решения

## Теоретический вопрос 51 — условие из файла

> Почему в TLS применяются и асимметричные, и симметричные криптографические механизмы? Какую роль играет сертификат в установлении доверия к серверу?

### Подробный ответ

Асимметричная криптография использует пару ключей и помогает подтвердить идентичность сервера и выполнить/подтвердить согласование ключевого материала. Симметричная криптография использует общий сеансовый ключ и гораздо эффективнее для шифрования больших объёмов данных. Поэтому TLS применяет комбинацию механизмов: сертификат и криптографический handshake помогают установить доверенный защищённый канал, а дальнейший трафик защищается симметрическими алгоритмами.

Сертификат связывает доменное имя с публичным ключом и содержит подпись удостоверяющего центра. Клиент проверяет цепочку доверия, срок действия, соответствие имени хоста и другие необходимые условия. Это помогает убедиться, что соединение установлено с сервером, соответствующим указанному домену, а не с самозванцем. Сертификат не «шифрует сам по себе весь трафик» и не означает абсолютной безопасности приложения: серверная логика и авторизация остаются отдельными задачами.

## Теоретический вопрос 52 — условие из файла

> Для чего ORM нужен persistence context? Как он связан с идентичностью управляемого объекта, dirty checking и выполнением SQL при завершении транзакции?

### Подробный ответ

Persistence context — контекст отслеживания сущностей в ORM, который связывает идентификаторы записей с управляемыми объектами. В рамках одного контекста JPA обычно поддерживает уникальность управляемого экземпляра для конкретной сущности и её идентификатора. Когда сущность загружена, изменения её полей отслеживаются.

Dirty checking — механизм обнаружения изменений управляемой сущности по сравнению с её исходным состоянием. Во время flush ORM синхронизирует изменения с БД, формируя необходимые INSERT/UPDATE/DELETE. Flush может произойти до commit, при явном вызове или автоматически по правилам провайдера; при завершении транзакции изменения коммитятся либо откатываются. SQL не обязательно исполняется непосредственно в момент каждого setter-вызова.

Это уменьшает необходимость вручную обновлять каждую сущность, но работает для объектов, которые остаются managed внутри persistence context. Изменение detached-объекта автоматически не отслеживается тем же контекстом.

## Практическое задание 26 — условие из файла

> На Java/Spring Security напишите конфигурационный метод SecurityFilterChain, который требует HTTPS для всех запросов. TLS на сервере уже настроен.

### Решение

```java
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    return http
        .requiresChannel(channel -> channel
            .anyRequest()
            .requiresSecure())
        .build();
}
```

### Подробный разбор

`requiresChannel` задаёт требования к каналу для запросов, а `anyRequest().requiresSecure()` требует HTTPS для всех маршрутов. Если запрос пришёл по HTTP, Spring Security должен требовать защищённый канал; поведение редиректа зависит от версии и конфигурации.

TLS должен быть настроен на сервере или reverse proxy, как дано в условии. При работе за прокси необходимо доверенно настраивать forwarded headers: приложению нельзя принимать недоверенный клиентский заголовок за доказательство того, что исходное соединение было HTTPS. В существующем проекте это правило следует объединить с остальной конфигурацией SecurityFilterChain, а не случайно создавать конфликтующую вторую цепочку.
