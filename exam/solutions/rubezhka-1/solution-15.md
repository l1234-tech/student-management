# Рубежка №1 — билет 15: точные условия и подробные решения

## Теоретический вопрос 29 — условие из файла

> Сравните назначения Lock, RLock, Semaphore, Event и Queue. Почему Queue часто предпочтительнее общего изменяемого списка для передачи задач между потоками?

### Подробный ответ

- **Lock** — взаимное исключение: в критической секции одновременно работает только один поток.
- **RLock** — повторно захватываемая блокировка: один и тот же поток может захватить её несколько раз и должен столько же раз освободить.
- **Semaphore** — счётчик разрешений, ограничивает число потоков, одновременно использующих ресурс.
- **Event** — флаг для сигнализации: потоки могут ждать, пока другой поток установит событие.
- **Queue** — потокобезопасная очередь для передачи элементов между producers и consumers.

Queue часто лучше общего списка, потому что встроенно предоставляет координацию доступа, операции ожидания, а в вариантах вроде `queue.Queue` — удобный механизм блокирующего ожидания и учёта задач. При использовании списка разработчику пришлось бы вручную проектировать синхронизацию и безопасно координировать проверку «есть ли элемент» и извлечение.

## Теоретический вопрос 30 — условие из файла

> Почему Flask, Django REST Framework и FastAPI нельзя считать полноценной заменой HTTP-сервера в production? Разграничьте обязанности сервера, фреймворка и обработчика.

### Подробный ответ

Фреймворки помогают писать приложение, но в типичной production-схеме их используют вместе с серверным окружением:
- **HTTP/WSGI/ASGI-сервер** принимает сетевые подключения, разбирает HTTP на соответствующем уровне и передаёт запрос приложению; также может управлять процессами/потоками и соединениями.
- **Framework** предоставляет маршрутизацию, доступ к параметрам запроса, middleware, сериализацию/валидацию и обработку ошибок.
- **Handler/view/controller** — конкретная функция или метод маршрута, который выполняет бизнес-сценарий и формирует ответ.

Например, Uvicorn часто используется для ASGI-приложения FastAPI, а WSGI-сервер — для синхронного Flask-приложения. В production также могут применяться reverse proxy, TLS-терминация, ограничения размера/времени запроса, логирование и мониторинг.

**Прямой ответ:** Flask, DRF и FastAPI — framework/инструменты приложения, а не универсальная замена всей инфраструктуре production-сервера. При этом существуют режимы и инструменты разработки, позволяющие запустить приложение непосредственно; речь о разграничении ответственности и требованиях промышленного развёртывания.

## Практическое задание 15 — условие из файла

> На Python/FastAPI напишите POST /students, который принимает Pydantic-модель с полями isu_id: int и group: str, возвращает статус 201 и JSON созданного студента. При повторном ИСУ ID возвращайте 409. Считайте, что repo.exists(id) и repo.create(data) уже существуют.

### Решение

```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

class StudentCreate(BaseModel):
    isu_id: int
    group: str

@app.post("/students", status_code=201)
def create_student(data: StudentCreate):
    if repo.exists(data.isu_id):
        raise HTTPException(
            status_code=409,
            detail="student_already_exists"
        )

    student = repo.create(data)
    return student
```

### Подробный разбор

- Pydantic-модель описывает поля тела запроса; FastAPI разбирает JSON и валидирует поля по модели.
- `@app.post(..., status_code=201)` задаёт статус успешного создания.
- `repo.exists` проверяет, нет ли уже записи с таким ИСУ. При конфликте выбрасываем `HTTPException(409)`, соответствующий конфликту состояния ресурса.
- `repo.create(data)` сохраняет студента; возвращаемый объект FastAPI сериализует в HTTP-ответ.

Условие предполагает, что `repo` и методы репозитория уже существуют. В production проверка «сначала exists, потом create» подвержена гонке двух параллельных запросов; надёжная гарантия уникальности должна быть также в базе данных через UNIQUE constraint, а конфликт БД нужно преобразовать в HTTP 409.
