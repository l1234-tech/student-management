# Рубежка №1 — билет 6: точные условия и подробные решения

## Теоретический вопрос 11 — условие из файла

> Зачем совмещать встроенную HTML-валидацию и проверки на JavaScript? Какие ограничения у этих проверок и почему они не отменяют серверной валидации?

### Подробный ответ

HTML-валидация позволяет быстро проверять простые ограничения средствами браузера: `required`, тип input, `min`, `max`, `step`, `pattern`. Это уменьшает количество очевидных ошибок ещё до отправки формы и помогает быстро сообщить об ошибке пользователю.

JavaScript полезен для дополнительных правил: зависимостей между полями, проверок сразу нескольких значений, собственного текста ошибок и динамического интерфейса. Но обе проверки выполняются на клиенте, который контролирует пользователь. Их можно отключить, обойти через DevTools или вообще отправить HTTP-запрос напрямую.

Поэтому backend обязан повторно проверить типы, обязательность, формат, диапазоны, бизнес-правила и права доступа. Например, проверка `min="1"` помогает в браузере, но сервер всё равно должен убедиться, что ИСУ положителен и не нарушает ограничение уникальности. Форматная валидация также не заменяет авторизацию: пользователь с корректно оформленным запросом не обязательно имеет право редактировать студента.

**Прямой ответ:** HTML и JavaScript обеспечивают удобство и раннюю обратную связь; доверять им как границе безопасности нельзя. Финальная проверка данных должна быть на сервере.

## Теоретический вопрос 12 — условие из файла

> Если к одному элементу подходят несколько CSS-правил с разными селекторами, как браузер определяет итоговый стиль? Объясните роль каскада, специфичности и порядка объявления.

### Подробный ответ

CSS каскадирует: для каждого свойства браузер выбирает правило-победитель, учитывая происхождение и важность декларации, слои каскада, специфичность селектора и порядок объявления. Упрощённо для обычных авторских правил: селектор с ID обычно специфичнее класса, класс — селектора тега; если специфичность одинакова, обычно побеждает более позднее правило.

```css
p { color: black; }
.note { color: blue; }
#warning { color: red; }
```

Для элемента `<p id="warning" class="note">...</p>` цвет будет красным: `#warning` имеет более высокую специфичность, чем `.note` и `p`. Если два правила имеют равную специфичность и одинаковые уровни каскада, позже объявленное правило побеждает.

Это упрощённое объяснение: `!important`, inline-стили, cascade layers и стили браузера влияют на полный порядок приоритетов. На практике лучше не полагаться на постоянное увеличение специфичности и избегать избыточного `!important`.

**Прямой ответ:** сперва работает каскадный приоритет, затем сравнивается специфичность, а порядок объявления разрешает конфликт у равноприоритетных правил.

## Практическое задание 6 — условие из файла

> Напишите адаптивный CSS для контейнера .cards: на экране шире 700px — две равные колонки карточек, до 700px включительно — одна колонка. Между карточками 16px.

### Решение

```css
.cards {
  display: grid;
  grid-template-columns: repeat(2, minmax(0, 1fr));
  gap: 16px;
}

@media (max-width: 700px) {
  .cards {
    grid-template-columns: 1fr;
  }
}
```

### Подробный разбор

По умолчанию используется две равные колонки. `repeat(2, minmax(0, 1fr))` задаёт две гибкие колонки одинаковой ширины; нулевой минимум помогает длинному содержимому не растягивать сетку. При ширине viewport 700px или меньше срабатывает media query и устанавливается одна колонка. `gap: 16px` задаёт расстояние между карточками по обеим осям.

**Проверка границы:** на 701px будет две колонки; ровно на 700px и ниже — одна.
