## Теория 1. God Service и cohesion

God Service — сервис, который отвечает слишком за многое: бизнес-правила, валидацию HTTP, запросы к БД, отправку уведомлений и форматирование ответа. Это снижает cohesion (связность элементов внутри модуля): изменения по разным причинам концентрируются в одном классе, его трудно тестировать и переиспользовать.

Признаки: много несвязанных публичных методов, множество зависимостей, длинные методы, проверки HTTP-статусов внутри бизнес-логики, SQL и форматирование JSON в одном месте. Разделять стоит по устойчивым обязанностям, не создавая класс на каждую строку.

## Теория 2. DTO и mapping

ORM Entity отражает модель хранения и может содержать внутренние поля, связи и технические детали. Если возвращать её напрямую, API связывается со схемой БД, может раскрыть лишние данные и столкнуться с циклической сериализацией ленивых связей.

Request DTO описывает входной контракт, Response DTO — публичный формат ответа. Mapping переводит между DTO и сущностями/моделью. Это позволяет менять внутреннюю структуру, не ломая контракт API, и явно контролировать, какие поля разрешено менять клиенту.

## Практика. TypeScript type guard

```ts
interface Student {
  isu_id: number;
  group: string;
}

function isStudent(value: unknown): value is Student {
  if (typeof value !== "object" || value === null) return false;
  if (!("isu_id" in value) || !("group" in value)) return false;

  const candidate = value as Record<string, unknown>;
  return typeof candidate.isu_id === "number"
      && typeof candidate.group === "string";
}
```

Тип `unknown` требует проверить значение до использования. Type guard возвращает boolean и сообщает TypeScript, что при результате true значение можно рассматривать как Student. Интерфейс сам по себе не проверяет данные во время выполнения: JSON из API нужно проверять реально.

## Прямые теоретические ответы

**Прямой ответ на вопросы 23–24.** God Service — сервис, который выполняет слишком много несвязанных задач: управляет студентами, формирует отчёты, отправляет уведомления, разбирает HTTP и работает с файлами. Признаки: много причин для изменения, чрезмерно много зависимостей, длинные методы, тяжёлое тестирование и низкая cohesion (внутренняя связанность по одной ответственности). Разделение оправдано, если разные части меняются независимо и имеют чёткие границы, а не просто ради увеличения числа классов.

API не всегда должно отдавать ORM-сущность напрямую: у неё могут быть внутренние поля, связи, циклические ссылки и структура, не предназначенная для клиента. Request DTO задаёт допустимую форму входных данных; Response DTO — публичную форму ответа; mapping переводит DTO в доменную модель или обратно. Это позволяет менять внутреннюю модель БД, не ломая API, и явно контролировать, какие поля клиент может читать или присылать.
