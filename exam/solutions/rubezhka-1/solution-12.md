# Рубежка №1 — билет 12: точные условия и подробные решения

## Теоретический вопрос 23 — условие из файла

> Почему God Service — архитектурный антипаттерн? Как понять, что сервис потерял cohesion и его уже стоит разделить?

### Подробный ответ

God Service — сервис, который накопил слишком много разных обязанностей: правила управления студентами, работу с файлами, отправку уведомлений, форматирование ответа, чтение данных, обработку HTTP и многое другое. Это антипаттерн, потому что изменения по разным причинам концентрируются в одном классе.

Cohesion — насколько тесно обязанности компонента связаны с одной целью. Признаки низкой cohesion: много несвязанных публичных методов, множество зависимостей, длинные методы с ветвлениями по разным сценариям, смешивание предметных правил с HTTP/SQL/форматированием и сложные тесты, которым нужно настраивать почти всё приложение.

Разделять нужно по устойчивым обязанностям, например выделить сервис уведомлений или экспорт отчётов, когда они имеют собственные правила и могут меняться независимо. Не следует создавать класс для каждой мелочи только ради количества файлов.

**Прямой ответ:** God Service затрудняет понимание, тестирование и изменение системы, потому что нарушает принцип единой ответственности и имеет низкую внутреннюю связанность. Сервис стоит разделить, когда его части имеют независимые причины изменения и понятные границы.

## Теоретический вопрос 24 — условие из файла

> Почему API не всегда должен возвращать объект внутренней модели или ORM-сущность напрямую? Объясните назначение Request DTO, Response DTO и mapping.

### Подробный ответ

ORM-сущность представляет структуру хранения и может включать технические поля, ленивые связи, циклические ссылки и внутренние данные. Если отдавать её напрямую, API становится зависимым от схемы БД, может случайно раскрыть поля, а сериализация связей способна вызвать лишние запросы или циклические структуры.

- **Request DTO** описывает форму входных данных, которые разрешено передать серверу.
- **Response DTO** задаёт публичную структуру ответа, предназначенную клиенту.
- **Mapping** преобразует входной DTO в модель/сущность или сущность в выходной DTO.

Например, клиент может передавать `isu_id` и `group`, но не должен самостоятельно задавать внутренний признак администратора или техническую дату создания. При ответе сервер может вернуть только разрешённые поля. Mapping отделяет публичный контракт API от внутренней модели, поэтому изменение таблиц не обязано ломать клиентов.

## Практическое задание 12 — условие из файла

> На TypeScript объявите интерфейс Student с числовым isu_id и строковым group. Напишите функцию isStudent(value: unknown): value is Student, которая проверяет эти два поля на этапе выполнения, прежде чем доверять объекту из API.

### Решение

```ts
interface Student {
  isu_id: number;
  group: string;
}

function isStudent(value: unknown): value is Student {
  if (typeof value !== "object" || value === null) {
    return false;
  }

  if (!("isu_id" in value) || !("group" in value)) {
    return false;
  }

  const candidate = value as Record<string, unknown>;

  return typeof candidate.isu_id === "number"
      && typeof candidate.group === "string";
}
```

### Подробный разбор

- `unknown` означает, что значение нельзя безопасно использовать, пока не доказан его тип.
- Проверка `typeof value === "object"` исключает примитивы, а `value !== null` нужен потому, что `typeof null` тоже равен `"object"`.
- Проверка наличия полей позволяет обращаться к ним после соответствующего сужения типа.
- Приведение к `Record<string, unknown>` позволяет проверить значения полей без доверия к их типам.
- `value is Student` — type predicate: если функция вернула `true`, TypeScript считает значение типом Student в соответствующей ветке.

Интерфейс TypeScript сам по себе исчезает при компиляции и не валидирует JSON во время выполнения. Поэтому данные API необходимо реально проверять этой функцией, прежде чем использовать.
