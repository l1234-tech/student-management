# Рубежка №1 — билет 2: точные условия и подробные решения

## Теоретический вопрос 3 — условие из файла

> Почему HTTP является stateless, но приложение способно «узнавать» пользователя при последующих запросах? Объясните роль cookies и сведений, передаваемых клиентом.

### Подробный ответ

HTTP — протокол без обязательной встроенной памяти о предыдущих запросах: каждый запрос содержит сведения, необходимые для его обработки сейчас — метод, путь, заголовки и, при необходимости, тело. Сам по себе следующий запрос не обязан автоматически знать результат предыдущего.

Приложение связывает запросы с пользователем с помощью контекста, который передаётся явно или восстанавливается сервером. Например:

1. После входа сервер создаёт сессию и отправляет браузеру cookie с идентификатором сессии.
2. Браузер сохраняет cookie и при подходящих условиях автоматически включает её в последующие запросы.
3. Сервер извлекает идентификатор из cookie и по нему находит серверную сессию с информацией о пользователе.
4. Альтернативный подход — клиент передаёт токен, например в заголовке `Authorization: Bearer ...`; сервер проверяет токен и определяет субъект запроса.

**Важно:** stateless не означает, что сервер ничего не хранит. Записи студентов и аккаунты могут храниться в базе данных. Stateless означает отсутствие неявной связи между HTTP-запросами в самом протоколе; приложение добавляет такую связь механизмами сессий, cookies, токенов или баз данных.

Cookie не является автоматически доказательством подлинности: сервер должен корректно проверить сессию или токен. Для cookies аутентификации нужны соответствующие настройки безопасности (`Secure`, `HttpOnly`, `SameSite`) и защита от CSRF в зависимости от архитектуры.

## Теоретический вопрос 4 — условие из файла

> Что означают свойства safe и idempotent у HTTP-метода? Почему повторная отправка одного и того же POST-запроса может быть опаснее повтора PUT?

### Подробный ответ

**Safe (безопасный)** — метод, который по своему назначению не должен менять состояние ресурса. Основной пример — GET: он читает данные. Логи и статистика на сервере не нарушают это свойство, поскольку не являются запрошенным изменением ресурса.

**Idempotent (идемпотентный)** — метод, для которого повтор идентичного запроса имеет тот же целевой эффект на состояние, что и один вызов. HTTP определяет GET, PUT и DELETE как идемпотентные, но только GET относится к safe-методам.

- Повтор `PUT /students/42` с одинаковым полным представлением должен оставить ресурс в одном и том же состоянии.
- Повтор `DELETE /students/42` не должен восстановить удалённую запись; ответы могут различаться, но желаемое состояние не меняется.
- Повтор `POST /students` часто создаёт ещё одну запись. Поэтому при сетевом тайм-ауте клиент не всегда знает, обработал ли сервер первый запрос; повтор может привести к дубликату.

Для критичных POST-операций API может использовать ключ идемпотентности или ограничение уникальности, например уникальный ИСУ ID. Таким образом, POST не обязательно небезопасен, но протокол не обещает идемпотентность по умолчанию.

## Практическое задание 2 — условие из файла

> На JavaScript напишите функцию getAddressParts(address), принимающую абсолютный URL и возвращающую объект с полями host, path, sort (значение параметра sort или null) и fragment (без символа #). Не разбирайте строку вручную.

### Решение

```js
function getAddressParts(address) {
  const url = new URL(address);

  return {
    host: url.host,
    path: url.pathname,
    sort: url.searchParams.get("sort"),
    fragment: url.hash.startsWith("#") ? url.hash.slice(1) : url.hash
  };
}
```

### Подробный разбор

- `new URL(address)` — стандартный парсер URL. Он корректно разбирает схему, имя хоста, порт, путь, query-параметры и fragment.
- `url.host` возвращает hostname и порт, если порт указан. Например, для `https://example.com:8443/a?sort=name#top` это `example.com:8443`.
- `url.pathname` — путь, например `/a`.
- `url.searchParams.get("sort")` возвращает значение параметра `sort`; если параметра нет — `null`, как требует условие.
- `url.hash` обычно содержит fragment вместе с символом `#`; `slice(1)` убирает его. Если fragment отсутствует, результат — пустая строка.

Не нужно делить строку вручную по `/`, `?` и `#`: URL допускают кодирование, порты, повторяющиеся параметры и другие детали, которые надёжнее обрабатывает встроенный парсер.

Для некорректного или относительного URL конструктор `URL` выбросит `TypeError`; по условию на вход приходит абсолютный URL, поэтому дополнительный fallback не требуется.


## Прямой ответ на вопросы 3–4

**HTTP stateless, потому что отдельный запрос не обязан помнить контекст предыдущих запросов.** Чтобы связать запросы с пользователем, приложение использует явно передаваемые данные: cookie с идентификатором сессии, токен в заголовке Authorization или другой credential. Браузер автоматически отправляет подходящие cookies по правилам их атрибутов; сервер проверяет cookie и определяет связанную с ней сессию. Stateless не означает отсутствия БД или серверного состояния вообще: речь о том, что сам протокол не прикрепляет историю прошлых запросов к каждому новому запросу автоматически. Cookie должна проверяться сервером; атрибуты Secure, HttpOnly и SameSite помогают ограничить риски, но не заменяют авторизацию и другие защиты.

**Safe** означает, что по назначению запрос не должен менять состояние ресурса; **idempotent** — что повторение идентичного запроса имеет тот же целевой эффект, что и однократное выполнение. GET safe. PUT и DELETE идемпотентны по семантике, хотя ответы могут отличаться: первый DELETE может вернуть 204, повторный — 404. POST часто не идемпотентен: повтор создания может породить вторую запись. Для критичных операций используют уникальные ограничения, проверку повторов или idempotency key.
