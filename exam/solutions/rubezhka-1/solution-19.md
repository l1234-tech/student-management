## Теория 1. Память четырёх воркеров

Четыре воркера обычно означают четыре отдельных процесса. У каждого свой адресный простор, поэтому глобальный словарь студентов в одном воркере не становится автоматически общим для остальных. POST, попавший в воркер A, может изменить его копию, а последующий GET в воркере B этой записи не увидит.

Это ограничивает хранение в памяти: оно временное и не подходит для согласованного состояния при нескольких процессах или перезапусках. Для общего хранилища используют БД, общий key-value store или другой IPC, но для приложения управления студентами БД — типичное решение.

## Теория 2. GIL и CPU-bound

В обычной сборке CPython GIL ограничивает одновременное выполнение Python bytecode несколькими потоками в одном процессе. Для CPU-bound кода (например, тяжёлые вычисления на Python) увеличение потоков не гарантирует ускорение и может добавить накладные расходы. Для I/O-bound задач потоки полезны, потому что во время ожидания сети/файла поток часто освобождает GIL.

Для CPU-bound параллелизма могут подойти multiprocessing, нативные библиотеки, которые освобождают GIL, либо специализированные вычислительные средства. Детали зависят от версии Python и используемой библиотеки.

## Практика. Spring MVC контроллер

```java
@RestController
@RequestMapping("/students")
public class StudentController {
    private final StudentService studentService;

    public StudentController(StudentService studentService) {
        this.studentService = studentService;
    }

    @GetMapping("/{id}")
    public StudentDto getStudent(@PathVariable long id) {
        return studentService.find(id);
    }
}
```

`@RestController` означает, что возвращаемое значение сериализуется в тело ответа, обычно JSON. `@GetMapping("/{id}")` сопоставляет GET с путём `/students/{id}`; `@PathVariable` извлекает ID. Сервис внедряется через конструктор. Это минимальный пример по условию: в полноценном проекте нужно определить поведение для отсутствующего студента и возвращать подходящий статус, например 404.

## Прямые теоретические ответы

**Прямой ответ на вопросы 37–38.** Четыре worker-процесса не являются одним общим хранилищем, потому что у каждого процесса своя виртуальная память. Если один процесс изменил глобальный словарь студентов, другие workers автоматически этого изменения не увидят. После перезапуска процесса данные в памяти также пропадут. Общие данные должны жить в БД, общем хранилище или передаваться через IPC.

В обычной сборке CPython GIL не позволяет нескольким потокам одновременно исполнять Python bytecode в одном процессе в общем случае. Поэтому добавление потоков не гарантирует ускорение CPU-bound задачи: потоки конкурируют за GIL и добавляют накладные расходы. Для I/O-bound задач потоки могут быть полезны, потому что во время ожидания I/O GIL часто отпускается; для CPU-bound кода рассматривают процессы, native-код, освобождающий GIL, или другие подходы.
