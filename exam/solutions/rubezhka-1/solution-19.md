# Рубежка №1 — билет 19: точные условия и подробные решения

## Теоретический вопрос 37 — условие из файла

> Почему четыре воркера одного Python backend-приложения не образуют одно общее хранилище объектов в памяти? Что это означает для учебного API, которое хранит студентов в словаре?

### Подробный ответ

Четыре worker-процесса обычно имеют четыре отдельных адресных пространства. У каждого своя память и свой экземпляр глобальных переменных. Если один worker изменит словарь студентов, другие workers не увидят это изменение автоматически. Поэтому POST-запрос, который попал в worker A, может создать запись только в его словаре, а последующий GET, попавший в worker B, не найдёт студента.

Хранение в глобальном словаре также теряет данные при завершении процесса. Для общего состояния между несколькими процессами обычно применяют базу данных или внешнее key-value-хранилище. В учебном одно-процессном примере словарь может быть достаточен для демонстрации, но не обеспечивает согласованность полноценного production API.

## Теоретический вопрос 38 — условие из файла

> Как GIL влияет на выполнение CPU-bound Python-кода в обычной сборке CPython? Почему увеличение количества потоков не обязано сокращать время вычислительной задачи?

### Подробный ответ

GIL (Global Interpreter Lock) в обычной сборке CPython ограничивает одновременное выполнение Python bytecode несколькими потоками одного процесса. Поэтому для CPU-bound задачи, где время расходуется преимущественно на вычисления в Python, новые потоки не обязаны ускорять работу: они конкурируют за GIL и создают дополнительные переключения.

Для I/O-bound задач потоки могут быть полезны, потому что во время ожидания ввода-вывода поток часто освобождает GIL, позволяя другому выполнять работу. Для CPU-bound нагрузки могут подойти несколько процессов, нативная библиотека, освобождающая GIL, или специализированная реализация вычислений. Поведение зависит от версии Python и конкретной библиотеки, поэтому формулировка относится именно к обычной сборке CPython, как указано в вопросе.

## Практическое задание 19 — условие из файла

> На Java напишите минимальный Spring MVC-контроллер StudentController с маршрутом GET /students/{id}. Он должен вызывать внедрённый StudentService.find(id) и возвращать StudentDto. Допускается опустить импорты и определения готовых классов.

### Решение

```java
@RestController
@RequestMapping("/students")
public class StudentController {
    private final StudentService studentService;

    public StudentController(StudentService studentService) {
        this.studentService = studentService;
    }

    @GetMapping("/{id}")
    public StudentDto getStudent(@PathVariable long id) {
        return studentService.find(id);
    }
}
```

### Подробный разбор

- `@RestController` объявляет контроллер REST: возвращаемый объект сериализуется в тело HTTP-ответа, обычно в JSON.
- `@RequestMapping("/students")` задаёт общий префикс пути.
- `@GetMapping("/{id}")` связывает GET-запрос с переменной частью URL.
- `@PathVariable` преобразует сегмент URL в аргумент `id`.
- Конструктор получает `StudentService` извне (constructor injection); контроллер не создаёт сервис через `new`.
- Метод возвращает DTO, чтобы публичный формат ответа был отделён от внутренней entity.

По условию определения классов можно опустить. В полноценном приложении следует также определить, что делать, если студента с таким ID нет, и вернуть соответствующий HTTP 404 через исключение/обработчик.
