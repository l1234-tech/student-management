# Рубежка №1 — билет 24: точные условия и подробные решения

## Теоретический вопрос 47 — условие из файла

> Почему singleton/ application-scoped бин не следует использовать для хранения изменяемых данных текущего запроса? Как область видимости влияет на число экземпляров и возможные гонки?

### Подробный ответ

Singleton в Spring обычно означает один экземпляр бина на ApplicationContext; application-scoped объект привязан к контексту приложения в рамках соответствующей технологии. Такой объект может обслуживать множество запросов одновременно. Если хранить в его изменяемых полях сведения текущего пользователя или запроса, два клиента могут перезаписать данные друг друга, а обработка станет зависеть от чередования потоков.

Например, поле `currentUserId` в singleton-сервисе — плохое место для ID текущего запроса: запрос A может записать 42, запрос B — 53, и код A прочитает уже 53. Это и ошибка изоляции данных, и потенциальная утечка между запросами.

Singleton подходит для stateless-сервисов и безопасной общей конфигурации. Данные запроса нужно передавать аргументами методов или хранить в предназначенном для этого request context. Scope определяет, сколько экземпляров и на какой срок создаётся контейнером, но сам по себе scope не заменяет синхронизацию.

## Теоретический вопрос 48 — условие из файла

> Чем динамический Proxy, BeanPostProcessor и CDI-интерцептор различаются по роли в системе? Почему их нельзя считать тремя независимыми названиями одного механизма?

### Подробный ответ

- **Динамический Proxy** — объект-обёртка, который перехватывает вызовы интерфейса или класса и может перед делегированием/после него выполнить дополнительную логику.
- **BeanPostProcessor** — расширение жизненного цикла Spring: контейнер вызывает его для экземпляров бинов до и/или после initialization callback; он может возвращать исходный объект или обёртку, например proxy.
- **CDI-интерцептор** — механизм Jakarta CDI для применения cross-cutting logic к вызовам методов, помеченных определённой interceptor binding, например для аудита или транзакционной логики.

Они связаны, но не эквивалентны. Proxy — это форма перехвата вызовов; BeanPostProcessor — точка расширения Spring lifecycle, с помощью которой в том числе могут создавать/внедрять proxy; CDI interceptor — декларативный механизм перехвата в CDI. У них разные уровни абстракции и правила настройки.

## Практическое задание 24 — условие из файла

> На JavaScript напишите async function requestWithRefresh(url, access, refresh): сделайте GET с Authorization: Bearer access; если получен 401, вызовите POST /auth/refresh с JSON {refresh}, возьмите из ответа новый access и повторите исходный GET ровно один раз. Иные ошибки не обрабатывайте. Считайте, что refresh endpoint возвращает JSON с полем access.

### Решение

```js
async function requestWithRefresh(url, access, refresh) {
  const makeGet = (token) => fetch(url, {
    method: "GET",
    headers: {
      "Authorization": `Bearer ${token}`
    }
  });

  const firstResponse = await makeGet(access);
  if (firstResponse.status !== 401) {
    return firstResponse;
  }

  const refreshResponse = await fetch("/auth/refresh", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "Accept": "application/json"
    },
    body: JSON.stringify({ refresh })
  });

  const data = await refreshResponse.json();
  const secondResponse = await makeGet(data.access);
  return secondResponse;
}
```

### Подробный разбор

1. Вспомогательная `makeGet(token)` формирует GET с заголовком Authorization.
2. Сначала запрос выполняется с текущим access token.
3. Если статус отличается от 401, функция сразу возвращает первый ответ: refresh не вызывается.
4. Только при 401 отправляется POST с JSON `{ refresh }` на `/auth/refresh`.
5. Из ответа читается новое поле `access`, затем исходный GET выполняется один дополнительный раз.
6. Вторая попытка не запускает рекурсивный refresh, поэтому повтор происходит ровно один раз.

Условие говорит «иные ошибки не обрабатывайте», поэтому код не добавляет дополнительные ветки для ошибок refresh или второго GET; они возвращаются/передаются дальше в рамках поведения fetch и вызывающего кода. В реальном клиенте обработку отказа refresh обычно делают явной, но это выходит за границы задания.
