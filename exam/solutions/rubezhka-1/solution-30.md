## Теория 1. Выбор способа устранения N+1

- `JOIN FETCH` полезен, когда конкретному запросу сразу нужна связь; он загружает связанные данные одним запросом, но join может увеличить число строк.
- `@EntityGraph` задаёт граф связей, которые следует загрузить для операции, не обязательно переписывая запрос вручную.
- Batch fetching группирует загрузку нескольких lazy-связей в меньшее число запросов.
- DTO projection выбирает только необходимые поля/связи и подходит для read-only API-ответа, когда не требуется управляемая Entity.

Выбор зависит от размера результата, кардинальности связей, числа коллекций, пагинации и нужных полей. «Меньше SQL любой ценой» — неверная цель: огромный join может передавать дублирующиеся строки и потреблять больше памяти. Нужно измерять запросы и выбирать стратегию для конкретного use case.

## Теория 2. LazyInitializationException и EAGER

LazyInitializationException типично возникает, когда приложение обращается к lazy-связи уже после закрытия persistence context/сессии и ORM не может загрузить данные. Перевод всех связей в EAGER не является универсальным решением: он может загрузить слишком много данных, увеличить число join-запросов и породить дополнительные N+1 проблемы в другом месте.

Альтернативы: загрузить нужные связи в транзакции через fetch join/EntityGraph, сформировать DTO внутри транзакции или использовать проекцию. API лучше возвращать контролируемый DTO, а не рассчитывать на сериализацию всей графовой структуры Entity после закрытия контекста.

## Практика. Репозиторий с загрузкой студентов групп

Вариант с JPQL:

```java
public interface StudyGroupRepository
        extends JpaRepository<StudyGroup, Long> {

    @Query("select distinct g from StudyGroup g left join fetch g.students")
    List<StudyGroup> findAllWithStudents();
}
```

`left join fetch` загружает группы и связанные коллекции студентов одним запросом, включая группы без студентов. `distinct` помогает убрать дублирующиеся объекты групп из результата на уровне JPA. Для пагинации fetch join коллекции требует особой осторожности: SQL-строки размножаются, поэтому для больших списков может потребоваться двухэтапная загрузка или DTO-проекция. Названия классов и поля связи должны соответствовать реальным Entity.
