# Рубежка №1 — билет 30: точные условия и подробные решения

## Теоретический вопрос 59 — условие из файла

> Когда для устранения N+1 подходят join fetch, @EntityGraph, пакетная загрузка и DTO-проекция? Почему нельзя выбирать способ только по принципу «меньше SQL любой ценой»?

### Подробный ответ

Все четыре подхода помогают управлять тем, как и когда загружаются связанные данные, но у каждого своя область применения.

- **`JOIN FETCH`** подходит, когда конкретному запросу действительно нужны связанные сущности. Связь можно загрузить в том же JPQL-запросе, но join по коллекции размножает SQL-строки и особенно требует осторожности с пагинацией.
- **`@EntityGraph`** позволяет объявить fetch plan для репозитория отдельно от бизнес-логики запроса. Он удобен, если нужно выразить, какие связи загружать для конкретного сценария.
- **Пакетная загрузка** группирует запросы на связанные сущности порциями и снижает число обращений без единого огромного join. Она полезна, когда одновременно загружается много сущностей/коллекций.
- **DTO-проекция** выбирает только поля, необходимые ответу API. Если клиенту нужна сводка, а не полные сущности со всеми связями, DTO может быть быстрее и безопаснее.

Нельзя выбирать только минимальное число SQL: огромный join может дублировать много данных, потреблять память, ломать ожидаемую пагинацию или загружать ненужные столбцы. Нужно учитывать размер результата, число строк, объём данных, требования к пагинации, кеширование и реальный профиль запросов.

## Теоретический вопрос 60 — условие из файла

> Что приводит к LazyInitializationException и почему решение «сделать все связи EAGER» может ухудшить систему? Опишите альтернативу для подготовки DTO ответа.

### Подробный ответ

`LazyInitializationException` возникает, когда код обращается к лениво загружаемой связи уже после того, как persistence context/сессия закрыта или сущность больше не может выполнить нужную загрузку. Например, сервис возвращает `StudyGroup`, транзакция завершается, а serializer затем пытается прочитать `group.students`; связи ещё не загружены, и ORM не может их получить.

Сделать все связи `EAGER` — не универсальное исправление. Это может привести к загрузке данных, которые не нужны конкретному endpoint, разрастанию результирующих join, дополнительным SQL-запросам и большому потреблению памяти. Граф сущностей может стать большим и трудно предсказуемым.

Альтернатива — целенаправленно загружать нужные данные внутри транзакции через `JOIN FETCH`, `@EntityGraph` или batch fetching, а затем преобразовывать их в DTO, который содержит только необходимую клиенту информацию. DTO формируется внутри корректной границы загрузки, поэтому сериализация не должна случайно инициировать запросы к уже закрытому контексту.

## Практическое задание 30 — условие из файла

> На Java/Spring Data JPA напишите метод репозитория findAllWithStudents(), который загружает все сущности StudyGroup вместе с коллекцией students.

### Решение

```java
public interface StudyGroupRepository extends JpaRepository<StudyGroup, Long> {
    @Query("SELECT DISTINCT g FROM StudyGroup g LEFT JOIN FETCH g.students")
    List<StudyGroup> findAllWithStudents();
}
```

### Подробный разбор

- `LEFT JOIN FETCH g.students` загружает коллекцию `students` в том же запросе, что и группы, включая группы без студентов.
- `DISTINCT` помогает избежать повторяющихся объектов StudyGroup в результирующем списке JPA, потому что SQL join возвращает несколько строк на группу, если у неё несколько студентов.
- `@Query` задаёт JPQL, где используются имена сущностей и их полей, а не напрямую имена таблиц/столбцов SQL.
- Возвращаемый тип — список StudyGroup.

Этот пример предполагает, что у `StudyGroup` есть связь с именем `students`, например `@OneToMany(mappedBy = "studyGroup")`. Если в фактической entity поле или имя сущности другое, JPQL нужно согласовать с кодом проекта. Для больших коллекций и пагинации fetch join требует осторожности; DTO-проекция или двухэтапная загрузка может быть предпочтительнее.
