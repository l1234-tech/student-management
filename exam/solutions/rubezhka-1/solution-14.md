# Рубежка №1 — билет 14: точные условия и подробные решения

## Теоретический вопрос 27 — условие из файла

> Чем архитектура MVC отличается от слоистой схемы Controller–Service–Repository? Что именно называют Model и View, когда backend отдаёт JSON вместо HTML?

### Подробный ответ

MVC (Model–View–Controller) разделяет модель приложения, представление и управление взаимодействием. Model содержит данные и правила предметной области, View отвечает за отображение, Controller принимает действия и координирует их обработку.

Схема Controller–Service–Repository — другая классификация ответственности в backend:
- Controller связывает HTTP-запрос/ответ с вызовом приложения;
- Service выполняет сценарии и бизнес-правила;
- Repository инкапсулирует доступ к хранилищу.

Эти схемы могут сочетаться. Если backend отдаёт JSON, View не обязательно означает HTML-шаблон: публичное представление данных может быть JSON-ответом/DTO, хотя фактическая сериализация часто выполняется framework. Model — предметные данные и правила, а не только ORM-класс.

**Прямой ответ:** MVC описывает роли Model, View и Controller в представлении/обработке взаимодействия; Controller–Service–Repository описывает разделение обязанностей backend-слоёв. Это не взаимоисключающие архитектуры.

## Теоретический вопрос 28 — условие из файла

> Как различаются Strategy, Factory Method и Adapter по решаемой задаче? Объясните, какой паттерн уместен для выбора алгоритма, создания объектов и подключения несовместимого интерфейса.

### Подробный ответ

- **Strategy** инкапсулирует взаимозаменяемые алгоритмы за единым интерфейсом. Клиент может выбрать способ расчёта, сортировки или скидки без ветвления по всей программе.
- **Factory Method** делегирует создание объекта и позволяет подклассам или конкретной реализации выбирать, какой продукт создать.
- **Adapter** оборачивает класс с несовместимым интерфейсом и предоставляет требуемый приложением контракт, преобразуя вызовы или данные.

Примеры: Strategy выбирает алгоритм расчёта оценки; Factory Method создаёт подходящий экспортёр CSV/PDF; Adapter позволяет использовать внешнюю библиотеку, метод которой не совпадает с нашим интерфейсом.

Запомнить можно через три вопроса: «какой алгоритм применить?» — Strategy; «какой объект создать?» — Factory Method; «как подружить несовместимые интерфейсы?» — Adapter.

## Практическое задание 14 — условие из файла

> На Python с FastAPI напишите глобальный обработчик исключения StudentNotFound, возвращающий HTTP 404 и JSON { "error": "student_not_found" }. Предположите, что app и класс исключения уже объявлены; нужные импорты покажите.

### Решение

```python
from fastapi import Request
from fastapi.responses import JSONResponse

@app.exception_handler(StudentNotFound)
async def student_not_found_handler(
    request: Request,
    exc: StudentNotFound
) -> JSONResponse:
    return JSONResponse(
        status_code=404,
        content={"error": "student_not_found"}
    )
```

### Подробный разбор

- `@app.exception_handler(StudentNotFound)` регистрирует обработчик именно для этого типа исключения на уровне приложения.
- FastAPI передаёт объект запроса и экземпляр исключения в функцию обработчика.
- `JSONResponse` формирует JSON-тело и явный HTTP-статус 404 Not Found.
- Ключ `error` и значение `student_not_found` соответствуют условию без дополнительного форматирования.

Это централизует преобразование доменной ситуации «студент не найден» в HTTP-ответ: сервис может сообщить об отсутствии объекта через исключение, а слой API решает, каким статусом и телом ответить. В рамках задания класс исключения и объект `app` считаются уже объявленными.
