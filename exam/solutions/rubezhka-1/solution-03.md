# Рубежка №1 — билет 3: точные условия и подробные решения

## Теоретический вопрос 5 — условие из файла

> Пользователь ввёл адрес HTTPS-сайта и нажал Enter. Объясните путь запроса от разбора URL до получения ответа. За что отвечают DNS, транспортное соединение, TLS, HTTP и серверное приложение?

### Подробный ответ

1. **Разбор URL.** Браузер определяет схему (`https`), хост, порт (обычно 443), путь и query-параметры. Fragment после `#` обычно используется на стороне браузера и не передаётся серверу в HTTP-запросе.
2. **DNS.** Браузер или системный resolver получает IP-адрес, соответствующий доменному имени. DNS отвечает за разрешение имени, но не за загрузку HTML.
3. **Транспорт.** Для HTTP/1.1 и HTTP/2 обычно устанавливается TCP-соединение. HTTP/3 использует QUIC поверх UDP. Транспорт доставляет байты, но сам не задаёт прикладное значение запроса.
4. **TLS.** Для HTTPS устанавливается защищённый канал: согласуются криптографические параметры, проверяется сертификат сервера и вырабатываются ключи сессии. TLS обеспечивает конфиденциальность, целостность и аутентификацию сервера в пределах корректной проверки сертификата.
5. **HTTP.** Браузер отправляет метод, request-target, заголовки и при необходимости тело. Сервер отвечает статусом, заголовками и телом.
6. **Серверное приложение.** Сервер или gateway передаёт запрос маршруту/обработчику. Приложение проверяет входные данные и права, выполняет бизнес-логику и при необходимости обращается к БД.
7. **Ответ.** Браузер читает ответ и отображает HTML или обрабатывает JSON, например обновляет таблицу студентов.

Итого: DNS находит адрес; транспорт доставляет данные; TLS защищает канал; HTTP описывает сообщения запроса и ответа; серверное приложение решает, какую операцию выполнить.

## Теоретический вопрос 6 — условие из файла

> Что именно ограничивает CORS, почему это механизм браузера и чем проблема CORS отличается от ошибки выполнения backend-приложения?

### Подробный ответ

Same-Origin Policy (SOP) ограничивает возможность JavaScript-кода одной веб-страницы читать данные другого origin. Origin — это схема, хост и порт. Например, `https://app.example` и `https://api.example` — разные origin.

**CORS (Cross-Origin Resource Sharing)** — механизм, через который сервер с помощью HTTP-заголовков сообщает браузеру, какие cross-origin ответы разрешено открывать скриптам. Для некоторых запросов браузер сначала посылает preflight-запрос OPTIONS и проверяет, разрешены ли метод и заголовки. Затем он выполняет основной запрос, если проверка пройдена.

Это механизм браузерной безопасности: браузер ограничивает доступ веб-страницы к ответу. Прямой запрос через curl или backend-to-backend вызов не подчиняется этой браузерной политике. Запрос может даже дойти до сервера и обработаться, но браузер не позволит скрипту прочитать ответ, если CORS-конфигурация неправильна.

**CORS не равен ошибке backend:** ошибка backend — например, 500 из-за исключения приложения; CORS-ошибка — браузер не разрешил странице получить доступ к cross-origin ответу. Диагностировать нужно по вкладкам Network и Console и по серверным логам. CORS не заменяет аутентификацию, авторизацию или CSRF-защиту.

## Практическое задание 3 — условие из файла

> Запишите сырой HTTP/1.1-запрос для создания студента через POST /api/students на api.example.com: тело JSON {"isu_id":42,"group":"M3301"}. Укажите необходимые заголовки; точное значение Content-Length вычислять не нужно.

### Решение

```http
POST /api/students HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json

{"isu_id":42,"group":"M3301"}
```

### Подробный разбор

- `POST` — запрос передаёт данные для обработки; здесь ожидается создание студента.
- `/api/students` — адрес коллекции студентов на сервере `api.example.com`.
- `Host` указывает хост назначения в HTTP/1.1.
- `Content-Type: application/json` говорит серверу, что тело — JSON, чтобы он мог выбрать соответствующий парсер.
- `Accept: application/json` указывает предпочтительный формат ответа.
- Пустая строка отделяет заголовки от тела.
- Тело содержит JSON-объект с `isu_id` и `group`.

По условию точное значение Content-Length вычислять не нужно. В реальном обмене длина тела или способ передачи задаются протокольной реализацией корректно. Само наличие JSON не гарантирует, что данные корректны: backend должен проверить типы, обязательные поля, допустимость ИСУ и бизнес-ограничения.


## Прямой ответ на вопросы 5–6

**При открытии HTTPS URL браузер сначала разбирает адрес, затем находит сервер и устанавливает защищённый канал, после чего отправляет HTTP-запрос.** URL задаёт схему, хост, путь и необязательные query-параметры. DNS разрешает имя хоста в IP-адрес. Для HTTP/1.1 обычно устанавливается TCP-соединение, затем TLS согласует параметры защиты и проверяет сертификат сервера. После этого браузер передаёт HTTP-запрос; сервер сопоставляет его маршруту, выполняет проверки, бизнес-логику и при необходимости обращается к БД. Ответ содержит статус, заголовки и тело. DNS не отдаёт страницу; TLS защищает канал; HTTP описывает обмен; приложение определяет смысл запроса. Фрагмент после # обычно не отправляется серверу.

**CORS ограничивает доступ браузерного JavaScript к ответам с другого origin.** Origin состоит из схемы, хоста и порта. Same-Origin Policy по умолчанию не даёт скрипту свободно читать данные другого origin; CORS позволяет серверу явно разрешить конкретные взаимодействия через заголовки. Для некоторых запросов браузер отправляет предварительный OPTIONS preflight. CORS — механизм браузера, а не аутентификация или авторизация. Запрос может дойти до сервера и быть обработан, но браузер не разрешит коду читать ответ из-за отсутствующих или неподходящих CORS-заголовков. Поэтому CORS-сообщение в браузере не равно backend-ошибке 500 и не заменяет CSRF-защиту.
