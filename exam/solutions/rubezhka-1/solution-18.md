# Рубежка №1 — билет 18: точные условия и подробные решения

## Теоретический вопрос 35 — условие из файла

> Как отличаются этапы валидации и построения ответа у Flask, DRF и FastAPI? Почему один и тот же неверный объект может приводить к разным стандартным ответам?

### Подробный ответ

Flask предоставляет маршрутизацию, request/response API и механизмы обработки ошибок, но типовую валидацию тела, сериализацию и формат ошибок разработчик часто выбирает и задаёт явно. Django REST Framework (DRF) предоставляет Serializer, который проверяет входные поля и преобразует данные, а также средства построения API-ответов. FastAPI использует аннотации типов и модели Pydantic для разбора/валидации запроса и может выполнять валидацию ответа по объявленной модели.

Поэтому неверный объект не обязан приводить к одинаковому ответу во всех трёх системах. Статус и тело зависят от того, на каком этапе возникла ошибка, от стандартных правил framework, пользовательских обработчиков исключений и настроек приложения. Нельзя предполагать, что все они всегда возвращают один и тот же статус или JSON-формат.

В проекте на DRF правильнее ориентироваться на фактический Serializer и обработчики именно вашего API; общие принципы frameworks не заменяют проверку кода и конфигурации конкретной лабораторной.

## Теоретический вопрос 36 — условие из файла

> Проследите жизненный цикл одного POST-запроса во Flask от приёма сервером до формирования JSON-ответа. Где возникают ошибки маршрутизации, валидации и выполнения обработчика?

### Подробный ответ

1. HTTP-сервер принимает сетевой запрос и передаёт его WSGI-приложению.
2. Flask формирует request context и сопоставляет метод/путь с зарегистрированным маршрутом.
3. Вызывается view-функция соответствующего маршрута.
4. Обработчик читает тело запроса, например вызывает `request.get_json()`, и проверяет входные данные.
5. Прикладная логика выполняет сценарий, при необходимости вызывает service/repository и записывает данные в хранилище.
6. Обработчик создаёт ответ, например `jsonify(...)`, Flask формирует HTTP-ответ, а сервер передаёт его клиенту.

Ошибки маршрутизации возникают, когда путь не найден (часто 404) или метод не разрешён (405). Ошибка разбора/валидации может быть отображена как 400/422 или другой согласованный статус. Бизнес-конфликт, например повтор ИСУ, часто отражается как 409. Необработанное неожиданное исключение обычно приводит к 500. Конкретные статусы определяет контракт API и обработчики ошибок.

## Практическое задание 18 — условие из файла

> На Python напишите программу, в которой два потока по 1000 раз увеличивают общий счётчик counter, и итог гарантированно равен 2000. Выведите итог после завершения обоих потоков.

### Решение

```python
import threading

counter = 0
lock = threading.Lock()

def increment_many():
    global counter
    for _ in range(1000):
        with lock:
            counter += 1

threads = [
    threading.Thread(target=increment_many),
    threading.Thread(target=increment_many)
]

for thread in threads:
    thread.start()

for thread in threads:
    thread.join()

print(counter)  # 2000
```

### Подробный разбор

Инкремент — логическая последовательность чтения значения, вычисления нового и записи обратно. Без блокировки переключение между потоками может привести к потерянным обновлениям. `threading.Lock` гарантирует, что в критической секции `counter += 1` одновременно находится только один поток.

Каждый поток делает 1000 инкрементов, всего их 2000. `join()` ждёт завершения каждого потока, поэтому печать происходит после всех операций. GIL не стоит считать заменой блокировке: корректность разделяемого состояния должна обеспечиваться явной синхронизацией.
