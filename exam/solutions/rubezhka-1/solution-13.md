# Рубежка №1 — билет 13: точные условия и подробные решения

## Теоретический вопрос 25 — условие из файла

> Почему backend нельзя свести только к REST API или только к базе данных? Перечислите обязанности серверного приложения на примере управления студентами и объясните связь между ними.

### Подробный ответ

Backend — это серверная часть приложения, а не синоним HTTP-маршрутов или базы данных. Он принимает запросы, проверяет структуру данных и права пользователя, выполняет бизнес-правила, взаимодействует с хранилищем, обрабатывает ошибки и формирует HTTP-ответ.

В системе студентов путь может выглядеть так:
1. Controller принимает `POST /students` и разбирает запрос.
2. Валидация проверяет, что ИСУ — допустимое число, группа задана корректно, обязательные поля присутствуют.
3. Проверка доступа определяет, может ли этот пользователь создавать или менять записи.
4. Service выполняет бизнес-правила, например проверяет уникальность ИСУ.
5. Repository взаимодействует с БД; БД обеспечивает долговременное хранение и ограничения целостности.
6. Обработчик ошибок переводит известные ситуации в подходящие HTTP-статусы, а приложение возвращает JSON-ответ.

REST API — способ представления интерфейса взаимодействия. База хранит данные, но сама по себе не реализует полный сценарий доступа, бизнес-проверок и формирования ответа. Все компоненты связаны общим контрактом и согласованными правилами.

## Теоретический вопрос 26 — условие из файла

> Чем Decorator и Proxy похожи внешне и чем отличаются по назначению? Приведите примеры из инфраструктуры backend, соответствующие этой разнице.

### Подробный ответ

Decorator и Proxy могут оба оборачивать объект и предоставлять тот же или похожий интерфейс. Различается цель.

- **Decorator** добавляет объекту дополнительное поведение через обёртку, например логирование, метрики, кэширование или дополнительную проверку до делегирования вызова.
- **Proxy** представляет объект-заместитель и контролирует доступ к реальному объекту: например, проверяет разрешение, откладывает создание/загрузку объекта или перенаправляет вызов к удалённому ресурсу.

В backend декоратор репозитория мог бы добавлять сбор метрик, не изменяя сам репозиторий. Proxy в Spring может перехватывать вызов сервисного метода для транзакционного управления или аспектов. В реальных реализациях механизмы могут пересекаться: прокси также может добавлять поведение, поэтому главное отличие — назначение, а не просто наличие оболочки.

**Прямой ответ:** Decorator в первую очередь расширяет поведение; Proxy в первую очередь управляет доступом к представляемому объекту или способом вызова.

## Практическое задание 13 — условие из файла

> На Python напишите минимальные классы StudentRepository (хранит студентов в словаре и ищет по ID) и StudentService с методом get_student(isu_id). Сервис не должен сам создавать репозиторий.

### Решение

```python
class StudentRepository:
    def __init__(self):
        self._students = {}

    def add(self, student):
        self._students[student["isu_id"]] = student

    def get_by_id(self, isu_id):
        return self._students.get(isu_id)


class StudentService:
    def __init__(self, repository):
        self._repository = repository

    def get_student(self, isu_id):
        student = self._repository.get_by_id(isu_id)
        if student is None:
            raise LookupError(f"Student {isu_id} not found")
        return student
```

### Подробный разбор

- Repository инкапсулирует хранение: вызывающий код не должен напрямую менять внутренний словарь.
- `get_by_id` возвращает найденную запись или `None`.
- Service содержит сценарий получения студента и определяет поведение, если записи нет.
- Репозиторий передаётся в `StudentService` в конструкторе. Сервис не создаёт его сам, что выполняет требование о DI и позволяет подменить хранилище на тестовый объект.

Минимальный пример использует словарь и словари-студенты для краткости. В полноценном приложении лучше ввести тип Student и доменное исключение, а слой API должен преобразовать отсутствие записи в HTTP 404.
