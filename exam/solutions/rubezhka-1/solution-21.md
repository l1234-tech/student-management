# Рубежка №1 — билет 21: точные условия и подробные решения

## Теоретический вопрос 41 — условие из файла

> Как контейнер Spring находит, создаёт и связывает компоненты, помеченные аннотациями? Чем управляемый бин отличается от объекта того же класса, созданного оператором new?

### Подробный ответ

Spring контейнер (обычно ApplicationContext) запускает обработку конфигурации, обнаруживает компоненты через component scanning и аннотации вроде `@Component`, `@Service`, `@Repository`, `@Controller` или через методы `@Bean`. На основе метаданных определяются BeanDefinition: из какого класса/фабрики создать объект, какая область видимости и какие зависимости нужны. Затем контейнер создаёт объекты, внедряет зависимости, выполняет пост-обработку и управляет жизненным циклом.

**Spring bean** — объект, созданием и конфигурацией которого управляет контейнер: он может получить зависимости, участвовать в callback жизненного цикла, быть обёрнут прокси для транзакций или аспектов. Объект, который разработчик создал самостоятельно через `new`, не регистрируется в контейнере автоматически; Spring не внедрит ему зависимости и не применит к нему контейнерные post-processors, если это отдельно не сделано.

Аннотация сама по себе не «магически делает объект Spring bean»: класс должен быть обнаружен или объявлен как bean-конфигурация.

## Теоретический вопрос 42 — условие из файла

> Почему значение зависимости, внедряемой в поле контейнером, может быть недоступно в конструкторе, но доступно после инициализации? Объясните различие между конструктором, @PostConstruct и стадией работы с готовым прокси.

### Подробный ответ

При field injection последовательность обычно такова: контейнер создаёт экземпляр и выполняет конструктор; затем внедряет значения в поля; затем вызывает callback инициализации, включая `@PostConstruct`; позже бин может пройти дальнейшую пост-обработку и быть обёрнут прокси.

Поэтому в конструкторе поле, которое контейнер должен заполнить после создания объекта, ещё имеет значение по умолчанию (например, `null`). В `@PostConstruct` такое поле уже обычно внедрено, поэтому там доступны действия, которым нужны зависимости. Однако вызов методов прокси-зависимого поведения внутри инициализации надо проектировать аккуратно: прокси текущего бина может быть ещё не готов на конкретном этапе, а некоторые механизмы AOP/транзакций не работают так, как после полной инициализации.

Constructor injection меняет эту ситуацию: обязательная зависимость передаётся параметром, и объект может использовать её в конструкторе. Это одна из причин, по которой внедрение через конструктор часто предпочтительнее.

## Практическое задание 21 — условие из файла

> На Java/Spring напишите бин StudentService, который при старте приложения, когда все зависимости уже внедрены, запоминает момент запуска. Время берите из бина Clock.

### Решение

```java
import java.time.Clock;
import java.time.Instant;
import jakarta.annotation.PostConstruct;
import org.springframework.stereotype.Service;

@Service
public class StudentService {
    private final Clock clock;
    private Instant startedAt;

    public StudentService(Clock clock) {
        this.clock = clock;
    }

    @PostConstruct
    public void initialize() {
        this.startedAt = Instant.now(clock);
    }

    public Instant getStartedAt() {
        return startedAt;
    }
}
```

### Конфигурация Clock

Если в контексте ещё нет бина Clock, его можно объявить, например:

```java
@Configuration
public class TimeConfig {
    @Bean
    public Clock clock() {
        return Clock.systemUTC();
    }
}
```

### Подробный разбор

Spring сначала внедряет `Clock` через конструктор. После создания и внедрения зависимости контейнер вызывает `@PostConstruct`, поэтому в `initialize()` можно сохранить время. `Instant.now(clock)` использует предоставленные часы, а не напрямую системное глобальное время.

Преимущество Clock injection — тестируемость: тест может передать `Clock.fixed(...)` и сравнить точный результат без зависимости от реального времени. Импорты `jakarta.annotation.PostConstruct` соответствуют современным версиям Spring; в старых проектах пакет может отличаться.
