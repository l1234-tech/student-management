# Рубежка №1 — билет 11: точные условия и подробные решения

## Теоретический вопрос 21 — условие из файла

> Чем организация проекта по слоям отличается от организации по функциональным областям? В какой ситуации структура controllers/services/repositories начинает мешать?

### Подробный ответ

Организация **по слоям** группирует код по технической роли: controllers обрабатывают HTTP, services содержат сценарии и бизнес-правила, repositories отвечают за доступ к хранилищу. Организация **по функциональным областям** собирает в одном модуле всё, что относится к одной предметной области или фиче, например студентам, группам или общежитиям; внутри этого модуля могут оставаться слои.

Структура controllers/services/repositories начинает мешать, когда изменение одной функции вынуждает искать связанные файлы по множеству каталогов, в которых лежат компоненты разных функций. Для маленького проекта структура по слоям может быть понятнее; для большого часто удобна комбинация: сначала функциональная область, а внутри — контроллеры, сервисы и доступ к данным. Главная цель — сделать ответственность и зависимости очевидными, а не добиться определённого количества папок.

## Теоретический вопрос 22 — условие из файла

> Что изменяет Dependency Injection в способе создания сервисов и репозиториев? Почему «зависимость передаётся извне» обычно лучше, чем «сервис самостоятельно конструирует всё, что использует»?

### Подробный ответ

Dependency Injection (DI, внедрение зависимостей) — подход, при котором объект получает необходимые зависимости от вызывающего кода или контейнера, вместо того чтобы самостоятельно создавать конкретные реализации.

```java
@Service
public class StudentService {
    private final StudentRepository repository;

    public StudentService(StudentRepository repository) {
        this.repository = repository;
    }
}
```

Здесь сервис не создаёт репозиторий через `new`, а получает его в конструкторе. Благодаря этому уменьшается связанность: сервису важно, чтобы объект удовлетворял нужному контракту, а не как именно он создан. В тестах можно передать fake/mock-репозиторий, а в приложении Spring контейнер выберет управляемый бин.

**Прямой ответ:** DI упрощает замену реализации, изолированное тестирование и управление жизненным циклом объектов; конструктор делает обязательные зависимости явными. Если сервис сам создаёт всё, что использует, его труднее тестировать и конфигурировать, потому что создание и бизнес-логика оказываются смешаны.

## Практическое задание 11 — условие из файла

> Напишите JavaScript-функцию saveStudent(student), отправляющую JSON методом POST на /api/students. При HTTP-ошибке она должна бросать Error с кодом статуса, при успешном ответе — возвращать объект из JSON.

### Решение

```js
async function saveStudent(student) {
  const response = await fetch("/api/students", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "Accept": "application/json"
    },
    body: JSON.stringify(student)
  });

  if (!response.ok) {
    throw new Error(`HTTP error: ${response.status}`);
  }

  return await response.json();
}
```

### Подробный разбор

1. `fetch` выполняет POST-запрос по адресу `/api/students`.
2. `JSON.stringify(student)` превращает JS-объект в JSON-строку, а `Content-Type` сообщает серверу формат тела.
3. `Accept` указывает, что клиент ожидает JSON в ответе.
4. `fetch` обычно не выбрасывает исключение для статусов 400 или 500, поэтому надо явно проверить `response.ok`.
5. В ошибке используется `response.status`, что выполняет условие о коде статуса.
6. При успехе `response.json()` читает JSON-тело и возвращает разобранный JS-объект.

Это предполагает, что успешный endpoint возвращает JSON, как сказано в условии. Если реальный API возвращает 204 No Content, читать JSON не следует; тогда контракт функции нужно изменить.
