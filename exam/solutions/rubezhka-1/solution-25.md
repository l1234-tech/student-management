# Рубежка №1 — билет 25: точные условия и подробные решения

## Теоретический вопрос 49 — условие из файла

> Почему Spring Security выполняет проверку пользователя до входа в Spring MVC-контроллер? Объясните роль SecurityFilterChain, AuthenticationManager и SecurityContext.

### Подробный ответ

Проверять безопасность до вызова контроллера нужно, чтобы запрещённый запрос не достиг бизнес-логики и не прочитал/изменил данные. В Spring Security запрос сначала проходит фильтры безопасности, а только затем маршрутизируется Spring MVC, если проверка допускает продолжение.

- **SecurityFilterChain** содержит последовательность фильтров безопасности и правила, которые применяются к запросу.
- **AuthenticationManager** координирует процесс аутентификации, передавая запросы соответствующему AuthenticationProvider.
- **SecurityContext** хранит Authentication текущего выполнения запроса: кто аутентифицирован и какие authorities/roles ему назначены.

Для JWT фильтр извлекает Bearer token из Authorization, проверяет подпись и обязательные claims, формирует Authentication и помещает его в SecurityContext. Дальше правила авторизации решают, разрешено ли конкретному пользователю читать/изменять записи. Аутентификация отвечает «кто ты?», авторизация — «что тебе разрешено?».

## Теоретический вопрос 50 — условие из файла

> Почему хранить пароли в открытом виде или в виде простого SHA-256 небезопасно? Объясните назначение случайной соли и медленных алгоритмов BCrypt/Argon2id.

### Подробный ответ

Открытый пароль сразу раскрывается при утечке БД. Простой SHA-256 тоже непригоден как самостоятельный password hashing: это быстрый алгоритм, поэтому злоумышленник может проверять очень много догадок в секунду, используя словари и видеокарты.

Соль — случайное уникальное значение, которое включается в вычисление хеша пароля. Она препятствует использованию готовых таблиц и гарантирует, что одинаковые пароли обычно имеют разные сохранённые хеши. Соль не обязана быть секретной, но должна храниться вместе с параметрами хеширования.

BCrypt и Argon2id созданы для хранения паролей и позволяют настраивать стоимость вычисления (Argon2id также позволяет регулировать память). Это делает массовый перебор дороже. При входе сервер получает введённый пароль и проверяет его специализированным методом вроде `PasswordEncoder.matches`; он не расшифровывает сохранённый хеш.

## Практическое задание 25 — условие из файла

> На Java/Spring Security напишите SecurityFilterChain для REST API: GET /students/** разрешён ролям USER и ADMIN; изменение /students/** разрешено только ADMIN; остальные запросы требуют аутентификацию. Клиенты передают JWT в Authorization; настройте сессии и CSRF соответственно.

### Решение

```java
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    return http
        .csrf(csrf -> csrf.disable())
        .sessionManagement(session -> session
            .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers(HttpMethod.GET, "/students/**")
                .hasAnyRole("USER", "ADMIN")
            .requestMatchers("/students/**")
                .hasRole("ADMIN")
            .anyRequest()
                .authenticated())
        .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()))
        .build();
}
```

### Подробный разбор

- Правило GET проверяется первым: чтение `/students/**` разрешено ролям USER и ADMIN.
- Остальные методы на `/students/**` разрешены только ADMIN.
- `anyRequest().authenticated()` требует аутентификацию для остальных маршрутов.
- `STATELESS` говорит Spring Security не хранить пользовательское состояние в HTTP-сессии: запросы должны самостоятельно передавать credentials, в условии — JWT в заголовке Authorization.
- Конфигурация resource server с JWT подключает соответствующий механизм обработки Bearer-токена, но в реальном приложении также нужен корректно настроенный JwtDecoder/issuer и преобразование claims в authorities.

CSRF отключён здесь на основании условия о stateless REST API с явным Authorization: Bearer JWT. Это решение корректно только если браузер не прикладывает credentials автоматически. Если JWT/сессия передаются cookie, CSRF-защита, наоборот, нужна. В реальном приложении важно явно ограничить CORS и настроить HTTPS.
