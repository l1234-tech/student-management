# Лабораторная №4 — вопросы и развёрнутые ответы

Источник формулировок: ТЗ «Лабораторная работа №4. Frontend на JavaScript-фреймворке». Практические примеры привязаны к реализации Vue 3 в каталоге [4 lab](../../4%20lab/README.md) и к backend лабораторной №3.

## 1. JavaScript-фреймворки: React, Vue, Angular, Svelte. Основные особенности и различия

JavaScript-фреймворк или UI-библиотека предоставляет способ описывать интерфейс декларативно, разбивать его на компоненты и обновлять отображение при изменении данных. Вместо ручного поиска DOM-элементов и изменения их свойств разработчик описывает, какой интерфейс должен соответствовать текущему состоянию.

**React** — библиотека для построения интерфейсов. Использует компоненты-функции, JSX, props и hooks. Состояние обычно организуется через useState/useReducer и дополнительные библиотеки. React сам по себе не задаёт всю структуру приложения: маршрутизация и глобальное состояние выбираются отдельно.

**Vue** — прогрессивный фреймворк с шаблонами, реактивными ref/reactive, Composition API и однофайловыми компонентами .vue. В проекте используется Vue 3 Composition API, Vue Router для маршрутов и Pinia для глобального состояния.

**Angular** — комплексный фреймворк на TypeScript с DI, сервисами, маршрутизатором, формами и CLI. Он задаёт больше архитектурных соглашений и встроенных инструментов.

**Svelte** компилирует компоненты в эффективный JavaScript во время сборки; реактивность встроена в язык/компилятор, отдельный Virtual DOM не является центральным механизмом.

Общее: компонентный подход, декларативный UI, реактивное обновление. Отличаются моделью реактивности, синтаксисом, инструментами и степенью встроенной инфраструктуры. В этой лабораторной конкретный выбор — Vue; RxJS обязателен независимо от фреймворка.

## 2. SPA и клиентская маршрутизация. Принципы работы одностраничных приложений

SPA (Single Page Application) загружает базовый HTML-документ один раз, а затем меняет содержимое интерфейса средствами JavaScript. Переходы между разделами обычно не требуют полной перезагрузки документа: клиентский маршрутизатор сопоставляет URL с компонентом страницы, а приложение загружает необходимые данные через API.

В Vue Router маршрут связывается с компонентом страницы. Например, `/login` отображает страницу входа, `/register` — регистрации, `/students` — список, а `/students/:isu` — карточку студента. RouterView — место, в котором отображается компонент текущего маршрута; RouterLink создаёт навигационные ссылки.

Преимущества SPA: плавная навигация, повторное использование загруженных ресурсов, сохранение состояния между переходами. Недостатки: первоначальная загрузка JavaScript, необходимость самостоятельно организовать маршрутизацию и загрузку данных, вопросы SEO и доступности контента до выполнения JS. Для лабораторной №4 используется SPA; SSR и метафреймворк относятся к следующей лабораторной.

## 3. Компонентная архитектура. Компоненты, props, события и взаимодействие между компонентами

Компонент — самостоятельная часть интерфейса с ограниченной ответственностью. Он может содержать шаблон, логику и стили, принимать входные данные, хранить локальное состояние и генерировать события. Компоненты позволяют повторно использовать интерфейс и изолировать изменения.

В Vue данные от родителя к ребёнку передаются через **props**. Props описывают входной контракт и не должны напрямую изменяться дочерним компонентом. Для передачи события от ребёнка родителю применяется `emit`: например, форма сообщает, что пользователь нажал «Сохранить», а родитель выполняет запрос и обновляет состояние.

В проекте примеры компонентного разделения: StudentsPage координирует список, StudentsTable отвечает за отображение строк, StudentFilters — за фильтры, StudentPagination — за навигацию по страницам, StudentForm — за ввод данных. Это лучше, чем помещать всю логику приложения в один компонент.

Если много промежуточных компонентов передают одни и те же props, возникает props drilling. Для действительно общего состояния применяют хранилище, например Pinia. Props при этом остаются удобным способом передавать локальные данные и настройки компонентов.

## 4. Жизненный цикл компонентов. Hooks и lifecycle-механизмы

Жизненный цикл — последовательность этапов существования компонента: создание, настройка реактивности, монтирование в DOM, обновления и размонтирование. На разных этапах могут понадобиться разные действия: загрузить данные после появления компонента, синхронизировать сторонний объект или очистить подписку перед удалением.

В Vue Composition API предоставляет lifecycle hooks: `onMounted`, `onUpdated`, `onUnmounted` и другие. `onMounted` вызывается после монтирования компонента и подходит для действий, которым нужен DOM. `onUnmounted` — место для очистки таймеров, обработчиков и подписок, созданных компонентом.

В React похожую роль часто выполняет useEffect с функцией очистки; Angular использует lifecycle hooks класса; Svelte предоставляет соответствующие lifecycle-функции. Названия и точная семантика различаются, поэтому нельзя механически переносить код между фреймворками.

Особенно важно освобождать RxJS Subscription при завершении жизненного цикла компонента, если поток не завершается самостоятельно. Иначе подписка может продолжить удерживать объекты и выполнять ненужную работу.

## 5. Рендеринг интерфейса. Virtual DOM, reconciliation и условный рендеринг

DOM — объектное представление HTML-документа в браузере. Прямые многочисленные изменения DOM вручную сложны для сопровождения. Многие фреймворки используют декларативное описание интерфейса и механизм согласования изменений.

Virtual DOM — структура объектов, описывающая предполагаемое дерево интерфейса. При изменении состояния фреймворк получает новое описание, сравнивает его с предыдущим и применяет необходимые изменения к реальному DOM. В React процесс сравнения называют reconciliation; Vue также использует Virtual DOM и алгоритм обновления дерева.

Virtual DOM не означает, что любое обновление автоматически быстрее ручного DOM во всех ситуациях: важны объём дерева, стабильные ключи, вычисления и количество изменений. При списках нужно указывать устойчивый `key`, чтобы фреймворк правильно сопоставлял элементы.

Условный рендеринг позволяет показывать элементы только при выполнении условия. В Vue `v-if` создаёт/удаляет фрагмент, а `v-show` переключает CSS display. Например, форма может показывать сообщение об ошибке только при наличии ошибки, а кнопку редактирования — только пользователю с ролью ADMIN.

## 6. Реактивность во frontend. Механизмы отслеживания изменений и обновления интерфейса

Реактивность — автоматическое отслеживание зависимостей между данными и вычислениями/шаблонами. Когда реактивное значение меняется, фреймворк определяет, какие вычисления и участки интерфейса зависят от него, и обновляет их.

В Vue 3 `ref` создаёт реактивное значение, доступное в JavaScript через свойство `.value`; `reactive` делает реактивным объект. `computed` описывает производное значение, которое пересчитывается при изменении зависимостей. `watch` следит за указанными источниками и запускает побочный эффект.

В проекте состояние списка, фильтров, загрузки и ошибок хранится в Pinia store; компоненты используют это состояние, а Vue обновляет интерфейс при изменениях. Не следует путать реактивность Vue и RxJS: Vue связывает данные с интерфейсом, а RxJS организует обработку последовательностей событий и асинхронных значений.

## 7. Управление состоянием. Локальное и глобальное состояние, инструменты state management

Состояние — данные, от которых зависит поведение или отображение интерфейса. **Локальное состояние** принадлежит одному компоненту: например, открыт ли выпадающий список или какое поле сейчас редактируется. **Глобальное состояние** используется несколькими независимыми компонентами или страницами: пользовательская сессия, роль, список студентов, параметры фильтрации.

В Vue локальное состояние часто создаётся через `ref` и `reactive`. Для общего состояния в этой лабораторной используется Pinia. Store позволяет централизовать данные, getters и actions, чтобы разные компоненты работали с согласованным состоянием.

В проекте есть auth store для текущего пользователя и токенов, а также students store для данных студентов, загрузки, ошибок и операций. Это отделяет отображение от управления данными. Альтернативы: React Context/Redux/Zustand, Angular Signals/NgRx, Svelte Stores/Runes.

Не нужно помещать в глобальное хранилище каждое локальное поле: это усложняет архитектуру. Глобальным должно быть то состояние, которому действительно нужны несколько потребителей или централизованные правила.

## 8. Реактивное программирование. Основные принципы и отличия от императивного подхода

Императивный подход описывает последовательность команд: получить событие, вручную вызвать функцию, изменить переменную, найти элемент DOM и обновить его. Реактивный подход описывает поток значений и преобразования над ним: при поступлении нового значения поток автоматически проходит через цепочку операторов и передаёт результат подписчикам.

Реактивное программирование особенно полезно для событий, которые поступают во времени: ввод текста, клики, сетевые ответы, таймеры, события WebSocket. Вместо большого количества вложенных обработчиков можно задать декларативную цепочку преобразований, фильтрации и объединения.

RxJS — библиотека для работы с Observable-потоками. Observable описывает источник последовательности значений; оператор преобразует или комбинирует поток; подписчик получает результат. Важная особенность: Observable может выдать много значений, завершиться или сообщить об ошибке.

В лабораторной №4 RxJS используется практически для поиска студентов: поток ввода преобразуется, одинаковые значения отбрасываются, запрос откладывается на короткое время, а устаревший запрос отменяется при появлении нового ввода.

## 9. RxJS. Observable, Observer, Subject, BehaviorSubject и Subscription

**Observable** — описание потока, который может передавать значения, ошибку и сигнал завершения. Подписка запускает или подключает потребителя к потоку. **Observer** — объект с обработчиками `next`, `error` и `complete`. **Subscription** — объект, представляющий активную подписку; метод `unsubscribe()` прекращает получение значений.

**Subject** одновременно является Observable и Observer: в него можно отправлять значения методом `next`, а подписчики получают их. Он часто используется для публикации событий нескольким потребителям. **BehaviorSubject** хранит последнее значение и немедленно отдаёт его новому подписчику; поэтому он удобен для представления текущего состояния.

Обычный Observable может быть cold: каждый подписчик запускает независимое выполнение источника. Subject обычно hot: подписчики наблюдают общий поток событий, который уже может идти. Это различие влияет на количество сетевых запросов и распределение событий.

В поисковом composable проекта создаётся поток событий поиска, который обрабатывается операторами RxJS. Подписку нужно корректно завершать, чтобы не оставлять активную работу после ухода со страницы.

## 10. Операторы RxJS. Преобразование, фильтрация, комбинирование и обработка потоков данных

Операторы RxJS — функции, позволяющие строить конвейер обработки Observable. Они не изменяют исходный поток на месте, а возвращают новый Observable с преобразованным поведением.

Основные группы:
- преобразование: `map`, `switchMap`, `mergeMap`, `concatMap`;
- фильтрация: `filter`, `distinctUntilChanged`, `take`;
- временная обработка: `debounceTime`, `throttleTime`, `delay`;
- комбинирование: `combineLatest`, `merge`, `zip`;
- обработка ошибок: `catchError`, `retry`, `finalize`.

Для поля поиска важны `debounceTime` и `distinctUntilChanged): первый ждёт паузу после ввода, второй не пропускает подряд одинаковые значения. `switchMap` переключается на новый внутренний Observable и отписывается от предыдущего, поэтому старый поисковый запрос перестаёт быть актуальным.

В реализации проекта запросы выполняются через fetch с AbortController, чтобы отмена предыдущей RxJS-ветки также прерывала сетевую операцию. `catchError` позволяет обработать ошибку отдельного запроса и сохранить работоспособность внешнего потока.

## 11. Асинхронные потоки. Hot и cold Observable, управление подписками и предотвращение утечек памяти

Cold Observable начинает выполнение отдельно для каждого подписчика. Например, Observable, созданный из функции, может заново выполнить операцию при каждой подписке. Hot Observable представляет общий источник событий, например ввод пользователя или Subject: несколько подписчиков наблюдают одну и ту же последовательность.

Управление подписками необходимо, потому что подписка может удерживать ссылки на компоненты и продолжать выполнять обработчики после того, как компонент больше не нужен. Это создаёт утечки памяти, лишние запросы и неожиданные изменения состояния.

Подписки следует завершать через `unsubscribe()`, использовать операторы жизненного цикла (например, takeUntil) или механизм автоматического связывания с уничтожением компонента. Для одноразовых потоков, которые завершаются самостоятельно, ручная очистка обычно не требуется, но это нужно понимать по источнику.

В сценарии поиска `switchMap` отменяет предыдущую внутреннюю операцию при новом значении. Это решает проблему устаревших запросов, но не отменяет необходимость корректно закрывать внешнюю подписку при уничтожении владельца composable/компонента.

## 12. Реактивная обработка пользовательских событий. Поиск, фильтрация и отмена устаревших запросов

Поле поиска генерирует много событий — практически по одному на каждый введённый символ. Если немедленно отправлять запрос на каждый символ, сервер получает лишнюю нагрузку, а ответы могут прийти в неправильном порядке: запрос для старого текста иногда завершится позже нового и перезапишет актуальный результат.

Обычно применяют цепочку: событие ввода → нормализация строки → debounce → удаление повторов → запрос → отображение результата. `debounceTime(300)` ждёт 300 мс тишины; `distinctUntilChanged` пропускает только изменившееся значение; `switchMap` переключается на запрос для последнего значения и отменяет предыдущий.

Отмена важна не только для производительности, но и для корректности данных: на экране должен оставаться результат последнего актуального запроса. В проекте RxJS-поиск находится в `src/composables/useStudentSearch.js`, а API-обращения — в `src/api/students.js`.

Фильтры по полям студента могут отправляться как единый объект поиска. Серверная фильтрация нужна даже при наличии клиентского интерфейса фильтров: backend остаётся источником достоверных данных и применяет права доступа.

## 13. Клиентская валидация, обработка ошибок и управление состояниями загрузки

Клиентская валидация проверяет данные до отправки: обязательные поля, формат email, длину пароля, диапазоны чисел и другие ограничения. Она улучшает UX и позволяет сразу показать понятное сообщение. Но клиенту нельзя доверять как единственному уровню защиты: пользователь может отключить JavaScript или отправить HTTP-запрос вручную. Поэтому backend лабораторной №3 повторно проверяет данные.

Асинхронная операция должна иметь как минимум состояния loading, success и error. Пока запрос выполняется, следует показывать индикатор загрузки и блокировать повторную отправку формы. При ошибке пользователю нужно сообщить понятную причину, не показывая внутренние трассировки или секреты сервера.

В проекте есть общие ErrorMessage и LoadingIndicator, а HTTP-клиент обрабатывает сетевые и серверные ошибки. Нужно различать 401 (нет действительной аутентификации), 403 (доступ запрещён), 404 (ресурс отсутствует), 409 (конфликт), 422 (ошибка валидации) и 5xx (ошибка сервера).

## 14. Аутентификация и авторизация. JWT, access- и refresh-токены

Аутентификация отвечает на вопрос «кто пользователь?», авторизация — «что ему разрешено?». После входа backend выдаёт JWT. Клиент прикладывает access token к защищённым запросам, обычно в заголовке `Authorization: Bearer <token>`.

Access token короткоживущий и используется для доступа к API. Refresh token имеет более длительный срок жизни и предназначен для получения новой пары токенов после истечения access token. Refresh token нельзя использовать вместо access token для обычного запроса к ресурсу.

В проекте лабораторной №4 auth store управляет сессией, а HTTP-клиент добавляет Bearer-токен и при 401 пытается обновить токены через refresh endpoint. Повторный запрос ограничен, чтобы не создать бесконечный цикл. Logout отзывает refresh-сессию на backend и очищает клиентское состояние.

JWT обычно подписан, а не зашифрован: payload можно прочитать, поэтому в него нельзя помещать пароль или секретные данные. Подпись позволяет проверить целостность и подлинность токена.

## 15. Защита маршрутов и разграничение доступа на основе ролей

Защита маршрутов на frontend управляет навигацией и UX: неавторизованного пользователя перенаправляют на login, а пользователя без нужной роли не пускают на страницу административной операции. В Vue Router это реализуется через route guards и метаданные маршрутов, например требование авторизации или роли ADMIN.

Но frontend-защита не является границей безопасности. Пользователь может вручную вызвать API через curl/Postman, минуя интерфейс. Поэтому backend лабораторной №3 обязан независимо проверять JWT и роль для каждого защищённого endpoint.

В проекте USER может просматривать студентов и карточки, но не может создавать, редактировать или удалять записи. ADMIN имеет права на все операции. Регистрация создаёт обычного USER; назначение ADMIN выполняется серверной конфигурацией, а не выбором роли в форме регистрации.

Важно различать 401 и 403: 401 означает, что пользователь не аутентифицирован или токен недействителен; 403 означает, что личность установлена, но прав на операцию недостаточно.

## 16. Безопасность frontend-приложений. XSS, CSRF и основные способы защиты

XSS (Cross-Site Scripting) возникает, когда недоверенные данные интерпретируются браузером как исполняемый HTML/JavaScript. Атакующий может внедрить скрипт, который действует в контексте сайта. Защита включает контекстное экранирование, безопасный вывод текста, отказ от опасного `v-html` для непроверенных данных, Content Security Policy и обновление зависимостей.

CSRF (Cross-Site Request Forgery) — принуждение браузера авторизованного пользователя отправить нежелательный запрос на сайт. Особенно актуально для аутентификации через автоматически отправляемые cookies. Защита: SameSite cookies, CSRF-токены, проверка Origin/Referer и корректные методы/политики CORS. Bearer-токен в заголовке не отправляется браузером автоматически на чужом сайте, но хранение токена в доступном JavaScript месте повышает последствия XSS.

В проекте access/refresh токены хранятся в sessionStorage. Это не защищает от XSS: скрипт в том же origin может прочитать токены. HttpOnly Secure cookies уменьшили бы доступность токена для JS, но потребовали бы соответствующей поддержки backend и CSRF-защиты.

CORS — не универсальная защита от CSRF и не механизм аутентификации; это политика браузера, определяющая доступность ответов cross-origin JavaScript.

## 17. Архитектура frontend-приложения. Разделение ответственности и организация проекта

Архитектура делит приложение на части с ясными обязанностями. Страницы связывают сценарии, компоненты отображают повторно используемые блоки, stores управляют общим состоянием, API-модули отвечают за HTTP, composables инкапсулируют повторяемую логику, router определяет навигацию, styles содержат оформление.

В каталоге `4 lab/src` это разделение видно по папкам:
- `pages` — страницы приложения;
- `components` — таблица, фильтры, форма, пагинация и общие UI-состояния;
- `stores` — Pinia stores авторизации и студентов;
- `api` — HTTP-клиент и функции работы с endpoint'ами;
- `composables` — RxJS-поиск;
- `router` — маршруты и проверки доступа;
- `styles` — общие стили.

Такой подход облегчает тестирование и изменение: например, смена URL API не должна требовать переписывания таблицы, а смена внешнего вида кнопки не должна затрагивать бизнес-логику.

## 18. Docker и контейнеризация. Dockerfile, образы и контейнеры

Контейнеризация упаковывает приложение и его окружение в воспроизводимый образ. **Dockerfile** — инструкция сборки образа; **image** — неизменяемый шаблон файловой системы и конфигурации; **container** — запущенный экземпляр образа с изолированными процессами, сетью и файловой системой.

Контейнер помогает одинаково запускать приложение на разных машинах, уменьшает зависимость от локально установленных версий Node/Java и упрощает развертывание. Он не является виртуальной машиной: контейнеры используют ядро операционной системы хоста.

В лабораторной №4 требуется контейнеризировать frontend и backend лабораторной №3. Dockerfile frontend описывает сборку Vue-приложения, Dockerfile.backend — сборку Spring Boot backend. Параметры окружения передаются отдельно, секреты не должны попадать в исходный код или образ.

## 19. Многоэтапная сборка Docker. Сборка frontend и раздача статических файлов через Nginx

Multi-stage build использует несколько стадий одного Dockerfile. На первой стадии устанавливаются зависимости и собирается приложение; на последнюю копируются только артефакты, необходимые для запуска. Поэтому в production-образ не обязательно включать исходники, npm и весь набор build-зависимостей.

Для Vue/Vite типичный процесс: Node-образ выполняет npm ci и npm run build, получая каталог dist; затем Nginx-образ получает dist и конфигурацию веб-сервера. Nginx раздаёт статические файлы и может проксировать API-запросы к backend.

Преимущества: меньший runtime-образ, меньше лишних инструментов, более чёткое разделение сборки и запуска. Nginx должен корректно обрабатывать SPA-маршруты: при запросе вложенного клиентского URL возвращать index.html, если это не существующий статический файл. Запросы /api/ должны проксироваться на backend, а не попадать в SPA fallback.

## 20. Docker Compose. Сети контейнеров, переменные окружения и взаимодействие frontend с backend

Docker Compose описывает несколько связанных сервисов в одном YAML-файле: образы или сборки, порты, переменные окружения, volumes, сети и зависимости. Команда `docker compose up --build` собирает необходимые образы и запускает сервисы.

В Compose контейнеры обычно обращаются друг к другу по имени сервиса и внутреннему порту, например frontend/Nginx → backend:8080, backend → db:5432. Публикация порта нужна для доступа с хоста; внутреннее взаимодействие контейнеров не должно использовать localhost, потому что localhost внутри контейнера указывает на сам контейнер.

В лабораторной №4 Compose запускает frontend через Nginx, backend из лабораторной №3 и PostgreSQL. Nginx проксирует `/api/` к backend, а backend подключается к БД по сетевому имени сервиса. Переменные DB_PASSWORD и параметры администратора задаются через .env; в репозитории хранится только .env.example без реальных секретов.

Volume позволяет сохранять данные БД между пересозданиями контейнеров. `docker compose down` останавливает и удаляет контейнеры/сеть, но обычно сохраняет volume; `docker compose down --volumes` удаляет и данные volume, поэтому применять эту команду нужно осознанно.

## Как связаны части проекта

Сценарий получения списка: пользователь открывает страницу → Vue Router выбирает StudentsPage → Pinia store запрашивает данные через API-модуль → HTTP-клиент добавляет access token → Nginx (в Docker) проксирует /api → Spring Security проверяет JWT и роль → StudentController вызывает StudentService → репозиторий обращается к PostgreSQL → JSON-ответ возвращается в store → Vue реактивно обновляет таблицу.

Для поиска добавляется RxJS-цепочка, которая уменьшает число запросов и отменяет устаревшие. Для создания/изменения/удаления backend отдельно проверяет роль ADMIN; скрытие кнопки на frontend не заменяет эту проверку.
