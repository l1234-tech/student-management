# Лабораторная №5 — вопросы и развёрнутые ответы

Источник формулировок: ТЗ «Лабораторная работа №5. Frontend на метафреймворке». Для варианта Vue целевой метафреймворк — **Nuxt**. В репозитории сохранена лабораторная №4 как исходная SPA-реализация; каталог `5 lab` содержит пока описание целевой реализации, а не готовый код лабораторной №5.

## 1. Метафреймворки: Next.js, Nuxt, SvelteKit, AnalogJS. Назначение и отличия от обычных frontend-фреймворков

UI-фреймворк решает прежде всего задачу построения интерфейса: компоненты, реактивность, состояние и обновление DOM. Метафреймворк строится поверх UI-фреймворка и добавляет инфраструктуру полноценного веб-приложения: файловую маршрутизацию, серверный рендеринг, серверную загрузку данных, middleware, обработку ошибок, сборку и серверный runtime.

**Next.js** расширяет React; **Nuxt** — Vue; **SvelteKit** — Svelte; **AnalogJS** — Angular. Конкретные API и соглашения различаются, но решаемые задачи во многом одинаковы. Для варианта Vue в лабораторной №5 используется Nuxt.

Nuxt предоставляет файловую маршрутизацию, layouts, серверный рендеринг, middleware, серверные обработчики через Nitro и средства получения данных. Это не означает, что бизнес-логика и база данных должны переехать из Spring Boot: по условию лабораторной Java-backend лабораторной №3 остаётся источником бизнес-правил и данных. Nuxt отвечает за frontend-возможности: SSR, навигацию, middleware и получение данных.

## 2. Ограничения SPA. Клиентский и серверный рендеринг: CSR и SSR

При CSR (Client-Side Rendering) сервер отдаёт базовую HTML-оболочку и JavaScript-бандлы. Браузер загружает и выполняет JavaScript, приложение запрашивает данные и формирует интерфейс. Поэтому до загрузки и выполнения JS пользователь может видеть пустой экран или индикатор загрузки.

Ограничения CSR: первый контент может появляться позднее; поисковому роботу или клиенту без выполнения JS сложнее получить содержимое; первоначальная загрузка зависит от размера JS и сети. После загрузки SPA переходы могут быть быстрыми, потому что приложение уже работает в браузере.

При SSR (Server-Side Rendering) HTML страницы формируется на сервере и отправляется браузеру уже с содержимым. Это может улучшить скорость появления первого контента и доступность содержимого для поисковых систем. После этого браузер загружает клиентский JavaScript и гидратирует страницу, чтобы сделать её интерактивной.

SSR не устраняет задержки API и базы данных: если сервер долго получает данные из Spring Boot, он так же долго формирует HTML. SSR также требует учитывать серверное окружение, нагрузку и согласованность первоначального HTML с клиентским рендерингом.

## 3. Стратегии рендеринга: CSR, SSR, SSG, ISR. Преимущества, недостатки и сценарии применения

**CSR** — интерфейс формируется в браузере после загрузки JS. Подходит для закрытых интерактивных приложений, где SEO не критично и данные часто меняются. Минус — первый контент может появляться позднее.

**SSR** — HTML формируется на сервере на каждый запрос или при необходимости. Подходит для персонализированных страниц и данных, которые должны быть актуальными при открытии. Минусы — нагрузка на сервер и зависимость времени ответа от серверных запросов.

**SSG (Static Site Generation)** — HTML создаётся во время сборки. Готовые файлы можно раздавать через CDN очень быстро. Хорошо для документации, маркетинговых страниц и контента, который меняется редко. Недостаток — после изменения данных нужна новая генерация или механизм обновления.

**ISR (Incremental Static Regeneration)** — статическая страница обновляется постепенно по заданной политике или событию, а не только полной пересборкой всего сайта. Позволяет совместить скорость статики и обновляемость.

Нельзя сказать, что одна стратегия всегда лучшая. Выбор зависит от актуальности данных, персонализации, SEO, нагрузки и допустимой задержки. Для списка студентов с авторизацией могут потребоваться динамические данные, а публичные справочные страницы можно генерировать статически.

## 4. Гибридный рендеринг. Совмещение серверного и клиентского рендеринга

Гибридный рендеринг — использование разных стратегий в одном приложении или даже на разных участках одной страницы. Например, публичная справочная страница может быть статической, список студентов — серверно отрендеренным с учётом пользователя, а интерактивная форма — работать на клиенте.

Метафреймворк позволяет выбирать стратегию по маршруту и по типу данных. Это важно, потому что разные страницы имеют разные требования. Страница профиля зависит от текущей сессии и не должна быть общей статической страницей для всех. Страница ошибки или 404 может иметь простой серверный рендеринг.

В лабораторной №5 сохраняется функциональность лабораторной №4, но добавляются серверный рендеринг и метафреймворковые механизмы. При проектировании нужно решить, какие данные безопасно получать на сервере, какие действия требуют браузера и как передавать результат первоначального получения данных клиенту.

## 5. Hydration. Назначение, принцип работы и проблема Hydration Mismatch

Hydration (гидратация) — процесс, при котором клиентский JavaScript подключается к HTML, уже сформированному сервером, и связывает его с компонентами, состоянием и обработчиками событий. Серверный HTML позволяет раньше показать контент, а гидратация делает его интерактивным без полной перезагрузки документа.

Hydration mismatch возникает, когда первоначальная разметка, которую сформировал сервер, отличается от разметки, которую браузер ожидает при гидратации. Например, сервер отрендерил дату/время в одной временной зоне, а клиент — в другой; компонент использовал случайное число; браузерное хранилище было прочитано до гидратации; ветвление зависело от `window`.

Чтобы избежать mismatch, первоначальный рендер должен быть детерминированным и одинаковым на сервере и клиенте. Данные из localStorage/sessionStorage, window, document и других browser-only API нужно читать в клиентских lifecycle hooks или в клиентских компонентах после гидратации. Если данные зависят от пользователя, их нужно передавать согласованно через серверный контекст/сессию.

## 6. Streaming SSR. Потоковая передача HTML и постепенная загрузка содержимого

Обычный SSR часто ждёт завершения необходимых операций, прежде чем отдать готовую страницу. Streaming SSR позволяет отправлять HTML частями по мере готовности отдельных участков. Сначала браузер получает shell страницы и fallback для ещё не готовых блоков, затем — содержимое этих блоков.

Это полезно, когда на странице несколько независимых запросов, которые завершаются с разной скоростью. Например, шапка и каркас списка студентов могут появиться раньше, чем подробная статистика или дополнительные данные. Пользователь видит прогресс, не ожидая самый медленный участок.

Streaming не ускоряет сами запросы к API и не делает медленную БД быстрее. Он меняет порядок доставки уже готовых частей и улучшает воспринимаемую скорость. В React часто обсуждают Suspense boundaries; в других метафреймворках механизмы и API отличаются, поэтому важно объяснять общий принцип, а не переносить React API напрямую в Nuxt.

## 7. Серверные и клиентские компоненты. Особенности выполнения кода в разных окружениях

В метафреймворке код может выполняться на сервере, в браузере или в обоих окружениях. Серверный код имеет доступ к серверному контексту и может безопасно обращаться к приватным переменным окружения, но не имеет browser API вроде window/document. Клиентский код может работать с DOM, событиями мыши, localStorage и sessionStorage, но секреты в нём недоступны безопасно хранить.

Термины Server Components и Client Components особенно характерны для React/Next.js и не являются универсальными названиями для всех метафреймворков. В Nuxt важно различать серверное выполнение, клиентское выполнение, универсальные компоненты и специальные client-only/server-only участки.

Для Student Management серверная часть Nuxt может получить данные для первого отображения, а интерактивные формы, таблица, поиск и управление состоянием работают в браузере. Однако запросы к Java-backend должны учитывать авторизацию: нельзя случайно передать токен или секрет в HTML, сериализуемые props либо публичную конфигурацию.

## 8. Файловая маршрутизация. Динамические маршруты, вложенные страницы и Layouts

Файловая маршрутизация связывает структуру файлов проекта с URL. В Nuxt страницы размещаются в каталоге `pages`; имя файла задаёт путь, а динамический сегмент записывается в квадратных скобках. Например, `pages/students/[id].vue` соответствует адресу `/students/123`, где 123 доступен как параметр маршрута.

Вложенные каталоги формируют вложенные URL. Layouts задают общую оболочку для группы страниц: меню, шапку, боковую панель и общую структуру. При переходах общая оболочка может сохраняться, а содержимое страницы меняться.

Для лабораторной №5 явно требуется динамический маршрут карточки студента `/students/[id]`. Список студентов, вход, регистрация и профиль также должны быть представлены страницами Nuxt. Нужно не путать динамический параметр маршрута с query-параметром: ID является частью пути, а параметры фильтрации могут находиться после `?`.

## 9. Клиентская навигация и Prefetching. Предварительная загрузка страниц и ресурсов

Клиентская навигация позволяет переходить между страницами без полной перезагрузки документа. Метафреймворк перехватывает переход по внутренней ссылке, загружает необходимые данные и компоненты и обновляет текущий маршрут.

Prefetching — предварительная загрузка ресурсов или данных маршрута до того, как пользователь нажмёт ссылку. Например, когда ссылка попадает в область видимости, framework может начать загружать код следующей страницы. В результате фактический переход ощущается быстрее.

Prefetching имеет цену: он расходует сеть и может загружать то, что пользователь не откроет. Для страниц, требующих авторизации, нужно учитывать актуальность сессии и не кэшировать персональные данные без правильной политики. Prefetch не заменяет проверку прав на backend.

## 10. Серверная загрузка данных. Взаимодействие метафреймворка с внешним REST API

Серверная загрузка данных означает, что метафреймворк получает данные во время серверного рендеринга и использует их для первоначального HTML. В Nuxt для этого обычно применяются `useFetch` и `useAsyncData`: они интегрированы с SSR и позволяют передать результат на клиент, чтобы избежать повторного запроса при гидратации.

В этой лабораторной источником данных остаётся Java REST API лабораторной №3. Nuxt не должен дублировать бизнес-правила или обращаться к PostgreSQL напрямую. Он запрашивает endpoint'ы backend: список студентов, карточку, регистрацию, вход и другие операции.

Нужно правильно передавать авторизационные данные. На сервере нельзя рассчитывать на sessionStorage браузера: его там нет. Если SSR-запрос зависит от пользователя, механизм сессии/токена должен быть доступен серверному запросу безопасным способом, например через корректно настроенные cookies или контролируемый proxy. Нельзя помещать секреты в публичную конфигурацию.

Для клиентских действий можно использовать обычные запросы к API после гидратации. Важно не смешивать серверную загрузку данных для первого экрана и обработчики событий, которые запускаются только в браузере.

## 11. Последовательная и параллельная загрузка данных. Проблема Request Waterfall

Request Waterfall (цепочка запросов) возникает, когда следующий запрос начинается только после завершения предыдущего, хотя эти запросы независимы. Если три независимых запроса занимают примерно по 300 мс и запускаются последовательно, суммарное ожидание будет около 900 мс.

Если запросы независимы, их можно запустить параллельно: `Promise.all([requestA(), requestB(), requestC()])`. Тогда общее ожидание будет близко к длительности самого долгого запроса, то есть около 300 мс в приведённом примере, плюс накладные расходы.

Последовательность нужна, если второй запрос зависит от результата первого: например, сначала получить ID пользователя, затем загрузить его профиль. Нельзя бездумно распараллеливать зависимые операции.

В Student Management список и профиль пользователя могут быть независимыми запросами, но конкретное решение зависит от страницы и контракта backend. Важно измерять реальный bottleneck, а не запускать параллельно абсолютно всё.

## 12. Кеширование данных. Cache Hit, Cache Miss и основные стратегии кеширования

Кеш — временное или долговременное хранилище копии данных, позволяющее избежать повторной дорогой операции. Cache Hit — запрошенные данные найдены в кеше; Cache Miss — записи нет или она считается непригодной, поэтому выполняется получение из источника.

Кешировать можно на разных уровнях: браузер, CDN, серверное приложение, Nuxt data cache или база данных. У каждого кеша должны быть ключ, срок свежести, правила обновления и политика приватности. Ключ должен учитывать параметры, которые меняют результат: пользователя, фильтры, страницу, сортировку и другие условия.

Для публичных неизменяемых ресурсов подходит длительное кеширование. Для списка студентов с авторизацией нужна осторожность: данные одного пользователя нельзя случайно отдать другому. Для динамического списка разумнее короткий TTL или явное обновление после мутаций.

Кеширование — не то же самое, что хранение бизнес-данных. Источником истины остаётся backend/PostgreSQL, а кеш — оптимизация, которую можно пересоздать.

## 13. Revalidation и инвалидация кеша. Обновление данных по времени и по событию

Revalidation — проверка актуальности кешированной записи и, при необходимости, её обновление. Она может запускаться по времени (TTL), по событию (например, после изменения студента) или по запросу пользователя.

Инвалидация кеша — признание определённой записи или группы записей устаревшей. После создания/редактирования/удаления студента нужно обновить кеш списка и, если затронуто, кеш карточки. Иначе пользователь может увидеть старые данные после успешной операции.

SWR (stale-while-revalidate) — стратегия, при которой сначала возвращается сохранённая версия данных, а обновление выполняется в фоне. Это повышает отзывчивость, но означает, что пользователь некоторое время может видеть устаревшую информацию.

Для лабораторной №5 важно явно определить, какие данные кешируются и как очищаются после изменений. Кеш профиля и списка студентов должен быть разделён по пользователю/сессии, если содержимое персонализировано.

## 14. Middleware и защищённые маршруты. Перенаправление пользователей и проверка доступа

Middleware — промежуточная функция, которая выполняется до обработки маршрута или во время навигации. Она может проверить наличие сессии, роль, параметры запроса, перенаправить пользователя или остановить переход.

В Nuxt route middleware можно использовать для защиты страниц. Например, middleware для авторизации перенаправляет гостя на `/login`; middleware для администратора запрещает открывать страницу создания или редактирования студентам с ролью USER.

Но проверка middleware не является достаточной защитой. Backend лабораторной №3 обязан проверять JWT и права пользователя при каждом запросе к защищённому endpoint. Иначе пользователь может обойти интерфейс и отправить HTTP-запрос напрямую.

Важно правильно разделять серверное и клиентское выполнение middleware и не обращаться к browser-only API на сервере. Также нужно избегать циклических перенаправлений: например, страница login не должна требовать авторизацию.

## 15. Обработка состояний приложения. Loading, Error, Not Found и HTTP-статусы

Асинхронные страницы должны явно показывать состояние загрузки, ошибку или отсутствие ресурса. **Loading** отображается, пока запрос выполняется. **Error** показывает понятное сообщение, если запрос завершился ошибкой. **Not Found** означает, что запрашиваемая страница или студент не существует, и должен соответствовать HTTP 404, а не просто пустому экрану.

HTTP-статус описывает результат запроса: 200 — успешно; 201 — ресурс создан; 204 — успешно без тела; 400 — некорректный запрос; 401 — не аутентифицирован; 403 — запрещено; 404 — не найдено; 409 — конфликт; 422 — ошибка валидации; 5xx — серверная ошибка.

Nuxt должен корректно передавать статус ответа, если серверный запрос к backend получил 404 или другую ошибку. Нельзя превращать все ошибки в 200 с текстом «что-то пошло не так»: это ломает семантику HTTP, кеширование и обработку на клиенте.

Для списка студентов нужно показывать индикатор загрузки, сообщение об ошибке и пустое состояние, если список успешно загружен, но записей нет. Для динамической карточки `/students/[id]` при отсутствии студента должна отображаться 404-страница или корректный Not Found state.

## Как лабораторная №5 продолжает лабораторную №4

Лабораторная №4 — Vue SPA: Vue Router, Pinia, RxJS, клиентские API-запросы, JWT и Docker. Лабораторная №5 переносит frontend на Nuxt, сохраняя функциональность, но добавляет SSR, файловые и динамические маршруты, middleware, состояния loading/error/404 и кеширование с обновлением.

Backend не переписывается: Java/Spring Boot из лабораторной №3 по-прежнему выполняет бизнес-логику, проверяет JWT и роли, работает с PostgreSQL. Nuxt отвечает за представление и серверные возможности frontend.
