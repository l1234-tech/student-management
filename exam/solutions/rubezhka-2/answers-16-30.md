### 16. Virtual DOM и reconciliation. Как изменения состояния превращаются в изменения интерфейса?

Virtual DOM — распространённое название объектов/структур, которыми библиотека описывает желаемое дерево UI в памяти. Когда меняются props или state, компонент формирует новое описание. Reconciliation сопоставляет его с предыдущим описанием и определяет необходимые изменения. На этапе commit библиотека применяет их к реальному DOM, после чего браузер пересчитывает отображение.

Упрощённая последовательность: действие → изменение state → повторное вычисление UI → reconciliation → DOM-обновление. Например, если в таблице студентов изменился только текст имени, библиотека может обновить соответствующий текстовый узел, сохранив остальную структуру. Это не означает, что любой фреймворк всегда строит два полных дерева или что diff автоматически делает все обновления бесплатными: реализация и оптимизации отличаются.

**Опора на лекцию:** лекция 9 о декларативном компонентном рендеринге. **Дополнение:** этапы объясняют общий принцип; детали конкретной библиотеки см. в её документации.

### 17. Context API, Redux Toolkit и аналоги. Когда достаточно контекста?

Context решает задачу передачи значения глубоко по дереву без промежуточных props: тема оформления, текущий пользователь, локаль или зависимости конкретного поддерева. Сам Context не задаёт полноценную архитектуру изменений состояния и не предоставляет автоматически reducers, middleware, инструменты времени и правила запросов.

Для небольшого состояния контекст вместе с `useState`/`useReducer` может быть достаточным. Отдельный store, например Redux Toolkit или Pinia, полезен, когда много частей приложения читают и изменяют общее состояние, нужны предсказуемые действия, middleware, devtools или единый слой бизнес-операций. Выбор зависит от сложности и модели команды, а не от размера проекта по числу компонентов.

**Опора на лекцию:** управление состоянием и store. **Дополнение:** граница применения сверена с [React Context](https://react.dev/learn/passing-data-deeply-with-context) и [Redux Toolkit](https://redux-toolkit.js.org/introduction/getting-started).

### 18. Условный рендеринг и вывод списков. Как state влияет на отображение?

Интерфейс строится из текущего состояния: `loading` показывает индикатор, `error` — сообщение, пустой результат — подсказку, а успешный запрос — список. Условие выбирает ветку представления, а список отображает элементы коллекции.

```jsx
if (status === 'loading') return <p>Загрузка…</p>;
if (status === 'error') return <p role="alert">Не удалось загрузить список</p>;
return students.length
  ? <ul>{students.map(s => <li key={s.id}>{s.name}</li>)}</ul>
  : <p>Студенты не найдены</p>;
```

Во Vue похожий результат задают `v-if`/`v-else` и `v-for`; `v-show` меняет видимость CSS, сохраняя узел, тогда как `v-if` условно создаёт/удаляет его. Для списков нужен стабильный ключ. Разделяйте состояния загрузки, ошибки, пустого результата и готовых данных: пустой массив сам по себе не сообщает, завершился ли запрос.

**Опора на лекцию:** декларативная модель «UI = функция данных». **Дополнение:** условные конструкции конкретных фреймворков.

### 19. Svelte и компилируемая реактивность. Чем подход отличается от Virtual DOM?

Svelte компилирует компонентный код в JavaScript, который обновляет DOM в ответ на изменения состояния. В классическом описании Svelte это противопоставляется рантайм-подходу Virtual DOM, где библиотека во время работы сравнивает описания интерфейса. В актуальном Svelte 5 реактивность в runes mode задаётся, например, `$state` и `$derived`; компилятор анализирует зависимости.

```svelte
<script>
  let count = $state(0);
  let doubled = $derived(count * 2);
</script>

<button onclick={() => count++}>{doubled}</button>
```

Главное различие — где выполняется работа по отслеживанию изменений: часть работы переносится в компиляцию, а не решается общим runtime diff-алгоритмом. Это не означает, что Svelte не имеет runtime-кода или что Virtual DOM всегда медленнее: итог зависит от приложения, реализации и измерений.

**Опора на лекцию:** сравнение компонентных подходов. **Дополнение:** синтаксис runes и `$derived` — [документация Svelte](https://svelte.dev/docs/svelte/$derived).

### 20. Props drilling: что это и как уменьшают проблему?

Props drilling — передача значения через несколько промежуточных компонентов, которым это значение не нужно, только чтобы оно дошло до глубокого потомка. Например, `currentUser` проходит через Layout и Sidebar к Avatar. Код становится связанным: изменение контракта затрагивает все промежуточные уровни.

Способы решения: изменить структуру и вынести нужный компонент ближе к данным; передать готовый JSX/`children`; поднять состояние к общему владельцу; применить Context/provide-inject для значения поддерева; использовать store для общего состояния приложения. Context или store не следует вводить автоматически: явные props часто понятнее, если цепочка короткая.

**Опора на лекцию:** компонентный контракт лекции 9. **Дополнение:** альтернативы описаны в [React Context](https://react.dev/learn/passing-data-deeply-with-context) и [Vue provide/inject](https://vuejs.org/guide/components/provide-inject.html).

### 21. Реактивный поиск с RxJS: меньше запросов и защита от устаревших результатов

Поле ввода генерирует много событий — по событию на каждый символ. `debounceTime` ждёт паузу перед выдачей значения; `distinctUntilChanged` пропускает повторное значение; `switchMap` переключает внутренний Observable на новый запрос. Поэтому новый запрос отменяет подписку на результат предыдущего, а поздний ответ старого поиска не попадёт в отображение.

```ts
fromEvent<InputEvent>(input, 'input').pipe(
  map(() => input.value.trim()),
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(q => api.searchStudents(q))
).subscribe(renderResults);
```

Отмена подписки не всегда означает, что сервер прекратил вычисление: фактическая отмена HTTP-запроса зависит от адаптера/механизма. Для пустого запроса можно вернуть `of([])`, а ошибки обработать внутри `switchMap`, чтобы ошибка одного запроса не завершила весь поток ввода.

**Опора на лекцию:** реактивное взаимодействие SPA и RxJS. **Дополнение:** операторы и их семантика — [официальная документация RxJS](https://rxjs.dev/api/operators).

### 22. RxJS: mergeMap и switchMap

Оба оператора превращают входное значение во внутренний Observable, но управляют параллельностью по-разному. `mergeMap` подписывается на внутренний поток каждого значения и объединяет их результаты. Несколько запросов могут выполняться параллельно, а завершаться в любом порядке. `switchMap` при новом входном значении отписывается от предыдущего внутреннего потока и оставляет только последний.

Поиск по строке обычно использует `switchMap`: важен результат для самого свежего ввода. Независимая загрузка деталей для каждого выбранного элемента может требовать `mergeMap`, если нужно сохранить все результаты. Для строго последовательных операций есть `concatMap`, для игнорирования новых значений на время текущей операции — `exhaustMap`.

**Опора на лекцию:** операторы RxJS. **Дополнение:** официальная спецификация [mergeMap](https://rxjs.dev/api/operators/mergeMap) и [switchMap](https://rxjs.dev/api/operators/switchMap).

### 23. Клиентская навигация в SPA. Как меняются URL и содержимое без полной загрузки?

Router перехватывает внутреннюю навигацию, сопоставляет URL с маршрутом, обновляет историю браузера и отображает нужную страницу или компонент. Данные для страницы могут быть загружены отдельно через API. При обычном переходе внутри приложения браузер не получает новый HTML-документ целиком.

History API позволяет вызвать `history.pushState()`/`replaceState()` и обработать переходы назад/вперёд через `popstate`; router связывает эти события с маршрутом. При прямом открытии `/students/42` сервер должен вернуть приложение или обработать URL маршрута, иначе пользователь получит 404 ещё до запуска JavaScript. Ссылки должны сохранять доступность и базовое поведение, а не быть только кликабельными `div`.

**Опора на лекцию:** лекция 8, SPA и навигация. **Дополнение:** [History API](https://developer.mozilla.org/en-US/docs/Web/API/History_API/Working_with_the_History_API).

### 24. Lazy Loading и Code Splitting. Как они влияют на загрузку SPA?

Code splitting делит JavaScript на чанки, которые можно загружать отдельно. Lazy loading откладывает загрузку части кода до момента, когда она потребуется, например при открытии страницы отчётов. Это уменьшает начальный объём JavaScript для пользователя, который эту страницу не открывает.

```js
const ReportsPage = () => import('./pages/ReportsPage.vue');
```

У разделения есть издержки: дополнительный запрос/ожидание при первом открытии чанка, необходимость показывать состояние загрузки и корректно обрабатывать сбой. Важно делить по маршрутам или крупным возможностям, а не превращать каждый мелкий компонент в отдельную загрузку. Оптимизация проверяется по фактическому размеру и метрикам загрузки.

**Опора на лекцию:** SPA и организация клиентского кода. **Дополнение:** техника зависит от сборщика и router проекта.

### 25. Path- и query-параметры URL как часть состояния интерфейса

Path-параметры обычно идентифицируют ресурс или маршрут: `/students/42` означает страницу студента с ID 42. Query-параметры обычно задают необязательные параметры представления/выборки: `/students?group=P3222&page=2&sort=name`.

URL удобен для состояния, которое пользователь должен сохранить, скопировать или восстановить через Back/Forward: выбранный раздел, поиск, фильтр и пагинация. Секреты и токены в URL помещать нельзя: URL может попасть в историю, журналы и заголовок Referer. Разбирайте и валидируйте параметры — текст из URL является внешним вводом.

**Опора на лекцию:** навигация SPA и REST-маршруты. **Дополнение:** синтаксис path/query определяется router и серверным API.

### 26. Формы в SPA: controlled/uncontrolled inputs и отправка

Controlled input хранит значение в state: отображаемое значение задаётся приложением, а `onChange` обновляет state. Это удобно для мгновенной валидации, форматирования и синхронизации нескольких полей. Uncontrolled input хранит значение в DOM; приложение читает его при отправке через `FormData` или ref. Такой вариант проще для небольших форм, но хуже подходит для логики, зависящей от каждого изменения.

```jsx
function NameForm() {
  const [name, setName] = useState('');
  return <input value={name} onChange={e => setName(e.target.value)} />;
}
```

При submit остановите стандартную перезагрузку, проверьте данные, покажите loading, отправьте запрос и отобразите успех или ошибку. Серверная проверка всё равно обязательна: клиентскую валидацию можно обойти.

**Опора на лекцию:** формы и состояние компонентов. **Дополнение:** controlled/uncontrolled различие см. в [React sharing state](https://react.dev/learn/sharing-state-between-components).

### 27. Lifting State Up. Когда состояние поднимают к общему родителю?

Если нескольким соседним компонентам нужно согласованное значение, его переносят в ближайшего общего родителя. Родитель становится единственным владельцем этого state и передаёт детям значение и callbacks. Например, если фильтр и список должны отражать один выбранный факультет, родитель хранит фильтр и передаёт его обоим.

Поднимать состояние выше нужно ровно настолько, насколько требуется для координации. Слишком высокое состояние заставляет несвязанные части приложения зависеть от него; локальный ввод, используемый одной формой, обычно не нужно класть в глобальный store.

**Опора на лекцию:** поток данных компонентов. **Дополнение:** схема соответствует [React lifting state up](https://react.dev/learn/sharing-state-between-components).

### 28. RxJS: Subject и BehaviorSubject

`Subject` одновременно является Observable и Observer: на него можно подписаться, а значения отправлять через `next()`. Это multicast: подписчики получают один и тот же поток отправленных значений. Обычный Subject не отдаёт новому подписчику уже прошедшие значения.

`BehaviorSubject` требует начальное значение и хранит последнее. Новый подписчик сразу получает текущее значение, затем последующие обновления. Это удобно для состояния, например выбранного фильтра. Но Subject не обязательно использовать для каждого состояния: чрезмерное число изменяемых потоков затрудняет поиск владельца и направления изменений.

```ts
const group$ = new BehaviorSubject('P3222');
group$.subscribe(group => renderGroup(group));
group$.next('P3223');
```

**Опора на лекцию:** RxJS и реактивное состояние. **Дополнение:** [официальное руководство Subject](https://rxjs.dev/guide/subject).

### 29. Редактирование студента через REST API в SPA: от формы до обновления списка

Типичный поток: пользователь меняет поля → форма выполняет клиентскую проверку → отправляет `PUT` или `PATCH /api/students/{id}` с JSON и авторизационными данными → API проверяет права, формат и бизнес-ограничения → сервер возвращает обновлённую запись/статус → клиент обновляет store или повторно загружает список. При ошибке форма сохраняет ввод и показывает понятное сообщение; сетевой сбой нужно отличать от ошибки валидации и отсутствия записи.

После ответа можно заменить соответствующий элемент в store по ID, чтобы не перезагружать всю страницу. Однако серверный ответ — источник окончательного значения, поскольку он может нормализовать данные или вычислить поля. Кнопку отправки обычно блокируют на время запроса, но защита от повторной операции должна учитывать и повторную отправку на сервере.

**Опора на лекцию:** SPA, REST и формы. **Дополнение:** формат конкретных методов определяется API; общее понятие HTTP описывает [MDN HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP).

### 30. Optimistic UI: что происходит при оптимистичном обновлении и откате?

Optimistic UI сначала показывает ожидаемый результат, не дожидаясь сервера. Например, после отправки новой группы строка сразу отображается с новым значением, а запрос выполняется в фоне. Успех закрепляет серверный результат; ошибка требует откатить прежние данные и показать сообщение.

Для корректного отката сохраните предыдущую версию записи или patch-операцию, а запрос сопоставьте с конкретной сущностью. Нужно учитывать параллельные обновления: простой возврат всего старого списка может стереть более новое изменение. Оптимистичный подход лучше подходит быстрым, часто успешным и обратимым действиям. Для платежа или необратимого действия преждевременное подтверждение может вводить пользователя в заблуждение.

**Опора на лекцию:** состояние UI и обмен с REST API. **Дополнение:** механизм отката зависит от store/data-fetching библиотеки.
