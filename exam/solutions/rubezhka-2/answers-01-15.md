### 1. Разделение представления, состояния и бизнес-логики в компонентном приложении

**Представление** отвечает за отображение: разметку, доступность и визуальные состояния загрузки, ошибки и пустого списка. **Состояние** хранит изменяемые данные интерфейса и приложения: записи студентов, фильтр, выбранный элемент, статус запроса. **Бизнес-логика** задаёт правила предметной области: какие поля обязательны, можно ли сохранить запись, как интерпретировать ответ сервера.

Разделение делает код проще для изменения и проверки. Компонент формы может отображать поля и сообщать о намерении сохранить данные; сервис или store выполняет операцию и применяет правила. Не вся логика обязана находиться в отдельном слое: небольшой компонент вправе содержать простую локальную логику, но HTTP-доступ, доменные правила и отображение не следует смешивать в одном обработчике.

**Пример:** `StudentForm` отображает `name` и `group` и вызывает `emit('save', form)`. `studentStore.saveStudent(form)` проверяет состояние операции и вызывает API-клиент. Ответ возвращается в store, который обновляет список; компонент отображает новое состояние.

**Опора на лекцию:** компонент и его понятный контракт — лекция 9. **Дополнение:** такое разделение также соответствует идее единого источника данных и тонких компонентов.

### 2. Императивный и декларативный подходы к построению интерфейса

Императивный код описывает последовательность команд: найти элемент, создать узел, изменить текст, скрыть кнопку, добавить обработчик. Разработчик вручную поддерживает соответствие между DOM и данными. Декларативный код описывает желаемый интерфейс для текущих данных, а библиотека применяет необходимые изменения.

```js
// Императивно
document.querySelector('#count').textContent = String(count);

// Декларативно во Vue
// <p>{{ count }}</p>
```

Декларативный стиль облегчает рассуждение о состоянии: если `count` равен 3, шаблон показывает 3. Он не отменяет императивные операции вообще: работа с Canvas, фокусом, сторонней библиотекой или браузерным API может требовать эффектов и refs. Такие операции изолируют в обработчиках и lifecycle/effect-функциях.

**Опора на лекцию:** лекция 9 прямо рассматривает декларативный и императивный подходы. **Дополнение:** примеры показывают различие на DOM и Vue-шаблоне.

### 3. Реактивные значения на примере ref, signal, state или rune

Реактивное значение — данные, за чтением которых фреймворк следит и при изменении которых обновляет зависимые вычисления или представление. Имена API различаются, но общая схема одинакова: объявить источник состояния, прочитать его в шаблоне/рендере, изменить через предусмотренный механизм.

```js
// Vue 3
import { ref } from 'vue';
const count = ref(0);
count.value++;

// Angular signal
const count = signal(0);
count.update(value => value + 1);

// Svelte 5 rune
let count = $state(0);
count++;
```

Vue `ref` и Angular `signal` отслеживают чтение и уведомляют подписанные вычисления. Svelte rune — конструкция компилятора, которая объявляет реактивное состояние компонента. Эти API нельзя смешивать синтаксически; важно понять общую модель и пользоваться моделью выбранного проекта.

**Опора на лекцию:** реактивность компонентного frontend — лекция 9. **Дополнение:** точные API сверены с официальными руководствами [Vue](https://vuejs.org/guide/essentials/reactivity-fundamentals.html), [Angular](https://angular.dev/guide/signals) и [Svelte](https://svelte.dev/docs/svelte/$state).

### 4. Очистка ресурсов компонента: подписки, таймеры и обработчики событий

Если компонент создаёт внешний ресурс, он должен освободить его, когда перестаёт быть нужен. Иначе callback может работать после удаления компонента, менять уже неактуальное состояние, повторно отправлять запросы или удерживать объекты в памяти.

```vue
<script setup>
import { onMounted, onUnmounted } from 'vue';

let timer;
function onResize() { /* обновить локальные измерения */ }

onMounted(() => {
  timer = window.setInterval(() => console.log('tick'), 1000);
  window.addEventListener('resize', onResize);
});

onUnmounted(() => {
  window.clearInterval(timer);
  window.removeEventListener('resize', onResize);
});
</script>
```

Для RxJS сохраняют `Subscription` и вызывают `unsubscribe()`, либо используют привязку подписки к lifecycle. Для HTTP-запросов можно применить `AbortController`, если операция должна прекратиться при уходе со страницы. Очистка должна совпадать с типом ресурса: снять тот же обработчик с того же объекта, очистить созданный таймер, отменить собственную подписку.

**Опора на лекцию:** жизненный цикл и внешние ресурсы компонента. **Дополнение:** конкретные способы очистки показаны для браузерных API и Vue.

### 5. Однонаправленный поток данных во frontend. Как организуется изменение состояния?

Однонаправленный поток означает, что данные проходят по понятной цепочке: владелец состояния передаёт значения вниз, а дочерний компонент сообщает о событии вверх. Ребёнок не меняет напрямую состояние родителя; родитель решает, как обработать событие и обновить данные.

```vue
<!-- Родитель -->
<StudentName :name="student.name" @rename="student.name = $event" />

<!-- Дочерний компонент получает prop и отправляет событие -->
```

Последовательность: действие пользователя → обработчик → изменение state/store → новая версия данных → повторный рендер зависимых компонентов. Такой поток делает изменения прослеживаемыми, помогает определить владельца данных и снижает риск скрытой мутации. При большом приложении store централизует отдельные данные, но принцип остаётся прежним: состояние меняется через определённые действия.

**Опора на лекцию:** контракт props/events и организация состояния — лекция 9. **Дополнение:** React описывает сходную схему как реакцию интерфейса на state.

### 6. Dependency Injection во frontend

Dependency Injection (DI, внедрение зависимостей) — способ передать компоненту нужный сервис извне, вместо того чтобы создавать его самостоятельно внутри компонента. Это уменьшает связанность: компонент зависит от контракта сервиса, а создание, конфигурация и область его жизни определяются контейнером или приложением.

```ts
// Angular: сервис запрашивается через DI-контейнер
import { Component, inject } from '@angular/core';
import { StudentApi } from './student-api';

@Component({ /* ... */ })
export class StudentPage {
  private readonly api = inject(StudentApi);
}
```

DI удобен для API-клиентов, логирования, конфигурации и тестовых замен. В тесте реальный `StudentApi` можно заменить mock-реализацией. В небольшом компоненте с одной простой функцией отдельный контейнер не нужен: достаточно обычной передачи функции или props. DI не означает, что бизнес-логика должна быть глобальной.

**Опора на лекцию:** зависимости и разделение ответственности в компонентном приложении. **Дополнение:** пример синтаксиса Angular приведён по [официальному руководству DI](https://angular.dev/guide/di).

### 7. Компонентная архитектура frontend-приложения

Компонент объединяет ограниченную часть интерфейса и её контракт: какие данные он принимает, какие события сообщает и какие элементы отображает. Страница обычно собирается из компонентов формы, фильтра, списка, строки записи и сообщений о состоянии запроса.

Преимущества: повторное использование, локализация изменений, понятная декомпозиция и возможность проверять части отдельно. Компонент не должен быть слишком крупным универсальным «комбайном», но и не каждую строку разметки нужно превращать в компонент. Хорошая граница возникает там, где есть отдельная ответственность или повторное использование.

Пример структуры: `StudentsPage` координирует загрузку и фильтры; `StudentFilter` отображает ввод и отправляет событие изменения; `StudentList` получает уже подготовленный список; `StudentCard` отображает одну запись.

**Опора на лекцию:** лекция 9 — компоненты, контракт и разбиение frontend. **Дополнение:** границы компонентов следует выбирать по ответственности и потребностям переиспользования.

### 8. Watchers и effects. Чем отслеживание изменений отличается от вычисления состояния?

Вычисляемое состояние (`computed`, selector, `$derived`) возвращает значение, получаемое из других данных. Watcher/effect запускает побочное действие, когда меняется зависимость: запрос к API, запись в storage, синхронизацию с браузерным API или журналирование.

В Vue `computed` лениво пересчитывается при чтении и кешируется до изменения зависимостей. `watch` явно наблюдает источник, `watchEffect` автоматически собирает зависимости, прочитанные во время выполнения. Эффекты могут быть асинхронными и требуют очистки/отмены предыдущей операции, если новые данные пришли раньше.

```js
const fullName = computed(() => `${first.value} ${last.value}`); // значение
watch(query, value => searchStudents(value));                  // эффект
```

Не следует запускать эффект только ради вычисления значения, которое можно получить из имеющегося state: дублирование создаёт рассинхронизацию. Также нельзя помещать мутации или сетевые запросы внутрь чистого computed.

**Опора на лекцию:** реактивность и производные значения. **Дополнение:** различие `computed`, `watch` и `watchEffect` сверено с [документацией Vue](https://vuejs.org/guide/essentials/watchers.html).

### 9. Reconciliation и key при рендеринге списков

Reconciliation — сопоставление предыдущего описания интерфейса с новым после изменения данных. Фреймворк решает, какие элементы сохранить, обновить, переместить или удалить. `key` помогает связать компонент списка с конкретной записью между рендерами.

```jsx
students.map(student => <StudentRow key={student.id} student={student} />)
```

Индекс массива — плохой ключ для списка, который сортируется, фильтруется или меняет состав. После удаления первой записи индексы сдвигаются, и фреймворк может связать введённый текст, фокус или локальное состояние строки с другой записью. Ключ должен быть уникальным среди соседей и стабильным во времени; обычно это постоянный ID данных. Не создавайте `Math.random()` при каждом рендере.

**Опора на лекцию:** компонентный рендеринг и идентичность элементов. **Дополнение:** правила `key` — [официальная документация React](https://react.dev/learn/rendering-lists).

### 10. Props и события компонентов. Передача данных между родителем и потомком

Props передают входные данные от родителя к ребёнку; ребёнок рассматривает их как вход и не должен мутировать. Событие или callback сообщает родителю о действии: пользователь изменил значение, выбрал запись или запросил сохранение. Родитель владеет состоянием и решает, как его обновить.

```vue
<!-- StudentName.vue -->
<script setup>
defineProps({ name: String });
const emit = defineEmits(['rename']);
</script>
<template>
  <button @click="emit('rename', 'Анна')">Переименовать {{ name }}</button>
</template>
```

```jsx
<StudentName name={student.name} onRename={name => setStudent({ ...student, name })} />
```

Props задают направление вниз, события/колбэки — уведомление вверх. Если одна и та же информация проходит через много промежуточных компонентов, это может быть prop drilling; сначала проверьте, не стоит ли изменить границы компонентов или поднять общий state.

**Опора на лекцию:** лекция 9, props и callback props. **Дополнение:** синтаксис см. в [Vue component events](https://vuejs.org/guide/components/events.html) и [React props](https://react.dev/learn/passing-props-to-a-component).

### 11. Вычисляемое состояние (computed/derived): назначение и отличие от обычного state

Обычный state хранит самостоятельные данные: список студентов, поисковый запрос и выбранную группу. Derived state вычисляется из них, например отфильтрованный список или количество результатов. Если значение можно однозначно получить из текущего состояния, его обычно не нужно хранить второй раз.

```js
const filtered = computed(() => students.value.filter(student =>
  student.name.toLowerCase().includes(query.value.toLowerCase())
));
```

Так приложение имеет единый источник истины: меняется `students` или `query`, производное значение пересчитывается. Отдельная копия `filtered` потребовала бы обновлять её во всех обработчиках и могла бы устареть. Computed/derived-функция должна быть чистой: вернуть результат без запроса к серверу, таймера или мутации исходного state.

**Опора на лекцию:** производные данные и единый источник состояния. **Дополнение:** рекомендации согласуются с [Vue computed](https://vuejs.org/guide/essentials/computed.html) и [React useState](https://react.dev/reference/react/useState).

### 12. Принципы проектирования переиспользуемых компонентов и разделения ответственности

Переиспользуемый компонент имеет узкую задачу и ясный интерфейс: обязательные и необязательные props, события, ожидаемый формат данных и поведение в состояниях загрузки/ошибки. Он не должен неявно предполагать конкретную страницу, обращаться к глобальному DOM или самостоятельно выполнять несколько несвязанных операций.

Разделение ответственности означает, например, что `StudentRow` отображает одну запись, `StudentForm` управляет вводом и валидацией полей, а `StudentApi` знает URL и формат HTTP-запросов. Компонент может быть контролируемым (получает значение и callback) или владеть небольшим локальным состоянием. Выбор зависит от того, кому нужно координировать поведение.

Переиспользование не является самоцелью: если абстракция требует много флагов (`isCompact`, `isAdmin`, `isEditable`, `showExtra`), возможно, у компонентов разные обязанности.

**Опора на лекцию:** контракт и композиция компонентов — лекция 9. **Дополнение:** примеры границ слоёв применены к предметной области студентов.

### 13. Slots, children и композиция компонентов. Зачем родителю передавать содержимое?

Slot/`children` позволяет компоненту-контейнеру определить общую оболочку, а родителю передать внутреннее содержимое. Контейнер знает оформление и расположение, но не обязан знать конкретную разметку содержимого. Это даёт композицию вместо множества специальных props для каждого варианта.

```vue
<!-- Card.vue -->
<template><section class="card"><slot /></section></template>

<!-- Родитель -->
<Card><h2>Студент</h2><p>Группа P3222</p></Card>
```

В React похожую роль играет `children`: `<Card><StudentDetails /></Card>`. Именованные slots подходят, когда у компонента несколько областей, например `header`, `default` и `actions`. Slot не является механизмом управления произвольным состоянием; он задаёт точку композиции содержимого.

**Опора на лекцию:** лекция 9 рассматривает slots и композицию. **Дополнение:** конкретный синтаксис — [Vue slots](https://vuejs.org/guide/components/slots.html) и [React children](https://react.dev/learn/passing-props-to-a-component).

### 14. Глобальный store: зачем он нужен и как организован на примере Pinia

Store нужен для состояния, которым пользуются разные несоседние компоненты или которое должно переживать переходы между страницами: текущая сессия, список студентов, настройки фильтра. Он централизует данные и операции. Локальное состояние формы или раскрытой подсказки обычно лучше оставить рядом с компонентом.

В Pinia store обычно описывает **state** (хранимые данные), **getters** (производные значения) и **actions** (операции изменения/асинхронная логика). Компоненты получают store и вызывают его действия; UI обновляется реактивно.

```js
export const useStudentsStore = defineStore('students', {
  state: () => ({ items: [], status: 'idle' }),
  getters: { count: state => state.items.length },
  actions: {
    async load() {
      this.status = 'loading';
      try { this.items = await api.list(); this.status = 'success'; }
      catch { this.status = 'error'; }
    }
  }
});
```

**Опора на лекцию:** state management и глобальное состояние. **Дополнение:** Pinia `state`, `getters` и `actions` — [официальное руководство](https://pinia.vuejs.org/core-concepts/).

### 15. Жизненный цикл компонента: создание, обновление, уничтожение; hooks и lifecycle

Жизненный цикл описывает этапы существования экземпляра компонента. При создании настраиваются состояние и зависимости; при монтировании компонент появляется в DOM; после изменения данных обновляется представление; при уничтожении удаляется из интерфейса и освобождаются ресурсы.

Lifecycle hooks позволяют выполнить задачу на подходящем этапе. Например, `onMounted` подходит для обращения к DOM-элементу или запуска подписки, `onUnmounted` — для очистки. Вычисление интерфейса лучше оставлять в шаблоне/computed, а не выполнять вручную в hook при каждом изменении.

Названия различаются: Vue использует `onMounted`/`onUnmounted`, React — `useEffect` с cleanup, Angular — hooks вроде `ngOnInit` и `ngOnDestroy`. Это не взаимозаменяемые API, но решают сходные задачи управления побочными действиями на протяжении жизни компонента.

**Опора на лекцию:** жизненный цикл и hooks — лекция 9. **Дополнение:** см. [Vue lifecycle](https://vuejs.org/guide/essentials/lifecycle.html) и [React effects](https://react.dev/learn/synchronizing-with-effects).
