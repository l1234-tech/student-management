# 6. Backend, REST API и Python/Django

## 6.1. Что делает backend

Backend — серверная часть приложения. Обычно она:
- принимает HTTP-запрос;
- проверяет маршрут и метод;
- читает параметры и тело;
- валидирует данные;
- проверяет аутентификацию и права;
- выполняет бизнес-логику;
- обращается к хранилищу;
- возвращает статус и данные.

**Бизнес-логика** — правила предметной области. Например, нельзя записать студента без имени или назначить оценку вне допустимого диапазона. **Валидация** — проверка соответствия входных данных требованиям.

## 6.2. Что означает REST

**REST (Representational State Transfer)** — архитектурный стиль построения распределённых систем. REST не является конкретным языком или библиотекой. В учебных CRUD API часто используют REST-подобные соглашения: ресурсы имеют URL, HTTP-методы отражают операции, а представления данных передаются в JSON.

Пример ресурса студентов:
- `GET /api/students` — список;
- `GET /api/students/42` — один объект;
- `POST /api/students` — создание;
- `PUT /api/students/42` — полная замена;
- `PATCH /api/students/42` — частичное обновление;
- `DELETE /api/students/42` — удаление.

**CRUD** — Create, Read, Update, Delete: создать, прочитать, изменить, удалить.

REST не требует, чтобы каждый API использовал строго именно такие URL, но единообразие облегчает понимание и тестирование.

## 6.3. Ресурс, представление и идентификатор

**Ресурс** — концептуальный объект предметной области, например студент. **Представление ресурса** — передаваемое клиенту описание, например JSON. **Идентификатор** отличает один ресурс от другого.

```json
{
  "id": 42,
  "name": "Анна",
  "group": "R3222"
}
```

Внутренняя модель базы данных может содержать больше полей, чем публичное API. Поэтому backend часто формирует отдельное представление/DTO и не отдаёт клиенту всю запись без разбора.

## 6.4. Где передаются параметры

- **Path parameter**: `/api/students/42` — идентификатор в пути.
- **Query parameter**: `/api/students?group=R3222` — фильтр в строке запроса.
- **Request body**: JSON в теле POST/PATCH/PUT.
- **Header**: метаданные, например Authorization.
- **Cookie**: браузерное хранилище данных, которое может отправляться серверу автоматически.

Типично: путь выбирает ресурс, query уточняет выборку, тело содержит изменяемые данные. Но конкретное API определяет правила само.

## 6.5. Django: основные термины

**Django** — Python-фреймворк для веб-приложений. Фреймворк предоставляет готовые механизмы и соглашения, чтобы не писать всё с нуля.

- **Project** — конфигурация Django-проекта.
- **App** — модуль приложения с определённой функциональностью.
- **URLconf** — таблица маршрутов, связывающая URL с обработчиками.
- **View** — функция или класс, который обрабатывает запрос и возвращает ответ.
- **Model** — описание данных и взаимодействия с БД через ORM.
- **Template** — шаблон для генерации HTML.
- **Middleware** — компонент, который обрабатывает запрос/ответ на общем уровне.
- **Migration** — версионируемое описание изменения схемы БД.

В обычном Django-приложении модели, шаблоны и views часто объясняют как MVT (Model–View–Template). Это близко к MVC, но терминология ролей отличается.

## 6.6. Маршрутизация и обработчик

Маршрут сопоставляет путь с кодом, который должен обработать запрос. В Django он определяется в URLconf. В FastAPI используются декораторы маршрутов, например `@app.get("/api/students")`.

Концептуальный пример Django:

```python
from django.urls import path
from . import views

urlpatterns = [
    path("students/", views.students_list, name="students-list"),
]
```

`path` описывает путь, `views.students_list` — обработчик, `name` — имя маршрута для ссылок из кода. Конкретный синтаксис зависит от фреймворка и структуры проекта.

## 6.7. Валидация и ошибки

Входные данные нельзя считать правильными только потому, что клиент прислал JSON. Backend должен проверить:
- обязательные поля;
- типы данных;
- диапазоны и длины;
- допустимые значения;
- уникальность там, где она нужна;
- права пользователя на действие.

Типичные ответы:
- 400 — запрос некорректен;
- 404 — объект не найден;
- 409 — конфликт, например дубликат уникального значения;
- 422 — данные не прошли проверку (если так принято в используемом API);
- 500 — непредвиденная серверная ошибка.

Не стоит отправлять пользователю подробный stack trace в production: он может раскрыть внутреннее устройство сервера. Подробности записывают в защищённые логи.

## 6.8. Слои приложения

В небольшом backend полезно разделять обязанности:

- **View/controller** принимает запрос и формирует HTTP-ответ.
- **Service** содержит сценарии и бизнес-логику.
- **Repository/data access** отвечает за чтение и запись данных.
- **Model/entity** описывает данные предметной области.
- **Serializer/DTO/schema** определяет, как данные принимаются или возвращаются через API.

Не каждый проект обязан иметь все эти слои. Смысл разделения — чтобы HTTP-обработка, бизнес-правила и работа с данными не были перемешаны в одной большой функции.

## 6.9. CORS и same-origin policy

**Origin (источник)** обычно определяется сочетанием схемы, домена и порта. Например, `http://localhost:3000` и `http://localhost:8000` — разные origin из-за разных портов.

**Same-origin policy** — браузерное ограничение на взаимодействие ресурсов разных источников. **CORS (Cross-Origin Resource Sharing)** — механизм, с помощью которого сервер объявляет, какие cross-origin запросы браузер может разрешить.

CORS не заменяет аутентификацию и авторизацию. Это не универсальная защита backend от всех клиентов: вне браузера запрос можно отправить другим инструментом.

## 6.10. Тестирование API

API можно проверять браузером (для простых GET), curl, Postman/Bruno или автоматическими тестами. Проверяй не только успешный случай, но и:
- неправильный метод;
- отсутствующий объект;
- неверный JSON;
- обязательное поле отсутствует;
- пользователь не авторизован;
- недостаточно прав;
- повторное создание дубликата.

Для каждого теста фиксируй ожидаемые статус и тело ответа.
