# 9. Базы данных, SQL, ORM и транзакции

## 9.1. Что такое база данных

**База данных (БД)** — организованная совокупность данных. **СУБД** — программная система, которая хранит данные, управляет доступом и выполняет запросы. PostgreSQL — пример реляционной СУБД.

В реляционной БД данные представлены таблицами:
- **таблица** — набор записей об одном типе сущностей;
- **строка/запись** — один объект;
- **столбец/поле** — свойство объекта;
- **схема** — логическое пространство объектов БД, например таблиц и представлений;
- **первичный ключ (PRIMARY KEY)** — однозначно идентифицирует строку;
- **внешний ключ (FOREIGN KEY)** — ссылается на строку другой или той же таблицы;
- **ограничение (constraint)** — правило допустимости данных.

## 9.2. SQL

**SQL (Structured Query Language)** — язык для определения структуры и работы с реляционными данными.

Основные категории команд:
- DDL: `CREATE`, `ALTER`, `DROP` — структура объектов;
- DML: `INSERT`, `UPDATE`, `DELETE` — изменение данных;
- запросы: `SELECT` — чтение;
- управление транзакциями: `BEGIN`, `COMMIT`, `ROLLBACK`.

Пример:

```sql
SELECT id, name
FROM students
WHERE group_name = 'R3222'
ORDER BY name;
```

- `SELECT` задаёт выбираемые столбцы;
- `FROM` задаёт таблицу;
- `WHERE` фильтрует строки;
- `ORDER BY` задаёт сортировку.

## 9.3. Связи и внешние ключи

Например, один студент может иметь несколько записей об оценках. Тогда таблица `grades` может хранить `student_id`, ссылающийся на `students.id`.

```sql
CREATE TABLE students (
    id BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE grades (
    id BIGSERIAL PRIMARY KEY,
    student_id BIGINT NOT NULL REFERENCES students(id),
    grade INTEGER NOT NULL CHECK (grade BETWEEN 1 AND 5)
);
```

- `NOT NULL` запрещает отсутствие значения.
- `REFERENCES` задаёт внешний ключ.
- `CHECK` проверяет условие.
- `PRIMARY KEY` обеспечивает уникальность и идентификацию строки.

Ограничения полезны, потому что правила сохраняются на уровне БД даже при наличии нескольких приложений-клиентов. Проверка на уровне приложения тоже нужна, но она не заменяет ограничения целостности.

## 9.4. JOIN

**JOIN** объединяет строки связанных таблиц.

```sql
SELECT students.name, grades.grade
FROM students
JOIN grades ON grades.student_id = students.id;
```

`JOIN` (INNER JOIN) возвращает пары строк, для которых условие совпало. `LEFT JOIN` сохраняет все строки левой таблицы и дополняет отсутствующие совпадения значениями NULL.

## 9.5. ORM и JPA

**ORM (Object-Relational Mapping)** — сопоставление объектов программы с реляционными таблицами. Вместо ручного преобразования каждой строки в объект ORM помогает отображать поля классов на столбцы БД.

В Java распространены **JPA** и реализации, например Hibernate. JPA — спецификация/набор интерфейсов и правил persistence, а Hibernate — одна из реализаций. Spring Data JPA добавляет удобный repository-слой поверх JPA.

Упрощённый пример:

```java
@Entity
@Table(name = "students")
public class Student {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    protected Student() {}

    public Student(String name) {
        this.name = name;
    }
}
```

- `@Entity` отмечает класс как сущность JPA.
- `@Table` указывает таблицу.
- `@Id` задаёт первичный ключ.
- `@GeneratedValue` определяет стратегию генерации идентификатора.
- `@Column` задаёт параметры отображения поля.
- Конструктор без аргументов нужен JPA-провайдеру в типичных сценариях; часто его делают protected.

Это иллюстрация: реальная сущность требует корректных импортов, доступа к полям/свойствам и согласования схемы БД.

## 9.6. Repository

Repository — абстракция доступа к данным. В Spring Data JPA интерфейс может выглядеть так:

```java
public interface StudentRepository
        extends JpaRepository<Student, Long> {
}
```

Spring Data JPA предоставляет распространённые операции, например поиск по ID, сохранение и удаление. Параметры здесь означают тип сущности `Student` и тип её идентификатора `Long`.

Сервис обычно использует repository, а контроллер — сервис. Это разделяет транспортный слой и детали хранения.

## 9.7. Транзакции и ACID

**Транзакция** — группа операций, которую БД рассматривает как единое целое в соответствии с правилами транзакционной модели.

ACID:
- **Atomicity (атомарность)** — всё или ничего;
- **Consistency (согласованность)** — транзакция переводит БД из одного допустимого состояния в другое, если правила корректно заданы;
- **Isolation (изолированность)** — параллельные транзакции не должны мешать друг другу сверх выбранного уровня изоляции;
- **Durability (надёжность сохранения)** — после подтверждения транзакции её результат сохраняется в соответствии с гарантиями СУБД.

Пример: перевод денег должен уменьшить баланс одного счёта и увеличить баланс другого в рамках одной транзакции. Если вторая операция падает, первая не должна остаться зафиксированной отдельно.

В Spring `@Transactional` часто задаёт транзакционные границы метода. Поведение зависит от конфигурации, типа исключения и proxy-механизма; аннотация не означает, что любой произвольный вызов автоматически работает как транзакция.

## 9.8. SQL-инъекция и параметризованные запросы

SQL-инъекция возникает, когда недоверенный ввод небезопасно склеивается с SQL-кодом.

Небезопасная идея:

```text
"SELECT * FROM users WHERE name = '" + userInput + "'"
```

Правильный подход — параметризованные запросы/подготовленные выражения или ORM API, которые отделяют значения от структуры запроса. Не следует пытаться защититься только ручным удалением кавычек.

## 9.9. Миграции

**Миграция** — версионируемое изменение схемы БД: создать таблицу, добавить столбец, изменить ограничение. Миграции позволяют воспроизводимо обновлять БД в разных окружениях и хранить историю структуры рядом с кодом.

Не следует путать миграцию с резервной копией: миграция меняет схему/данные по сценарию, а backup нужен для восстановления.
