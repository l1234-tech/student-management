# 8. Spring Boot, DI, слои приложения и REST-контроллеры

## 8.1. Что такое Spring и Spring Boot

**Spring Framework** — Java-платформа, предоставляющая механизмы для создания приложений, в том числе контейнер объектов, внедрение зависимостей, web-слой и интеграцию с другими библиотеками.

**Spring Boot** упрощает настройку и запуск Spring-приложений за счёт автоконфигурации, starter-зависимостей и встроенного web-сервера. Он не заменяет Spring, а упрощает его использование.

Часто встречающиеся термины:
- **Dependency (зависимость)** — объект или компонент, который нужен другому объекту для работы.
- **Bean** — объект, которым управляет Spring IoC-контейнер.
- **IoC (Inversion of Control)** — инверсия управления: создание и связывание объектов делегируется контейнеру/фреймворку.
- **DI (Dependency Injection)** — внедрение зависимостей: готовые зависимости передаются компоненту извне, а не создаются им самостоятельно.
- **ApplicationContext** — основной интерфейс контейнера Spring, который хранит и предоставляет beans, обрабатывает конфигурацию и события.

## 8.2. Почему плохо создавать зависимости вручную внутри сервиса

Предположим, сервис должен хранить студентов.

Плотно связанный вариант:

```java
public class StudentService {
    private final StudentRepository repository =
            new JdbcStudentRepository();

    public Student find(long id) {
        return repository.findById(id);
    }
}
```

Проблема не в самом `new`, а в том, что сервис самостоятельно выбирает конкретную реализацию. Чтобы заменить JDBC на другую БД или тестовую заглушку, придётся менять сервис. Тестировать его изолированно труднее.

Вариант с внедрением:

```java
public class StudentService {
    private final StudentRepository repository;

    public StudentService(StudentRepository repository) {
        this.repository = repository;
    }

    public Student find(long id) {
        return repository.findById(id);
    }
}
```

Теперь зависимость передаётся через конструктор. Сервис не отвечает за создание репозитория — он использует переданный контракт.

Преимущества:
1. слабее связанность между классами;
2. реализацию можно заменить конфигурацией;
3. тестам можно передать mock/fake-объект;
4. зависимости явно видны в конструкторе;
5. проще поддерживать и расширять код.

## 8.3. DI в Spring: пример

```java
public interface StudentRepository {
    Student findById(long id);
}
```

```java
@Repository
public class JpaStudentRepository implements StudentRepository {
    // Реализация работы с JPA.
    @Override
    public Student findById(long id) {
        // Здесь опущена конкретная логика обращения к БД.
        return null;
    }
}
```

```java
@Service
public class StudentService {
    private final StudentRepository repository;

    public StudentService(StudentRepository repository) {
        this.repository = repository;
    }

    public Student find(long id) {
        return repository.findById(id);
    }
}
```

Spring обнаруживает компоненты (при корректной конфигурации component scanning), создаёт bean репозитория и передаёт его в конструктор сервиса. Важно: пример иллюстрирует структуру; рабочая реализация репозитория должна действительно выполнять запрос к данным.

Частые аннотации:
- `@Component` — общий компонент, управляемый Spring;
- `@Service` — компонент сервисного слоя;
- `@Repository` — компонент слоя доступа к данным; также участвует в переводе некоторых исключений доступа к данным;
- `@Controller` — MVC-контроллер, обычно возвращающий представления;
- `@RestController` — контроллер, у которого методы по умолчанию возвращают данные в тело ответа;
- `@Autowired` — механизм явного внедрения зависимостей; для единственного конструктора во многих современных версиях Spring аннотация не требуется;
- `@Configuration` — класс конфигурации;
- `@Bean` — метод, возвращающий объект, которым управляет контейнер.

## 8.4. Почему обычно выбирают constructor injection

**Constructor injection** — передача зависимостей через конструктор. Обычно это предпочтительный вариант, потому что:
- объект не создаётся в неполном состоянии, если зависимость обязательна;
- поле можно объявить `final`;
- зависимости видны из сигнатуры;
- объект легко создать в unit-тесте без запуска контейнера.

Field injection через `@Autowired` на поле короче, но скрывает обязательные зависимости и затрудняет создание объекта вручную. Setter injection полезен, когда зависимость действительно необязательна или должна изменяться после создания, но это не обычный выбор для обязательных зависимостей.

## 8.5. Слои приложения

Типичная архитектура:

```text
HTTP request
    ↓
Controller — маршрутизация, параметры, HTTP-ответ
    ↓
Service — бизнес-правила и сценарий операции
    ↓
Repository — чтение/запись
    ↓
Database
```

- **Controller** не должен содержать всю бизнес-логику.
- **Service** описывает операции предметной области.
- **Repository** скрывает детали хранения данных.
- **Entity** — объект, отображаемый на запись/сущность БД.
- **DTO (Data Transfer Object)** — объект для передачи данных между слоями или через API.

DTO полезен, потому что публичный формат API не обязан совпадать со структурой таблицы. Например, пароль или служебные поля сущности нельзя просто сериализовать в ответ пользователю.

## 8.6. Пример REST-контроллера

```java
@RestController
@RequestMapping("/api/students")
public class StudentController {
    private final StudentService service;

    public StudentController(StudentService service) {
        this.service = service;
    }

    @GetMapping
    public List<StudentDto> getAll() {
        return service.findAll();
    }

    @GetMapping("/{id}")
    public StudentDto getById(@PathVariable long id) {
        return service.findById(id);
    }
}
```

- `@RequestMapping` задаёт общий путь контроллера.
- `@GetMapping` связывает метод с HTTP GET.
- `@PathVariable` берёт значение из пути URL.
- Возвращаемый объект сериализуется в JSON при стандартной конфигурации Spring Boot с Jackson.
- `StudentDto` здесь условный DTO, который должен быть определён в проекте.

Для POST часто применяют `@PostMapping` и `@RequestBody`, чтобы разобрать JSON из тела запроса. Валидация может использовать `@Valid` и ограничения DTO.

## 8.7. IoC и DI — не синонимы

IoC — более общий принцип: контроль над созданием/связыванием объектов передаётся контейнеру или фреймворку. DI — конкретный способ реализовать IoC, передавая объекту нужные зависимости.

Ответ на вопрос «зачем DI?» лучше формулировать не как «так требует Spring», а через слабую связанность, тестируемость, явные контракты и заменяемость реализаций.

## 8.8. Жизненный цикл bean и области видимости

Spring создаёт beans, внедряет зависимости и может выполнять дополнительные шаги инициализации/завершения. По умолчанию многие beans являются singleton: контейнер предоставляет один экземпляр bean на соответствующий контекст/определение. Это не означает, что singleton автоматически потокобезопасен. Не стоит хранить пользовательское изменяемое состояние в singleton-сервисе без понимания конкуренции запросов.

## 8.9. Частые ошибки

- Считать, что DI — это просто аннотация `@Autowired`. Суть — передача зависимостей извне.
- Помещать SQL, HTTP-ответы и всю бизнес-логику в контроллер.
- Возвращать Entity напрямую, не думая о публичном контракте и чувствительных полях.
- Делать сервис зависимым от конкретного класса, если можно зависеть от интерфейса/контракта.
- Считать, что Spring «сам догадается» о любой зависимости: компоненты должны быть обнаружены или явно объявлены, а неоднозначные реализации нужно разрешать конфигурацией или квалификаторами.
