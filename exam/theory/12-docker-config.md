# 12. Docker, конфигурация и запуск приложения

## 12.1. Зачем нужен Docker

**Docker** — платформа для сборки и запуска контейнеров. Контейнер упаковывает приложение и его пользовательское окружение/зависимости в воспроизводимый формат. Он использует ядро операционной системы хоста, поэтому контейнер не то же самое, что полноценная виртуальная машина.

Проблема, которую помогает решить контейнеризация: на разных компьютерах могут отличаться версии библиотек, системные пакеты и конфигурация. Образ описывает окружение более предсказуемо.

## 12.2. Образ и контейнер

- **Image (образ)** — неизменяемый шаблон, из которого создают контейнеры.
- **Container (контейнер)** — запущенный или остановленный экземпляр образа с собственным состоянием выполнения.
- **Dockerfile** — инструкции для сборки образа.
- **Registry** — хранилище образов, например Docker Hub.
- **Volume** — механизм хранения данных вне жизненного цикла файловой системы контейнера.
- **Port mapping** — публикация порта контейнера на хосте, например `8000:8000`.

Остановка и удаление контейнера могут уничтожить данные, которые хранились только в его изменяемом слое. Для постоянных данных применяют volumes или внешние хранилища.

## 12.3. Dockerfile

Учебный пример для Python-приложения:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["python", "manage.py", "runserver", "0.0.0.0:8000"]
```

- `FROM` задаёт базовый образ.
- `WORKDIR` устанавливает рабочую директорию.
- `COPY` копирует файлы в образ.
- `RUN` выполняет команду при сборке.
- `EXPOSE` документирует порт, который приложение предполагает использовать; само по себе не публикует порт на хост.
- `CMD` задаёт команду по умолчанию при запуске контейнера.

Этот пример демонстрационный, не production-конфигурация. Для реального развёртывания нужно отдельно продумать production-сервер, безопасность, права, секреты, статику и health checks.

## 12.4. Docker Compose

**Docker Compose** описывает несколько сервисов и связи между ними в одном конфигурационном файле. Например, приложение и PostgreSQL могут запускаться вместе.

```yaml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_HOST: db
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: students
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
```

- `services` перечисляет контейнерные сервисы.
- `build` указывает сборку из Dockerfile.
- `ports` связывает порт хоста и контейнера.
- `environment` передаёт переменные окружения.
- `volumes` описывает постоянное хранилище.

В Compose сервис обычно доступен другому сервису по имени сервиса в общей сети: здесь backend использует хост БД `db`, а не `localhost`. Внутри контейнера `localhost` указывает на сам этот контейнер.

## 12.5. Конфигурация и секреты

**Конфигурация** — параметры, которые меняют поведение приложения в зависимости от окружения: адрес БД, порт, уровень логирования. **Секреты** — чувствительные значения: пароль БД, ключ подписи токена, API-ключ.

Не следует хранить реальные секреты в публичном репозитории. Обычно в Git добавляют шаблон вроде `.env.example` с названиями переменных и безопасными примерными значениями, а реальный `.env` добавляют в `.gitignore`.

Пример:

```env
DATABASE_HOST=localhost
DATABASE_PORT=5432
DATABASE_NAME=students
DATABASE_USER=app
DATABASE_PASSWORD=replace-me
```

Значение `replace-me` — заглушка, не реальный пароль. Переменные окружения помогают не зашивать конфигурацию в исходный код, но сами по себе не являются полноценным хранилищем секретов.

## 12.6. Порты и localhost

- `localhost` — адрес текущего сетевого окружения.
- `127.0.0.1` — IPv4 loopback-адрес.
- `5432` — стандартный порт PostgreSQL.
- `8000` часто используют для локального web-сервера разработки, но это соглашение, а не обязательное значение.

Если backend запускается на хосте, а БД тоже на хосте, `localhost:5432` может быть правильным адресом. Если backend работает внутри контейнера, а PostgreSQL — в другом контейнере Compose, обычно нужен адрес сервиса БД, например `db:5432`.

## 12.7. Сборка и запуск

Типичный цикл:
1. написать Dockerfile;
2. собрать образ (`docker build`);
3. запустить контейнер (`docker run`) или описать сервис в Compose;
4. проверить логи и доступность порта;
5. при необходимости подключить volume и переменные окружения;
6. корректно остановить сервис.

Docker не заменяет тестирование и не делает приложение автоматически безопасным. Ошибки конфигурации, уязвимые зависимости и неправильные права остаются проблемами приложения.
