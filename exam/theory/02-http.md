# 2. HTTP: запросы, ответы, методы, заголовки и статусы

## 2.1. HTTP и HTTPS

**HTTP (Hypertext Transfer Protocol)** — протокол прикладного уровня для обмена запросами и ответами между клиентом и сервером. Он определяет структуру сообщений, методы, заголовки и коды статуса, но сам по себе не задаёт бизнес-логику приложения.

**HTTPS** — HTTP, передаваемый через защищённое соединение TLS. TLS помогает обеспечить конфиденциальность, целостность данных и проверку подлинности сервера при корректной настройке сертификатов. HTTPS не означает, что само приложение автоматически безопасно: ошибки авторизации или SQL-инъекции всё ещё возможны.

## 2.2. Из чего состоит запрос

Пример HTTP-запроса в упрощённом текстовом представлении:

```http
POST /api/students HTTP/1.1
Host: localhost:8000
Content-Type: application/json
Accept: application/json

{"name":"Анна","group":"R3222"}
```

- **Метод** `POST` описывает тип действия.
- **Путь** `/api/students` указывает ресурс или маршрут.
- **Версия протокола** здесь `HTTP/1.1`.
- **Заголовки** передают метаданные.
- **Тело** содержит данные запроса; оно есть не у всех запросов.

Основные заголовки:

- `Content-Type` — формат тела, например `application/json`.
- `Accept` — какие форматы ответа клиент предпочитает получать.
- `Authorization` — учётные данные или токен доступа, если endpoint требует авторизацию.
- `Cookie` — cookies, отправляемые браузером серверу.
- `Cache-Control` — директивы кэширования.
- `Content-Length` — размер тела в байтах, когда используется.

Не путай `Content-Type` и `Accept`: первый описывает отправляемое тело, второй — желаемый формат ответа.

## 2.3. Из чего состоит ответ

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"id":42,"name":"Анна","group":"R3222"}
```

Ответ содержит статус, заголовки и необязательное тело. В этом примере сервер сообщает, что ресурс создан, и возвращает представление нового студента.

## 2.4. HTTP-методы

| Метод | Типичное назначение | Пример |
|---|---|---|
| `GET` | Получить представление ресурса | `GET /api/students` |
| `POST` | Создать ресурс или выполнить операцию | `POST /api/students` |
| `PUT` | Заменить ресурс целиком | `PUT /api/students/42` |
| `PATCH` | Частично изменить ресурс | `PATCH /api/students/42` |
| `DELETE` | Удалить ресурс | `DELETE /api/students/42` |

Это соглашения REST API, а не автоматическая гарантия: конкретный backend может определить маршруты иначе.

**Безопасный (safe) метод** по смыслу не должен запрашивать изменение состояния сервера; стандартный пример — GET. **Идемпотентный метод** означает, что повторение одинакового запроса имеет тот же предполагаемый эффект, что и один запрос. GET, PUT и DELETE по определению HTTP идемпотентны; POST обычно не считается идемпотентным. Например, повторный POST создания может создать дубликаты, если сервер не реализовал отдельную защиту.

## 2.5. Коды состояния

Статус сообщает результат обработки запроса. Первая цифра задаёт категорию.

### 2xx — успех

- **200 OK** — запрос успешно обработан.
- **201 Created** — ресурс создан.
- **202 Accepted** — запрос принят, но обработка может ещё не завершиться.
- **204 No Content** — операция успешна, тела ответа нет.

### 3xx — перенаправление

- **301 Moved Permanently** — постоянное перенаправление.
- **302 Found** — временное перенаправление в распространённой практике.
- **304 Not Modified** — ресурс не изменился относительно условий кэширования; браузер может использовать кэшированную копию.

### 4xx — проблема запроса или доступа

- **400 Bad Request** — некорректный запрос.
- **401 Unauthorized** — не предоставлены подходящие учётные данные для аутентификации.
- **403 Forbidden** — сервер понял запрос, но отказывает в доступе.
- **404 Not Found** — ресурс/маршрут не найден или сервер не раскрывает его существование.
- **405 Method Not Allowed** — метод не поддерживается для данного ресурса.
- **409 Conflict** — конфликт с текущим состоянием ресурса.
- **415 Unsupported Media Type** — неподдерживаемый формат тела.
- **422 Unprocessable Content** — синтаксически понятное содержимое не проходит семантическую проверку; конкретное использование зависит от API.

### 5xx — проблема на стороне сервера

- **500 Internal Server Error** — непредвиденная ошибка сервера.
- **502 Bad Gateway** — шлюз получил некорректный ответ от вышестоящего сервера.
- **503 Service Unavailable** — сервис временно недоступен или перегружен.
- **504 Gateway Timeout** — шлюз не дождался ответа от вышестоящего сервера вовремя.

Запомни принцип: 4xx обычно указывает на проблему запроса, данных или доступа; 5xx — на сбой в серверной обработке или инфраструктуре. Это полезное правило, но конкретная диагностика требует смотреть тело ответа и серверные логи.

## 2.6. JSON и сериализация

**JSON (JavaScript Object Notation)** — текстовый формат представления структурированных данных. Он поддерживает объекты, массивы, строки, числа, логические значения и `null`.

```json
{
  "id": 42,
  "name": "Анна",
  "active": true,
  "subjects": ["Java", "Web"]
}
```

**Сериализация** — преобразование объекта или структуры данных в формат передачи/хранения. **Десериализация** — обратное преобразование. Например, сервер превращает объект студента в JSON, а клиент разбирает JSON в JavaScript-объект.

В JSON имена полей и строковые значения пишутся в двойных кавычках. Комментарии и завершающие запятые стандартный JSON не поддерживает.

## 2.7. Запросы с параметрами

Пример фильтрации:

```http
GET /api/students?group=R3222&active=true
```

`group` и `active` — query-параметры. Они подходят для фильтрации, сортировки, поиска и постраничной выдачи.

Путь обычно обозначает конкретный ресурс: `/api/students/42`. Query-параметры уточняют выборку: `/api/students?group=R3222`.

## 2.8. Cookies, заголовки и тело

- **Cookie** — небольшой фрагмент данных, который браузер хранит и может отправлять серверу при соответствующих условиях.
- **Заголовок** — метаданные сообщения.
- **Тело запроса** — данные операции, например JSON для создания студента.
- **Тело ответа** — возвращаемые данные, HTML, JSON, файл или иной контент.

Cookies часто применяются для хранения идентификатора сессии. Не следует бездумно хранить в них секреты: безопасность зависит от атрибутов `Secure`, `HttpOnly`, `SameSite`, срока жизни и серверной логики.

## 2.9. Как обработать HTTP-ошибку в JavaScript

```js
async function loadStudents() {
  const response = await fetch("/api/students");

  if (!response.ok) {
    throw new Error(`HTTP error: ${response.status}`);
  }

  return response.json();
}
```

Важно: `fetch()` обычно не отклоняет Promise только потому, что сервер вернул 404 или 500. Он возвращает объект `Response`; поэтому нужно проверить `response.ok` или статус. Сетевые ошибки, напротив, обычно приводят к отклонению Promise.
