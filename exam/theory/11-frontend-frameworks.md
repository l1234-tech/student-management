# 11. Frontend-фреймворки, SPA, компоненты и состояние

## 11.1. Зачем нужен фреймворк

Когда интерфейс становится большим, ручное управление каждым DOM-узлом усложняется. **Frontend-фреймворк** предлагает архитектуру и инструменты для построения интерфейса из компонентов, работы с состоянием, маршрутизацией и жизненным циклом.

Библиотека обычно предоставляет отдельную функциональность, а фреймворк может задавать более целостную структуру приложения. В реальных проектах граница не всегда строгая.

Примеры технологий: React (часто называют библиотекой UI), Vue, Angular, Svelte. Они различаются синтаксисом и моделью обновления, но многие концепции похожи.

## 11.2. Компонент

**Компонент** — самостоятельная часть интерфейса, которую можно повторно использовать. Например, `StudentCard` отображает одного студента, а `StudentList` — список карточек.

Компонент обычно объединяет:
- структуру представления;
- входные параметры;
- логику взаимодействия;
- стили или правила оформления.

Компоненты уменьшают дублирование и помогают делить интерфейс по ответственности.

## 11.3. Props и state

**Props (properties)** — данные, которые компонент получает от родителя. Обычно компонент не должен напрямую изменять переданные props.

**State (состояние)** — данные, от которых зависит текущий интерфейс и которые могут изменяться со временем: введённый текст, выбранный фильтр, список студентов, состояние загрузки.

Пример концептуального состояния списка:
- `students` — данные;
- `loading` — идёт ли загрузка;
- `error` — ошибка, если она есть;
- `searchQuery` — текущий поисковый запрос.

Когда состояние меняется, фреймворк обновляет соответствующие части интерфейса согласно своей модели. Не нужно вручную изменять DOM в обход фреймворка без необходимости.

## 11.4. Декларативный UI

**Декларативный подход** означает, что код описывает, как интерфейс должен выглядеть при заданном состоянии, а фреймворк организует обновление.

Например, логика «если список пуст, покажи сообщение; иначе покажи элементы» описывается исходя из данных. Это отличается от императивного ручного создания и удаления каждого DOM-элемента.

## 11.5. SPA и маршрутизация

**SPA (Single-Page Application)** — веб-приложение, в котором основные переходы между представлениями выполняются клиентским JavaScript без полной загрузки нового HTML-документа при каждом переходе. SPA всё равно может загружать данные с backend и использовать HTTP API.

**Клиентская маршрутизация** сопоставляет URL и отображаемый компонент/представление в браузере. Например, `/students` показывает список, а `/students/42` — карточку конкретного студента.

Для SPA сервер часто должен возвращать стартовый HTML для клиентских маршрутов; иначе прямое открытие `/students/42` может привести к 404 на сервере, если маршрутизация не настроена.

SPA — не единственный способ строить сайты. Серверный рендеринг и гибридные подходы тоже широко используются.

## 11.6. Управление состоянием

Небольшое состояние можно хранить внутри компонента. Когда одно состояние нужно многим частям приложения, используют поднятие состояния к общему родителю, контекст или отдельные state-management решения.

**Однонаправленный поток данных** — подход, при котором данные идут по предсказуемому направлению, а изменения инициируются явными событиями/действиями. Он упрощает поиск причин изменения UI.

Важно различать:
- состояние интерфейса;
- данные, полученные с сервера;
- параметры URL;
- данные, которые должны пережить перезагрузку (например, серверное хранилище или подходящий браузерный storage).

Не всякое состояние нужно дублировать в нескольких местах: дублирование может привести к рассинхронизации.

## 11.7. Жизненный цикл и эффекты

Компоненты могут монтироваться, обновляться и размонтироваться. **Эффект** — работа, связанная с внешним миром: подписка на событие, запрос данных, таймер или синхронизация с API браузера. Конкретный механизм зависит от фреймворка.

Запросы данных нужно проектировать с учётом отмены/устаревших ответов, ошибок и повторных запусков. Нельзя полагаться на то, что любой эффект выполнится ровно один раз во всех режимах разработки и конфигурациях.

## 11.8. RxJS и Observable

**RxJS** — библиотека реактивного программирования для JavaScript. **Observable** описывает поток значений/событий, которые могут поступать во времени. Подписчик получает значения, ошибки и сигнал завершения.

**Subscription** — подписка на поток; её иногда нужно отменять, чтобы прекратить получение данных и избежать лишней работы. Операторы RxJS позволяют преобразовывать, фильтровать и комбинировать потоки.

Не путай Promise и Observable:
- Promise представляет один будущий результат или ошибку;
- Observable может выдавать ноль, одно или много значений во времени и часто поддерживает отмену через отписку.

RxJS особенно характерен для Angular-экосистемы, но не ограничен ею.

## 11.9. Какой фреймворк в лабораторной?

Если в условии лабораторной не зафиксирован конкретный фреймворк, нельзя автоматически считать React, Vue, Angular или Svelte обязательным. Сначала изучи требование и код проекта. Для теории можно знать общие идеи компонентов, состояния, маршрутизации и запросов, но реализацию и синтаксис нужно привязывать к выбранной технологии.
