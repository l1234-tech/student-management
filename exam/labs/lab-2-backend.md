# Лабораторная №2 — Python Backend и REST API

Источник: ТЗ «Лаб 2.pdf». В проекте см. [описание лабораторных 1–2](../../docs/labs-1-2.md).

## Требования
Разработать REST API для системы студентов. В ТЗ перечислены FastAPI, Flask и Django REST Framework. Frontend должен фильтровать студентов и работать stateless; бизнес-логика переносится на сервер. Модель студента сохраняется относительно лабораторной №1.

Обязательные маршруты из ТЗ: GET /api/requests, GET /api/requests/:id, POST /api/requests, PATCH /api/requests/:id, DELETE /api/requests/:id, QUERY /api/requests.

Фильтрация списка через query-параметры, например ?group=M3301&dormitory=8; при большом количестве параметров ТЗ предлагает QUERY.

Требуются JSON, корректные HTTP-коды, серверная валидация, уникальный ИСУ ID, хранение в памяти или JSON-файле, отдельные файлы маршрутов/бизнес-логики/доступа к данным и единый формат ошибок. В ТЗ перечислены коды 200, 201, 204, 400, 404, 409, 422, 500.

## Важные различия
- Path-параметр — часть пути, часто ID ресурса; query-параметр — параметр после вопросительного знака, например фильтр.
- Stateless не означает, что сервер не хранит БД. Он не должен зависеть от неявного состояния предыдущего запроса клиента.
- Клиентскую валидацию можно обойти, поэтому сервер проверяет входные данные самостоятельно.
- Обычно GET читает, POST создаёт, PATCH частично изменяет, DELETE удаляет.
- 201 — создано; 204 — успешно без тела; 404 — не найдено; 409 — конфликт; 422 часто применяется к семантически некорректным данным.
- Архитектурный поток: HTTP → маршрутизация → валидация → service → repository/storage → JSON.
