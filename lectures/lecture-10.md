# Лекция 10. Метафреймворки и серверный рендеринг

*Текстовый конспект по презентации «Лекция №10» из предоставленного архива.*

## CSR и SSR

При CSR браузер сначала загружает HTML-оболочку и JavaScript, затем выполняет код, запрашивает данные, формирует интерфейс и подключает обработчики. Поэтому первый экран зависит от загрузки и выполнения JS.

При SSR HTML формируется на сервере и приходит в браузер уже с содержимым. Это может улучшить время появления первого контента, но не ускоряет сам backend или базу данных. Медленный запрос к API задержит формирование HTML. Важные метрики: FCP (первое отображение контента), LCP (крупнейший видимый элемент), TTFB/TTFP — задержка до первого ответа/показа.

## SSG, ISR, SWR и гибридный рендеринг

- **SSG** — HTML создаётся во время сборки и может раздаваться через CDN.
- **ISR** — статические страницы обновляются постепенно, без полной пересборки всего сайта.
- **Revalidation** — правило проверки актуальности данных и обновления устаревшей копии.
- **SWR (stale-while-revalidate)** — сначала возвращается старая версия, а обновление выполняется в фоне.
- **Hybrid Rendering** — разные маршруты или части приложения используют разные стратегии.

Универсальной лучшей стратегии нет: выбор зависит от персонализации, частоты изменения данных, SEO и нагрузки.

## Метафреймворк и маршрутизация

Метафреймворк расширяет UI-фреймворк: добавляет файловую маршрутизацию, layouts, серверный рендеринг, middleware, серверную загрузку данных и другие механизмы.

Файловая маршрутизация определяет URL по структуре каталогов и файлов. Динамический сегмент, например `[id]`, позволяет построить страницу карточки по идентификатору. Layout сохраняет общую оболочку при переходах. Prefetch предварительно загружает ресурсы маршрута до клика.

## Hydration и окружения

Hydration — подключение клиентского JavaScript к HTML, который уже сформирован сервером, чтобы сделать его интерактивным. Hydration mismatch появляется, если серверная и клиентская версии первоначальной разметки различаются.

Частые причины: случайные значения, текущее время, разные локали/часовые пояса, чтение localStorage или window во время SSR. Browser-only API следует использовать на клиенте после гидратации. SSR-код должен учитывать, что сервер и браузер — разные окружения.

## Streaming SSR и Suspense

Streaming SSR передаёт HTML по частям: сначала shell и fallback, затем готовые блоки. Это полезно, когда независимые части страницы загружаются с разной скоростью. Streaming меняет время появления контента, но не ускоряет сами запросы.

Suspense boundary задаёт участок, для которого показывается fallback до готовности данных/компонента. Несколько независимых границ позволяют частям страницы появляться по мере готовности.

## Загрузка данных и Request Waterfall

Сервер может загружать данные для первого HTML, браузер — для интерактивных действий после гидратации. Часто используется сочетание обоих подходов.

Request Waterfall — последовательное выполнение независимых запросов. Если три запроса по 300 мс идут один за другим, ожидание близко к 900 мс. Если они независимы и запускаются параллельно через `Promise.all`, ожидание близко к самому долгому запросу — около 300 мс.

## Кеширование

Для кеша важны ключ, свежесть и правила обновления. Cache Hit означает, что данные найдены в кеше; Cache Miss — что их нужно получить из источника. HTTP Cache использует, в частности, Cache-Control и ETag. Revalidation проверяет актуальность сохранённой копии; TTL и события могут запускать обновление.

Кеш персональных данных должен учитывать пользователя и права доступа. После создания, изменения или удаления студента связанные кеши списка и карточки нужно обновить или инвалидировать.

## Связь с лабораторной №5

Для Vue-проекта выбран Nuxt. Требуется SSR, динамический маршрут `/students/[id]`, middleware для защищённых страниц, состояния loading/error/404 и обновление кеша после изменений. Java-backend лабораторной №3 остаётся источником бизнес-логики и данных; Nuxt отвечает за frontend-рендеринг и маршрутизацию.
