## Деплой и важные настройки

Сейчас проект настроен для учебного локального запуска. Это нормально для лабораторной и защиты, но перед реальным деплоем нужно помнить про несколько вещей.

### Что уже готово для запуска

- Зависимости описаны в `requirements.txt`.
- Django умеет отдавать HTML-шаблоны из `templates/`.
- Статика лежит в `static/`.
- Данные студентов лежат в `data/students_data.json`.
- API не требует авторизации, потому что это учебная лабораторная.

### Что важно поменять для настоящего сервера

В `config/settings.py` сейчас:

```python
DEBUG = True
ALLOWED_HOSTS = []
```

Для локальной разработки это удобно. Для настоящего деплоя нужно:

- поставить `DEBUG = False`, чтобы пользователи не видели технические ошибки Django;
- заполнить `ALLOWED_HOSTS`, например доменом или IP сервера;
- настроить отдачу static-файлов;
- убедиться, что у приложения есть права на запись в `data/students_data.json`;
- вынести `SECRET_KEY` из кода в переменные окружения, если это не учебный стенд.

### Почему JSON-файл подходит для лабораторной

По заданию можно использовать память или JSON-файл. Мы выбрали JSON-файл, потому что:

- данные не пропадают после перезапуска сервера;
- файл легко открыть и проверить вручную;
- не нужно поднимать отдельную базу данных;
- проще объяснить слой repository на защите.

Для реального проекта вместо JSON-файла обычно используют базу данных, например PostgreSQL или SQLite.

## Лабораторная 2

Во второй лабораторной мы перенесли основную логику на backend и сделали REST API.

Главные изменения:

- Добавлен Django-проект.
- Добавлено приложение `students`.
- Подключен Django REST Framework.
- Реализован REST API для студентов общежития.
- Cookie больше не используются для хранения студентов.
- Данные хранятся на сервере в JSON-файле `data/students_data.json`.

- Добавлена серверная валидация.
- Добавлен единый формат ошибок.
- Добавлены корректные HTTP-статусы.
- Добавлены фильтры на главной странице.

### Модель студента в API

В API студент имеет такую структуру:

```json
{
  "ISU": 123456,
  "name": "Ivan Ivanov",
  "group": "M3200",
  "dormitory": 1,
  "room": 1001,
  "checkin_date": "2024-01-01",
  "is_foreign": false,
  "note": "test"
}
```

Важно: `ISU` используется как уникальный идентификатор студента. Поэтому в URL `/api/requests/:id` значение `id` фактически означает ИСУ студента.

### REST API

| Метод | URL | Что делает |
| --- | --- | --- |
| `GET` | `/api/requests` | Получить список студентов |
| `GET` | `/api/requests/:ISU` | Получить одного студента по ИСУ |
| `POST` | `/api/requests` | Создать нового студента |
| `PATCH` | `/api/requests/:ISU` | Частично обновить студента |
| `DELETE` | `/api/requests/:ISU` | Удалить студента |
| `QUERY` | `/api/requests` | Отфильтровать студентов |

### Фильтрация

Backend поддерживает фильтры по полям:

- `ISU`
- `name`
- `group`
- `dormitory`
- `room`
- `is_foreign`

На главной странице добавлена форма фильтров. Она отправляет запрос `QUERY /api/requests` и перерисовывает таблицу результатами ответа.

Пример тела запроса:

```json
{
  "group": "M3200",
  "is_foreign": "true"
}
```

### HTTP-статусы

В проекте используются понятные HTTP-статусы:

| Статус | Когда используется |
| --- | --- |
| `200 OK` | Успешное получение, обновление или фильтрация |
| `201 Created` | Студент успешно создан |
| `204 No Content` | Студент успешно удален |
| `400 Bad Request` | Некорректный запрос, например неизвестный фильтр |
| `404 Not Found` | Студент не найден |
| `409 Conflict` | Студент с таким ИСУ уже существует |
| `422 Unprocessable Entity` | Данные понятны серверу, но не проходят валидацию |
| `500 Internal Server Error` | Непредвиденная ошибка сервера |

### Единый формат ошибок

Ошибки API возвращаются в одном формате:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Дата заселения не может быть в будущем",
    "details": {
      "checkin_date": ["Дата заселения не может быть в будущем"]
    }
  }
}
```

Зачем это нужно:

- frontend может одинаково обрабатывать разные ошибки;
- пользователю можно показать понятное сообщение;
- на защите проще объяснить поведение API;
- ошибки не зависят от внутренней структуры DRF.

## Что изменили для перехода на backend

Этот раздел полезен перед защитой, если нужно быстро понять, что именно поменялось по сравнению с первой лабораторной.

### Было в лабораторной 1

- JavaScript сам хранил список студентов в cookie.
- Добавление, редактирование и удаление происходили только в браузере.
- Если очистить cookie, данные пропадали.
- Если открыть сайт в другом браузере, список был пустой.
- Проверка данных была только на frontend.

### Стало в лабораторной 2

- JavaScript больше не хранит студентов.
- Frontend делает HTTP-запросы к backend.
- Backend хранит данные в JSON-файле.
- Валидация есть и на frontend, и на backend.
- Ошибки возвращаются в едином JSON-формате.
- У каждого действия есть правильный HTTP-метод и статус.

### Почему это называется stateless

Stateless означает, что сервер не держит состояние пользователя между запросами в сессии или cookie.

В нашем случае:

- frontend не хранит список студентов в cookie;
- каждый запрос содержит всю нужную информацию;
- backend берет данные из общего JSON-хранилища;
- результат не зависит от cookie конкретного браузера.

Например, чтобы удалить студента, frontend отправляет только:

```http
DELETE /api/requests/123456
```

Сервер сам находит студента с `ISU = 123456` в JSON-файле и удаляет его.

## Как frontend теперь работает с backend

### Главная страница

Файл: `static/js/index.js`

Что делает:

- загружает студентов через `GET /api/requests`;
- рисует таблицу;
- удаляет студента через `DELETE /api/requests/:ISU`;
- открывает форму редактирования через `/add-student/?id=:ISU`;
- открывает подробности через `/student/?id=:ISU`;
- отправляет фильтры через `QUERY /api/requests`.

### Форма добавления и редактирования

Файл: `static/js/student_form.js`

Что делает:

- если страница открыта без `id`, работает как добавление;
- если страница открыта с `?id=123456`, загружает студента через `GET /api/requests/123456`;
- при добавлении отправляет `POST /api/requests`;
- при редактировании отправляет `PATCH /api/requests/:ISU`;
- после успешного сохранения возвращает на главную страницу.

### Страница подробной информации

Файл: `static/js/student.js`

Что делает:

- берет `id` из URL;
- загружает студента через `GET /api/requests/:ISU`;
- показывает данные в таблице;
- если студент не найден, показывает сообщение об ошибке.

## Сравнение лабораторной 1 и лабораторной 2

| Критерий | Лабораторная 1 | Лабораторная 2 |
| --- | --- | --- |
| Основной фокус | Frontend | Backend + API |
| Хранение данных | Cookie в браузере | JSON-файл на сервере |
| Работа с данными | JavaScript напрямую менял массив | Frontend отправляет HTTP-запросы |
| Валидация | Только на клиенте | Клиентская и серверная |
| Архитектура | Страница сама хранит состояние | Stateless frontend + backend |
| Ошибки | Alert/локальная логика | Единый JSON-формат ошибок |
| Идентификатор | Внутренний `id` на frontend | `ISU` как единый идентификатор |
| Фильтрация | Не была полноценной API-операцией | `QUERY /api/requests` |

## Главное объяснение для защиты

Проект начинался как frontend-приложение, где браузер сам хранил студентов в cookie. Во второй лабораторной мы вынесли данные и бизнес-логику на backend. Теперь frontend только отображает интерфейс и отправляет HTTP-запросы, а backend отвечает за хранение, валидацию, фильтрацию и ошибки.

Это делает приложение ближе к реальной веб-архитектуре: клиент и сервер разделены, API можно тестировать отдельно, а данные не зависят от конкретного браузера.
