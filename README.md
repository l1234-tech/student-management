## Лабораторная 1. Frontend

В первой лабораторной был реализован клиентский интерфейс системы управления студентами без frontend-фреймворков.

### Цель первой лабораторной

Нужно было сделать интерфейс, который работает прямо в браузере: пользователь добавляет студентов через форму, видит их в таблице, может открыть подробную информацию, удалить запись или перейти к редактированию. На этом этапе серверной части ещё не было, поэтому данные хранились на стороне клиента.

### Что было сделано

- Главная страница со списком студентов в виде таблицы.
- Форма добавления и редактирования студента.
- Страница досье конкретного студента.
- Кнопки действий: добавить, редактировать, удалить, открыть подробную информацию.
- Минимальный адаптивный интерфейс на HTML и CSS.
- Клиентская логика на JavaScript в отдельных файлах.
- Валидация формы через HTML-атрибуты и JS.
- Favicon с котиком.

### Страницы первой версии

Главная страница:

- Показывала таблицу студентов.
- При загрузке читала список студентов из cookies.
- Динамически создавала строки таблицы через JavaScript.
- Содержала кнопки действий для каждой записи.

Форма студента:

- Использовалась и для добавления, и для редактирования.
- При добавлении создавала нового студента.
- При редактировании получала `id` из адресной строки и подставляла данные в поля формы.
- После сохранения возвращала пользователя на список студентов.

Страница досье:

- Получала `id` студента из query-параметра адреса.
- Находила нужного студента в сохранённых данных.
- Выводила все поля студента в таблицу "Тип - Значение".

### Модель студента

Модель студента включала:

- ФИО.
- Группу.
- ИСУ ID.
- Номер общежития.
- Комнату.
- Срок заселения.
- Признак иностранного студента.
- Заметки.

В первой версии объект студента собирался из формы примерно так:

```js
const student = {
  id: Date.now(),
  fullName: fullName,
  group: group,
  ISU: Number(ISU),
  numberHouse: Number(numberHouse),
  numberRoom: Number(numberRoom),
  date: date,
  inostran: inostran,
  note: note
};
```

`id` создавался через `Date.now()`, чтобы отличать записи друг от друга при удалении, редактировании и открытии досье.

### Хранение данных в cookies

По варианту использовались cookies. Так как cookies хранят только строки, массив студентов сериализовался в JSON:

```js
const data = encodeURIComponent(JSON.stringify(students));
document.cookie = `students=${data}`;
```

При чтении выполнялось обратное действие:

```js
const decodedData = decodeURIComponent(cookiesData);
const students = JSON.parse(decodedData);
```

То есть логика была такой:

```text
массив студентов -> JSON.stringify -> encodeURIComponent -> cookie
cookie -> decodeURIComponent -> JSON.parse -> массив студентов
```

### CRUD-операции на клиенте

Добавление:

- Пользователь заполнял форму.
- JS забирал значения из `input` и `textarea` через `document.getElementById()`.
- Создавался объект студента.
- Объект добавлялся в массив через `push()`.
- Массив сохранялся обратно в cookies.

Просмотр списка:

- Главная страница читала массив студентов из cookies.
- Таблица очищалась.
- Для каждого студента создавалась строка таблицы.

Удаление:

- У кнопки удаления был `data-id` студента.
- При клике JS получал этот `id` через `button.dataset.id`.
- Массив фильтровался через `filter()`.
- Обновлённый массив сохранялся в cookies.

Редактирование:

- Кнопка редактирования переводила на страницу формы с параметром `?id=...`.
- Форма по этому `id` находила студента.
- Поля автоматически заполнялись актуальными данными.
- При отправке формы старый объект заменялся обновлённым через `map()`.

Досье:

- Кнопка подробной информации переводила на страницу `student.html?id=...`.
- JS находил студента по `id`.
- Данные выводились в таблицу подробной информации.

### Валидация в первой лабораторной

Часть проверок была сделана HTML-атрибутами:

```html
<input type="number" required min="100000" max="999999">
<input type="date" required>
```

Часть проверок была реализована через JavaScript:

- ФИО должно состоять из букв.
- Группа должна соответствовать формату.
- ИСУ должен быть числом.
- ИСУ не должен начинаться с нуля.
- Дата заселения не должна быть в будущем.
- ИСУ должен быть уникальным среди студентов.

Ошибки показывались рядом с полями формы, а некорректные поля получали отдельный CSS-класс.

### Работа с DOM и событиями

В первой лабораторной активно использовались стандартные возможности браузера:

- `document.getElementById()` для поиска формы, таблицы и полей ввода.
- `document.querySelectorAll()` для поиска кнопок действий.
- `addEventListener()` для обработки `submit` и `click`.
- `innerHTML` и создание строк таблицы для изменения интерфейса.
- `window.location.href` для переходов между страницами.
- `URLSearchParams` для чтения `id` из адресной строки.

Пример перехода к редактированию:

```js
window.location.href = `student_form.html?id=${id}`;
```

### Ограничение первой версии

Главное ограничение первой лабораторной: приложение не было stateless. Данные жили в cookies конкретного браузера, поэтому другой браузер или другое устройство не видели этих студентов. Именно это стало причиной переноса бизнес-логики и хранения данных на backend во второй лабораторной.

## Лабораторная 2. Backend

Во второй лабораторной проект был перенесён на backend и стал работать через REST API.

### Цель второй лабораторной

Нужно было убрать хранение и основную бизнес-логику из браузера и перенести её на сервер. После этого frontend должен был стать stateless: он только отображает данные и отправляет запросы, а состояние студентов хранится и обрабатывается на backend.

### Использованный стек

- Python.
- Django.
- Django REST Framework.
- HTML, CSS, JavaScript.
- JSON-файл как простое серверное хранилище.

### Что изменилось по сравнению с первой лабораторной

- Бизнес-логика была перенесена с клиента на сервер.
- Frontend стал stateless: страницы получают и изменяют данные через API.
- Вместо cookies используется серверное хранение в `data/students_data.json`.
- Добавлена серверная валидация входных данных.
- Добавлена фильтрация студентов через query-параметры и метод `QUERY`.
- Ошибки API возвращаются в едином формате.
- Для студента используется уникальный идентификатор `ISU`.

### Как устроен backend

Backend реализован как Django-проект с приложением `students`.

Основное разделение по слоям:

- `views.py` принимает HTTP-запросы и возвращает HTTP-ответы.
- `urls.py` связывает URL-адреса с обработчиками.
- `serializers.py` проверяет входные данные.
- `services.py` содержит бизнес-логику.
- `repository.py` отвечает только за чтение и запись данных.
- `errors.py` описывает единый формат ошибок.

Такой подход нужен, чтобы маршруты, бизнес-логика, валидация и работа с данными не были смешаны в одном файле.

### Слой views

В `students/views.py` есть два типа обработчиков.

Первый тип отдаёт HTML-страницы:

- главная страница со списком студентов;
- страница формы добавления/редактирования;
- страница досье студента.

Второй тип реализует API:

```python
@api_view(['GET', 'POST', 'QUERY'])
def api_requests(request):
    ...
```

и:

```python
@api_view(['GET', 'PATCH', 'DELETE'])
def api_request_detail(request, ISU: int):
    ...
```

`views.py` не хранит студентов сам. Он вызывает функции из `services.py` и возвращает результат в JSON-формате.

### Слой services

В `students/services.py` находится бизнес-логика:

- получить список студентов;
- применить фильтры;
- найти студента по ИСУ;
- создать студента;
- обновить студента;
- удалить студента.

Например, при создании студента сервис сначала проверяет уникальность ИСУ:

```python
def create_student(data: dict) -> dict:
    if repo.get_by_id(int(data["ISU"])) is not None:
        raise ConflictError(f"Студент с ИСУ {data['ISU']} уже существует")
    return repo.add(data)
```

То есть `ISU` используется как уникальный идентификатор ресурса.

### Слой repository

В `students/repository.py` вынесена работа с JSON-файлом.

Repository умеет:

- прочитать всех студентов из `data/students_data.json`;
- найти студента по `ISU`;
- добавить запись;
- обновить запись;
- удалить запись;
- сохранить список обратно в файл.

Данные сохраняются через временный файл и `os.replace()`, чтобы уменьшить риск повреждения JSON-файла при записи.

### Серверное хранилище

Вместо cookies используется файл:

```text
data/students_data.json
```

Это не полноценная база данных, но для лабораторной подходит, потому что:

- данные сохраняются после перезапуска сервера;
- файл легко открыть и проверить вручную;
- не нужно настраивать отдельную СУБД;
- удобно показать слой repository на защите.

### Stateless frontend

После второй лабораторной браузер больше не хранит состояние студентов.

Теперь frontend работает так:

```text
страница открылась
JS делает fetch-запрос к API
сервер возвращает JSON
JS отрисовывает данные в DOM
```

Например, главная страница загружает список студентов через:

```js
await fetch("/api/requests");
```

Создание и редактирование происходят через `POST` и `PATCH`, удаление - через `DELETE`, а подробная информация загружается через `GET /api/requests/:ISU`.

### Frontend после подключения backend

HTML-страницы были перенесены в Django templates:

```text
templates/students/index.html
templates/students/student_form.html
templates/students/student.html
```

Статические файлы были перенесены в:

```text
static/css/
static/js/
static/images/
```

JavaScript теперь не работает напрямую с cookies. Вместо этого он обращается к API:

- `static/js/index.js` загружает список, применяет фильтры, удаляет студентов и делает переходы.
- `static/js/student_form.js` отправляет `POST` или `PATCH` для создания и редактирования.
- `static/js/student.js` загружает досье конкретного студента.
- `static/js/validation.js` оставляет клиентскую проверку формы перед отправкой.

### Фильтрация студентов

Фильтрация реализована на сервере в `services.list_students()`.

Поддерживаются поля:

```text
ISU, name, group, dormitory, room, is_foreign
```

Для обычной фильтрации можно использовать query-параметры:

```text
/api/requests?group=M3301&dormitory=8
```

Если фильтров становится много, frontend использует метод `QUERY` и отправляет фильтры JSON-телом запроса:

```js
fetch("/api/requests", {
  method: "QUERY",
  headers: {
    "Content-Type": "application/json"
  },
  body: JSON.stringify(filters)
});
```

### Формат ответа API

Успешные ответы возвращаются в единой обёртке:

```json
{
  "data": {
    "ISU": 123456,
    "name": "Иванов Иван Иванович"
  }
}
```

Для списка студентов возвращается массив в поле `data`:

```json
{
  "data": [
    {
      "ISU": 123456,
      "name": "Иванов Иван Иванович"
    }
  ]
}
```

Ошибки возвращаются в едином формате через специальные классы ошибок:

```json
{
  "error": {
    "code": "not_found",
    "message": "Студент с ИСУ 123456 не найден"
  }
}
```

### HTTP-коды

В проекте используются стандартные HTTP-коды:

- `200 OK` - успешное получение или обновление данных.
- `201 Created` - студент создан.
- `204 No Content` - студент удалён.
- `400 Bad Request` - неверный запрос или неизвестный фильтр.
- `404 Not Found` - студент не найден.
- `409 Conflict` - студент с таким ИСУ уже существует.
- `422 Unprocessable Entity` - ошибка валидации.
- `500 Internal Server Error` - внутренняя ошибка сервера.

### Примеры запросов

Получить всех студентов:

```powershell
curl http://127.0.0.1:8000/api/requests
```

Получить студента по ИСУ:

```powershell
curl http://127.0.0.1:8000/api/requests/123456
```

Создать студента:

```powershell
curl -X POST http://127.0.0.1:8000/api/requests `
  -H "Content-Type: application/json" `
  -d '{"ISU":123456,"name":"Иванов Иван Иванович","group":"M3301","dormitory":8,"room":1201,"checkin_date":"2024-09-01","is_foreign":false,"note":"Без замечаний"}'
```

Обновить студента:

```powershell
curl -X PATCH http://127.0.0.1:8000/api/requests/123456 `
  -H "Content-Type: application/json" `
  -d '{"room":1202}'
```

Удалить студента:

```powershell
curl -X DELETE http://127.0.0.1:8000/api/requests/123456
```

## Реализация API

Основные маршруты:

| Метод | URL | Назначение |
| --- | --- | --- |
| `GET` | `/api/requests` | Получить список студентов |
| `GET` | `/api/requests/:ISU` | Получить одного студента по ИСУ |
| `POST` | `/api/requests` | Создать студента |
| `PATCH` | `/api/requests/:ISU` | Обновить студента |
| `DELETE` | `/api/requests/:ISU` | Удалить студента |
| `QUERY` | `/api/requests` | Получить список с фильтрацией |

Пример фильтрации:

```text
GET /api/requests?group=M3301&dormitory=8
```

или через `QUERY`:

```json
{
  "group": "M3301",
  "dormitory": 8
}
```

## Валидация

В проекте есть два уровня валидации.

Клиентская валидация:

- `required`, `type="number"`, `min`, `max`, `pattern` в HTML.
- Проверки в `static/js/validation.js`.
- Проверка формата группы: первая буква и затем 4-5 цифр.

Серверная валидация:

- Реализована в `students/serializers.py`.
- Проверяется ФИО, группа, ИСУ, общежитие, комната, дата заселения и типы данных.
- При создании студента проверяется уникальность `ISU`.
- При ошибках API возвращает корректные HTTP-коды: `400`, `404`, `409`, `422`, `500`.

## Что важно на защите

- HTML отвечает за структуру страниц и формы.
- CSS отвечает за внешний вид и адаптивность.
- JavaScript работает с DOM, событиями пользователя и `fetch()`.
- JSON используется для обмена данными между frontend и backend.
- REST API разделяет клиентскую часть и серверную бизнес-логику.
- Django views принимают HTTP-запросы и возвращают JSON-ответы.
- Services содержат бизнес-логику CRUD и фильтрации.
- Repository изолирует работу с JSON-файлом.
- Serializer выполняет серверную валидацию данных.
- Приложение во второй лабораторной работает stateless: состояние хранится на сервере, а не в браузере.
